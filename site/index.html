Scan your own code before anyone else does.

Security scanner for your own projects — code, Git history and your local web app, checked on your machine.

It only scans GitHub repositories you are authorized for, checks that again on every scan, and never uploads your code or results.

What it checks

Three areas, picked per scan. Every result says what was and was not checked: each area is completed, partial, not tested or not selected. pgard rules list prints the full catalog.

Area Looks for Bounds
code SQL injection, XSS, SSRF, OS command execution, path traversal; weak or hardcoded cryptography, plaintext passwords, cookie flags, CSRF, missing rate limiting on login routes Current files and configuration, uncommitted ones included. Build output and dependency directories are skipped and listed.
history Committed .env files, secrets in tracked files, secrets that only exist in history Secret values are redacted in every output.
web Security headers, cookie flags, CORS with credentials, version disclosure, directory listing, exposed /.env and /.git A service on 127.0.0.1 you confirm. Anonymous GET and HEAD only, no forms. 20 pages, depth 2, 5 s per request, 60 s total.

Output

terminal The result with coverage per area. --panels opens a read-only full-screen view: overview, charts, coverage, findings.
dashboard pgard dashboard starts a local web dashboard on 127.0.0.1 with a per-session token. It is not hosted anywhere.
json --format json prints only the redacted result on stdout; progress goes to stderr. The schema is documented and versioned.
sarif --format sarif prints SARIF 2.1.0. Upload it to GitHub code scanning yourself after a local scan that exits 0 (command in the README). Never after exit 3, 4 or 5: a partial scan would close alerts for areas that were never checked.
html, pdf --report both --output-dir ./reports writes redacted reports to an existing folder you choose, never overwriting a file.
baseline pgard baseline set keeps a scan; later scans list matching findings under “In baseline”, so new ones stand out.
incremental A repeat scan reads only what changed and says so. --full scans everything again.
standards Rules map to OWASP Top 10 2025, CWE Top 25 2025 and, where one applies, SEI CERT Java. The map shows rules ran, partial, not run or no rules. It never says safe.
language Rule texts, result screens and report headings in English or Korean. Scan evidence, coverage notes and authorization reasons stay English.

How authorization works

A scanner is also a tool for probing other people's code. So before every scan, in the CLI and the dashboard, PGARD runs the five checks again. Only the GitHub sign-in is reused; there is no option to skip them and no cached approval. If any evidence is missing or unclear, the scan is blocked (exit code 3) and PGARD says which check failed and why.

  1. RepositoryThe current directory is a Git repository root with valid history and one unambiguous github.com remote.
  2. GitHub identityYou sign in once with the device flow; the sign-in is kept in the OS keychain.
  3. Owner approvalThe owner installed the PGARD GitHub App. For an organization repository you must be an active owner of the organization.
  4. Current accessGitHub says you currently have at least read access.
  5. ContributionOwners are exempt, but local history must share a commit with the default branch. Everyone else needs a merged pull request or a verified signed commit there.

Installing the App on the owner account is the owner's approval, and PGARD can never do it for you. The App ships its public client id; there is no client secret. If the install is all that is missing, PGARD prints the link, waits up to 10 minutes and runs all five checks again from scratch.

$ pgard login$ pgard project verify$ pgard scan

What stays, what leaves

Stays on your machine

  • Source code, Git history and scan results
  • Stored results: the last 20 scans per repository for 90 days, owner-only permissions on macOS and Linux. Opt out with --no-store, delete with pgard history clear --all
  • Your GitHub sign-in, in the OS keychain, never written to a file or printed
  • Reports you export, saved only where you choose

Goes over the network

  • GitHub, during scans: sign-in and the metadata authorization needs (identity, App installation, organization membership, access, contributions), including the SHAs of local commits
  • The OSV export host, only when you run pgard advisories update: a download of public vulnerability data. Nothing is uploaded
  • Loopback only: one GET / to each local port after authorization passes, to show you what it is

This website is static pages. It does not scan, collect data or offer sign-in or upload, and it is not the dashboard: the dashboard runs on your computer.

Limits

  • coveragePartial coverage is shown, not hidden, and a partial scan exits with code 4.
  • languagesPython and PHP are not analyzed yet. Java and Kotlin cover three categories, so a clean Java result says nothing about XSS, SSRF or cryptography.
  • dependenciesNo matching against known vulnerabilities (CVE, OSV) yet. PGARD ships no vulnerability database; it can read lockfiles and the user-run OSV download is groundwork.
  • remoteOnly a service on 127.0.0.1 that you confirm. No logged-in browsing, no attack or state-changing requests.
  • signalsDetection is pattern based and not complete; no findings does not mean secure. A badly built app can change state on a GET.
  • accuracyThe accuracy corpus is small (about ten samples per rule) and written by the authors. A good score there is not a promise about your code.

Next, with no dates: more languages and categories, matching dependencies against advisories, a pre-commit check. Open issues

FAQ

Does my code leave my machine?

No. Code, Git history and results are processed on your computer and not uploaded. The full list of what goes over the network is above.

Why does it need a GitHub sign-in?

To prove you are allowed to scan: your identity, the owner's App installation, your current access and your ownership or contribution. The token is kept in your OS keychain, never in a file.

Which repositories can I scan?

Your own, once the PGARD GitHub App is installed on your account (PGARD guides you through it). Someone else's personal repository only if its owner installed the App and you have current read access plus a merged pull request or a verified signed commit on the default branch. Organization repositories only if you are an active owner of the organization and the App is installed with access to the repository. Remote repositories are never scanned: the target is always the Git root of your current directory.

Is a clean result proof that my project is safe?

No. Every result lists what was not checked, and the standards map shows how few weaknesses in a category have a rule at all. See Limits.

Does it run on Windows?

Yes. macOS, Linux and Windows are supported and CI runs the full test suite on all three. On Windows the sign-in is kept in Credential Manager. The old console window (legacy conhost) and visual rendering have not been verified by a user.

Can I use it in CI?

Not today. Every scan needs a GitHub sign-in that a CI runner does not have, so a runner would produce a blocked result. Run PGARD locally and read --format json or --format sarif and the exit codes (0 completed, 3 blocked, 4 partial) in your own scripts.

How is it different from a hosted scanner?

Your code is not copied to a service. The trade-offs: you run it yourself, there is no hosted dashboard or continuous monitoring, and it asks GitHub whether you are allowed to scan.

How do I report a vulnerability in PGARD?

Privately, not in a public issue: use Report a vulnerability on the repository's Security tab. The security policy has the scope. There is no bug bounty.
