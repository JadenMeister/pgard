Scan your own code before anyone else does.

Security scanner for your own projects — code, Git history and your local web app, checked on your machine. It only scans GitHub repositories you are authorized for, checks that again on every scan, and never uploads your code or results.

01

How it works.

Three steps, all from your terminal.

  1. Install

    From npm or Homebrew.

    First release coming soon. Build from source today.

    $ npm install -g pgard
    $ git clone https://github.com/JadenMeister/pgard.git$ cd pgard$ npm ci$ npm run build

  2. Sign in and authorize

    Sign in to GitHub once with the device flow. The owner installs the PGARD GitHub App; PGARD then checks five things and tells you what is missing.

    $ pgard login$ pgard project verify

  3. Scan locally, view the results

    Code and Git history are scanned on your machine. Read the result in the terminal, in a full-screen panel view, or in the local dashboard.

    $ pgard scan --panels$ pgard dashboard

03

Features.

What is in the box today. Each line matches the README.

Code, history, local web

Three scan areas, chosen per scan. Every result says what was and was not checked.

Languages

JavaScript, TypeScript, React, Vue and Go. Java and Kotlin for SQL, command and path rules. Python and PHP are not analyzed yet.

OWASP, CWE, CERT

Rules map to OWASP Top 10 2025 and CWE Top 25 2025, and to SEI CERT Java rules where one applies. The map never says “safe”.

SARIF, JSON, HTML, PDF

Machine-readable output for scripts and code scanning, and reports you can read or share. English and Korean.

CLI panels

pgard scan --panels opens a read-only full-screen view in your terminal: overview, charts, coverage, findings.

Local dashboard

pgard dashboard starts a local web dashboard on 127.0.0.1 with a private session token. It is not hosted anywhere.

Baseline and history

Keep a scan as the baseline and later scans highlight what is new. Stored results stay on your computer and can be deleted.

Incremental scans

A repeat scan only looks at what changed and says so in the result. --full scans everything again.

Authorization gate

Five checks run again before every scan. There is no option to skip them.

04

What it checks.

Three areas, picked per scan, and what runs depends on the language. Run pgard rules list for the full catalog.

code

Code

Current source code and configuration.

  • SQL injection, XSS, SSRF, OS command execution and path traversal
  • Weak or hardcoded cryptography, plaintext passwords, cookie flags, CSRF, missing rate limiting on login routes
  • Walks the working tree; build output and dependency directories are skipped and listed

history

Git history

Committed secrets, past and present.

  • Committed .env files
  • Secrets in tracked files and secrets that only exist in history
  • Secret values are redacted in every output

web

Your local web service

Only a service you run on 127.0.0.1, and only after you confirm it.

  • Anonymous GET and HEAD requests only, no form submissions
  • Security headers, cookie flags, CORS with credentials, version disclosure, directory listing, exposed /.env and /.git
  • Limits: 20 pages, depth 2, 5 s per request, 60 s total

Languages and categories

Language Categories
JavaScript, TypeScript SQL injection, XSS, SSRF, command execution, path traversal, cryptography, password storage, cookies, CSRF, rate limiting
React, Vue XSS in dangerouslySetInnerHTML and v-html, plus the JavaScript and TypeScript rules
Go SQL injection (database/sql, GORM), command execution, path traversal, SSRF, cryptography, cookies
Java, Kotlin Only three categories: SQL injection, command execution and path traversal (also MyBatis mapper XML). Nothing else is checked yet.
Python, PHP Detected, not analyzed yet. The coverage shows them as not tested.

The standards map shows rules ran, rules partial, not run or no rules for each OWASP Top 10 2025 category and CWE Top 25 2025 entry. It never says safe, and nothing is shown in green.

05

Integrations and outputs.

PGARD writes files and streams. Where they go is your decision; PGARD uploads nothing.

SARIF to code scanning

SARIF 2.1.0 on stdout, ready to upload to GitHub code scanning in your own workflow. Upload only when the exit code is 0: a partial scan would close alerts for areas that were never checked.

$ pgard scan --format sarif > pgard.sarif

JSON for scripts

Only the redacted result goes to stdout; progress and prompts go to stderr, so the file is valid JSON. The schema is documented and versioned. Result schema

$ pgard scan --format json > result.json

HTML and PDF reports

Redacted reports in English or Korean, written to an existing folder you choose. Existing files are never overwritten.

$ pgard scan --report both --output-dir ./reports

06

Authorization first.

PGARD scans a repository only when it has evidence that you are allowed to.

Five checks run before every scan, in the CLI and in the dashboard. There is no option to skip them and no cached approval. If any evidence is missing or unclear, the scan is blocked (exit code 3) and PGARD says which check failed and why.

  1. RepositoryThe current directory is a Git repository root with valid history and one unambiguous github.com remote.
  2. GitHub identityYou sign in with the GitHub device flow, or reuse the sign-in saved in your OS keychain.
  3. Owner approvalThe PGARD GitHub App is installed by the owner of the repository. For an organization, you must be an active owner.
  4. Current accessGitHub says you currently have at least read access.
  5. ContributionOwners are exempt from proving a contribution, but local history must still share a commit with the default branch. Everyone else needs a merged pull request or a verified signed commit.

Why it exists.

PGARD is for people checking their own projects. A security scanner is also a tool for probing other people's code, so PGARD refuses to run on anything it cannot tie to you and to the owner's approval, every time, and tells you how to fix a blocked state.

The GitHub App.

Sign-in uses the PGARD GitHub App through the device flow; the app ships its public client id and PGARD has no client secret. Installing the App on the owner account is the owner's approval, and PGARD can never do it for you. If that is the only thing missing, PGARD prints the install link, waits up to 10 minutes, then runs all five checks again from scratch.

07

Local-first.

Your code, history and results are processed on your computer.

Stays on your machine

  • Source code, Git history and scan results
  • Stored results: your last 20 scans per repository for 90 days, with owner-only permissions on macOS and Linux. Opt out with --no-store, delete with pgard history clear --all
  • Your GitHub sign-in, kept in the OS keychain and never written to a file or printed
  • Reports you export, saved only where you choose

Goes over the network

  • GitHub, during scans: sign-in and the metadata needed for authorization (your identity, the App installation, organization membership, your access, your contributions). To check contribution, PGARD sends the SHAs of local commits
  • The OSV export host, only when you run pgard advisories update yourself: a download of public vulnerability data. Nothing is uploaded
  • Loopback only: one GET / to each local port after authorization passes, to show you its identity

This website (pgard.dev) is static pages only. It does not scan anything, collect data, or offer sign-in or upload. It is not the dashboard: the dashboard runs on your computer.

08

Honest limits.

Short and frank. PGARD is pre-release.

  • Partial coverage is shown, not hidden. Each area is completed, partial, not tested or not selected, and a partial scan exits with code 4.
  • Python and PHP are not analyzed yet. Java and Kotlin cover three categories only, so a clean Java result says nothing about XSS, SSRF or cryptography.
  • No dependency vulnerability matching yet. PGARD ships no vulnerability database; the user-run OSV download is groundwork.
  • No remote scanning: only a service on 127.0.0.1 that you confirm. No logged-in browsing, no attack or state-changing requests.
  • Findings are signals, not proof. Detection is pattern based and not complete, and no findings does not mean secure. A badly built app can change state on a GET.
  • The accuracy corpus is small (about ten samples per rule) and written by the authors. A good score there is not a promise about your code.

Who it is for.

People who own the code they scan.

Solo developers, before a push

Scan the working tree and Git history of your own project, including uncommitted files. A repeat scan only re-reads what changed.

Teams reviewing their own repositories

Keep a baseline so new findings stand out, and send SARIF to code scanning from your own workflow. Organization repositories can be scanned by an organization owner.

FAQ

Does my code leave my machine?

No. Code, Git history and results are processed on your computer and are not uploaded. During scans PGARD contacts GitHub only, for sign-in and the metadata needed for authorization (including the SHAs of local commits, to check contribution). The one other destination is the OSV export host, and only if you run pgard advisories update yourself: it downloads public data and uploads nothing.

Why does it need a GitHub sign-in?

To prove you are allowed to scan. PGARD checks your GitHub identity, that the owner installed the PGARD GitHub App, that you currently have access and that you own the repository or contributed to it. The token is kept in your OS keychain, never in a file.

Which repositories can I scan?

A repository you own, or an organization repository where you are an active owner, provided the PGARD GitHub App is installed on it. Other people need the owner to install the App, and a merged pull request or a verified signed commit in the default branch. Remote repositories are never scanned: the target is always the Git root of your current directory.

Is a clean result proof that my project is safe?

No. Findings are signals, detection is not complete, and no findings does not mean secure. Every result lists what was not checked, and the standards map shows how few weaknesses in a category have a rule at all.

What about Python and PHP?

Python and PHP files are detected but not analyzed yet; the coverage shows them as not tested. Java and Kotlin are checked for SQL injection, command execution and path traversal only.

Does it run on Windows?

Yes. macOS, Linux and Windows are supported and CI runs the full test suite on all three. On Windows the sign-in is kept in Credential Manager. The old console window (legacy conhost) and visual rendering have not been verified by a user.

Can I use it in CI?

Not as a documented setup yet. Sign-in is interactive and every scan checks authorization live. What exists today: --format json and --format sarif, and exit codes (0 completed, 3 blocked, 4 partial) that scripts can read on your own machine.

How is it different from a hosted scanner?

PGARD runs on your computer and uploads nothing, so your code is not copied to a service. The trade-offs are that you run it yourself, there is no hosted dashboard or continuous monitoring, and it asks GitHub whether you are allowed to scan.

Does it check dependencies for known CVEs?

Not yet. PGARD ships no vulnerability database and does not match dependency versions against advisories. It can read lockfiles and download public OSV data on request, which is groundwork for a later check.

How do I report a vulnerability in PGARD?

Privately, not in a public issue. Use the Report a vulnerability button on the repository's Security tab. See the security policy for the scope. There is no bug bounty.
