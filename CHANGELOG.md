# Changelog

All notable changes to PGARD are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project follows [Semantic Versioning](https://semver.org) with the pre-1.0 policy in [docs/RELEASING.md](docs/RELEASING.md). There is no release yet; everything merged so far is listed under Unreleased.

## [Unreleased]

### Security

- The published package bundles its pure-JavaScript third-party dependencies (#358). The TypeScript compiler, `pdfkit` and `fontkit`, `@vue/compiler-sfc` with `postcss` and `@babel/parser`, and their transitive dependencies (33 packages) are built into `dist/` at release time, so a malicious patch release of any of them published later cannot reach users who install `pgard`. Only `@napi-rs/keyring` (native) and `web-tree-sitter` (WebAssembly) remain as `dependencies`, both exact pins. The pack step fails for a bundled package without a license text or with a license outside a permissive allowlist (MIT, ISC, BSD-2/3-Clause, Apache-2.0, 0BSD, BlueOak-1.0.0, CC0-1.0, Python-2.0), and for module loading by a computed path outside a reviewed allowlist. No source maps are shipped. `NOTICE.md` in the package now lists every bundled package with its license text (generated at pack time).
- `packaging/homebrew/update-formula.sh` no longer trusts the registry alone (L3 of #358). Besides the registry's sha512 it compares the tarball with the claims in the registry's attestation document (a consistency check), and it then requires an independent root of trust: `gh attestation verify` (signature and signing identity: repository, release workflow, tag via `--source-ref`, GitHub-hosted runner via `--deny-self-hosted-runners`) or `EXPECTED_SHA256` copied from the GitHub run summary. Without either it exits 1 and leaves the formula alone; `PGARD_I_ACCEPT_UNVERIFIED_PROVENANCE=1` is the one explicit override. The release workflow prints the tarball sha256 in the `verify` job and again, for the bytes it publishes, in the `publish` job. The pack also keeps `/*!` license banners in `dist/`, picks up `*Notice*` files as license text, refuses bundled code that imports a package its own manifest does not declare, and pins the reviewed dynamic-loading allowlist to exact expressions.

### Changed

- Package size: the tarball grows from about 3.1 MB to 5.4 MB and the package unpacks to 27.7 MB instead of 13.3 MB, but an install is smaller overall (32 MB in 4 packages instead of 78 MB in 42 on macOS arm64), because the dependency trees that were installed next to it are gone. `pack:pgard` and `smoke:pack` now also run a JavaScript, Vue and Python scan through the CLI, write JSON, SARIF, HTML and PDF output and run `precommit` from the installed package.

### Fixed

- `PG-SECRET-002` false positives (#445): a value made only of letters and `-`, `_` or `.` in which `replace`, `random`, `generate`, `insert`, `set-me` or `put-your` is a whole word is a placeholder (the words never apply to URL passwords or provider tokens, and `Random2024Xk` is kept). In `.env` templates (`.env.example`, `.env.sample`, `.env.template`, `.env.dist`, `*.env.example`) and in Markdown, MDX, reStructuredText and AsciiDoc files, a value of three or more lowercase dictionary words with an example word (`my-secret-key-value`) is a placeholder (in docs only when unquoted or in a code span or fenced block; a passphrase like `correct-horse-battery-staple` and `.txt` files are still scanned). A `.env` template reports a generic value only with entropy of at least 3.0 and two character classes, or 20+ characters of one class; provider-specific secrets are reported everywhere. In source code, outside string literals, an unquoted value that starts with `=` or runs from a dotted member access into `)`, `}`, `]`, `||` or `&&` is no longer reported, which removes the matches in minified bundles such as `password:e.target.value})`; passwords in comments, strings and config files are unchanged. The generic credential lines of a tracked (or new, staged) environment file are folded into its `PG-SECRET-001` finding, whose evidence now counts them (`N credential values inside, not shown`), so a baseline made earlier stops matching when the count changes (a suppression matches by rule and path and keeps hiding the file; the count is visible in the suppressed listing); provider-specific secrets in it are still reported. The old per-line `PG-SECRET-002` findings in environment files will show once as "no longer reported" in the next comparison, and the `PG-SECRET-001` finding for such a file reads as new because its evidence changed. Corpus: 16 new cases.
- The report save prompt has a default folder and understands `~` (#436). "Save a report?" now asks `Save to folder [~/Downloads]:` (`저장할 폴더 [~/Downloads]:`); Enter accepts it. The default is the first existing of Downloads, Documents and the home folder (Linux reads `XDG_DOWNLOAD_DIR` and `XDG_DOCUMENTS_DIR` from `~/.config/user-dirs.dirs`; Windows uses `%USERPROFILE%`). A leading `~` is expanded in the prompt and in `--output-dir` of `scan`, `report` and `sbom`. A folder that does not exist can be created from the prompt after a `y` (mode 0700, only under your home folder, and the inside-the-repository confirmation still applies); `--output-dir` still requires an existing folder.
- Code-only scan hardening, part 2 (#427): the working-tree secrets pass no longer applies the scanned folder's own `pgard.config.json` `exclude` (it could hide a file from the check; the note says how many patterns were ignored), its 20 s limit is hard (each file-system call is raced against the deadline, so a hung NFS or FUSE mount ends the pass as partial on time), and Cancel returns at once for the whole scan, in the CLI and in `pgard web`. Every folder is opened without following a symbolic link swapped in after its parent was listed (`lstat`, `O_DIRECTORY | O_NOFOLLOW`, `dev`/`ino`), `readTextFile` uses the same safe read as the secrets pass (no symlink, no FIFO), a folder on another device (a mount point) is named and not entered, and `.git` is skipped in any case on macOS and Windows. In `pgard web`, a second click on "scan code only" keeps the gate's reason (`no_approval`) instead of drifting to `not_checked`. `readScanResult` refuses a pre-1.7 result that is blocked yet has findings. `pgard precommit` outside a Git repository prints a note and exits 0, as the design says (a repository whose work tree Git redirects is still refused, exit 3). The "0 of 0 source files" coverage notes are reworded. Design doc EN and KO: section 2.3 says what is bounded, and the stale `--require-authorization`, "`--code-only` not needed", "today it runs the full gate" and precommit exit 3 claims are corrected; the gate-first-then-fallback alternative is marked superseded by the 2026-10-30 decision.
- Code-only folder guard (#427, from the #414 audit): `pgard scan --code-only` finds the repository root by walking up to the nearest `.git` entry instead of `git rev-parse`, so a repository's own `core.worktree` can no longer send the scan to another folder or another repository's `.git`; the authorized scan refuses a repository whose Git-reported root is not the folder that holds `.git`, with a clear message. The too-broad and home check now also reads alias spellings (macOS `/System/Volumes/Data/...`, Windows `\\?\` prefixes and `\\host\C$` shares), compares device and inode with `/`, home and each parent of home, and refuses anything under `/proc`, `/sys` and `/dev`; the CLI and the web folder chooser use the same helper. The CLI now refuses a folder owned by another user or writable by group or others, like the web chooser, and the walk up stops at home on both (a project inside a home dotfiles repository is its own folder; home itself is refused).

### Changed

- `pgard web` and `pgard dashboard` open the page in your default browser and make the link single-use (#419). The launcher writes the link into a private redirect file (a new 0700 temporary folder, a 0600 `.html` file created exclusively, deleted after the exchange, on expiry and on exit) and opens only that file with a separate, narrow opener, so the token is never on a command line other local users can read (macOS `/usr/bin/open`, Linux `xdg-open` only with `DISPLAY` or `WAYLAND_DISPLAY`, Windows `rundll32 url.dll,FileProtocolHandler`; never over SSH on any system, not in CI or without a terminal; no shell, a fixed argument vector; an opener that exits non-zero within 1.5 s counts as not opened). On Linux the file lives in `$XDG_RUNTIME_DIR` or `~/.cache/pgard/open` (Snap browsers cannot read `/tmp`). The HTML page accepts the cross-site top-level navigation the browser makes from that file (`Sec-Fetch-Site: cross-site`, `navigate`, `document`, no `Origin`); the API and every other file keep the strict checks. The terminal then shows the link with the token masked (`#token=••••`); the full link is printed only when the browser was not opened or could not be started, or with the new `--print-url`. New `--no-open` (`--no-browser` also keeps the page from opening). The URL token is now an invitation: the page trades it once at `POST /api/session/exchange` for a per-tab session secret (32 random bytes, held as a hash in memory, compared in constant time), keeps it in `sessionStorage` (a reload of that tab keeps working) and sends it as `x-pgard-session`; `x-pgard-token` is no longer accepted by any route. A second exchange gets `409 token_used` and the page says "This link was already used" with what to do (use the open tab, or run the command again; stop the server if you did not open it). An unused link expires after 10 minutes (`410 token_expired`); a session ends after 30 minutes without use. The terminal prints `Browser connected at HH:MM:SS.` on each exchange and `Someone tried to reuse the link at HH:MM:SS.` on a refused reuse. Host, Origin, cross-site and CSP checks are unchanged. Also: the simple screen's re-check button is "Check approval again" ("승인 다시 확인") after a gate too, and the footer names the command that discards the results (`pgard web` or `pgard dashboard`).
- `pgard web` opens the simple screen (#414, phase 4): choose a folder with the system's folder dialog (macOS `osascript`, Linux `zenity` or `kdialog`) or paste its path, press Scan, read the findings (severity, `file:line`, a short title). Nothing is asked in the terminal any more. Scan runs the authorization gate first, as `pgard scan` does, with the sign-in that already exists (it never starts a device flow by itself; new `signIn` field on `POST /api/scan`, and `gateReason` on the scan status). When the gate does not pass, the page says why in one line (no GitHub App approval for this folder, not signed in, no GitHub remote, not a Git repository, approval could not be checked) and offers "Scan code only (not authorized)" and "How to approve"; not signed in offers a quiet "Sign in and check approval" link instead. A code-only scan runs only on that click, takes the gate's reason for `scanBasis.reason`, carries the "not authorized" label (also on every page of an export) and is never stored. Coverage, standards, rules, export and the full dashboard (Git history, local web checks, trend) are under More. The `PGARD_WEB_PROTOTYPE` flag and its preview server are removed; the folder dialog, pasted path and code-only routes are on in picker mode behind the same token, Host, Origin and CSP checks. Git's own data folder (`.git`, anything in it, a bare repository) is refused with the rule `pgard scan code` uses (now shared in `@pgard/result-store`), and a folder inside a repository is checked and scanned as that repository. A stored sign-in GitHub no longer accepts (401) counts as not signed in. A new folder window opens only after the last one's process exited and a 1.5 s pause. The full dashboard's search picker searches only folders added with `pgard web scope add` (the default development folders are no longer searched without being saved). `pgard dashboard` is unchanged; `pgard web` is still not available on Windows.
- GitHub requests (#414): the 10 s limit now covers reading the response body too, and a sign-in poll that times out is tried again until the device code expires instead of ending the sign-in (when GitHub then no longer accepts the code, the message says to sign in again). A request no longer leaves an abort listener on the caller's signal when its body is not read. The gate reason rule is shared in `@pgard/scan-core` (`gateFailureReason`). `scanBasis.reason` `check_failed` is documented as "the gate could not reach a decision" (no sign-in, a network error or time-out, or an internal error), and a repository with no commit maps to `not_a_git_repository`.

### Removed

- `--require-authorization` (#414, phase 2b): authorization first is the default again, so the flag has no job; `pgard scan code --require-authorization` is now a usage error (exit 2).

### Added

- Authorization first, then a question (#414, phase 2b, D1 revised 2026-10-30): `pgard scan` and `pgard scan code` check authorization first again. When it fails (no approval, a check that could not run, no GitHub remote, not a Git repository) and stdin and stdout are a terminal, PGARD asks "Skip Git history and scan only the current code? (marked as not authorized) [y/N]" (KO: "Git 기록은 빼고 현재 코드만 검사할까요? (권한 미확인으로 표시됩니다) [y/N]"). N, the default, exits 3 with the approval guidance; y runs the code-only scan with the gate's reason (`no_approval`, `check_failed`, `no_github_remote` or `not_a_git_repository`). Without a terminal nothing is asked: exit 3 and "For a code-only scan, add --code-only." `--code-only` (`scan`, `scan code`) runs the code-only scan with no check and no network. `scan history`, `scan web`, `scan all` and `baseline set --from-current` never offer it. The menu entry "Scan the current files (code only)" stays the explicit code-only choice. A gate that did not pass always exits 3 (also when it could not finish, `check_failed`, in every scope); 5 is for unexpected internal errors only. Each GitHub API request now has a 10 s time limit, so a stalled network ends the gate (and reaches the question) instead of hanging. A folder that can never be code-only scanned (home, too broad, `.git`) is refused at once instead of offered. `--code-only --full` is a usage error.

- `pgard scan code` is a code-only scan (#414, phase 2, D1 and D4): it checks the current files of any folder (a Git repository from its top folder, or a folder without Git) without the authorization gate, sign-in or network, never stores the result, and says so first (`! Code-only scan: authorization not verified ...`). JSON and SARIF carry `scanBasis` (`not_checked` or `not_a_git_repository`). Exit 0 or 4, never 3. (Phase 2b below replaces this default with authorization first and a question.) `pgard scan`, `scan history`, `scan web` and `scan all` stay strict (D2) and add a hint to `pgard scan code` when blocked; `pgard project verify` adds the same pointer, and `pgard doctor` an `[info]` row. Folders too broad to be one project are refused (exit 2), compared by real path: the root, a top-level folder (`/Users`, `/Volumes`, ...), the home folder or a folder above it, also when that is a repository's top folder (a dotfiles repository at home); the web folder chooser uses the same rule. Both the given path and its real path are checked, so macOS `/etc`, `/tmp` and `/var` (real paths in `/private`) are refused, and folders directly in `/private` count as top-level. An empty `HOME` falls back to the account's home folder; with neither, the scan is refused. A `.git` folder or a bare repository is refused too. The menu entry is "Scan the current files (code only)" (EN/KO), and the panel view's title starts with the not-verified label.
- Result labelling for code-only scans (#414, phase 1, result schema 1.7): an optional top-level `scanBasis` (`mode: "authorized" | "code_only"`, `authorization: "verified" | "not_verified"`, an open-ended `reason` such as `no_approval`, `check_failed` (the gate failed internally), `no_github_remote` or `not_a_git_repository`). Every scan writes it, and the reader refuses a `verified` basis without an allowed decision and five passed checks, a `code_only` basis that is not blocked, code-scope-only and unverified, an unverified authorized basis on a scan that ran or has findings, and a 1.7 result without `scanBasis`; a code-only result keeps `authorization.decision: "blocked"` and never claims authorization. SARIF carries it in `properties.pgard.scanBasis`, adds a code-only warning notification and uses the category `pgard/code-only/`. HTML and PDF reports of a code-only result carry a "Not authorized: code-only scan" banner on every page and a cover block with the reason. The result store refuses a result whose authorization is not verified. The secrets pass over the files on disk reads UTF-8 and UTF-16 text like the pre-commit check, reports a `.env` file by name even when its content is not read, opens files without following links or blocking, is bounded (entries, files, bytes, depth, time) and is `partial` with the skipped files named whenever it leaves something out (only a known binary format is skipped by design); it says "Environment file in the project folder" and "Secret in a project file" instead of "committed to Git" or "tracked file", in English and Korean (same rule ids and fingerprints). The CLI does not run code-only scans yet; design in [docs/CODE_ONLY_SCAN_DESIGN.md](docs/CODE_ONLY_SCAN_DESIGN.md).
- `pgard precommit` (M10-1, #404): a fast check of the **staged** changes for secrets (`PG-SECRET-001`, `PG-SECRET-002`) and the file-local source rules (JavaScript, TypeScript, Vue, Go), for use as a Git pre-commit hook. It reads the Git index (never the working tree; for `git commit -a` and `git commit <path>` the temporary index in `GIT_INDEX_FILE`, accepted only when it is a regular file inside the repository's `.git`) with `ls-files -s`, `ls-tree -r` and `cat-file`, which were already on the allowlist, and reports only lines the commit adds or changes (renames keep their old text, deletions, binary files and symbolic links have nothing to scan). Authorization is the scan's own gate, all five checks every time and never relaxed; a hook never starts a sign-in. `pgard.config.json` gets an optional `"precommit": { "mode": "block" | "warn", "whenNotScanned": "block" | "warn" }`: `block` (default) exits 1 on a finding, `warn` exits 0. When nothing or not everything was scanned (not authorized, an error, a timeout of 15 s for authorization, a file over 1 MiB, more than 500 changed files, the 5 s analysis cap) it says `NOT scanned` and why, and `whenNotScanned` (default: the same as `mode`) decides; an invalid config means `block`. Suppressions and the baseline apply. `pgard precommit install` writes `<git dir>/hooks/pre-commit` only inside the repository's own hooks directory, refuses when `core.hooksPath` is set or the hooks directory is a symbolic link out of `.git`, creates the file exclusively (mode 0755), never overwrites a hook PGARD did not write without confirmation in a terminal (the old one is kept as `pre-commit.pgard-backup`) and refuses without a terminal; `uninstall` removes only a hook that is exactly PGARD's script; `snippet` prints the lines for the pre-commit framework and husky. The hardened Git runner gets one narrow option, `indexFile`, accepted for `ls-files` with an absolute path only. Block or warn is read from the `pgard.config.json` in the index (the version being committed; an untracked file is ignored with a note), and so do suppressions and `exclude` (a note says when the working-tree file differs or is untracked; only `testDirectories` is read from the working tree). What counts as new: a secret whose value HEAD's file lacks, or whose span (a private key covers many lines) has an added line, so a changed key body under an unchanged header is reported; source findings count as new when their line or statement changed. A NUL byte hides nothing: text with stray NULs is scanned, a new `.env` file is flagged by its name whatever its content, clearly binary files of any size (a known file signature, or binary content at both ends) are skipped by design and named on every run, UTF-16 without a byte order mark is decoded and scanned (and read as UTF-8 too, since a file can mix both), a text file that merely starts with a signature such as `%PDF-` is text, and only text files over 1 MiB (including a big file that merely starts with NULs) are "not scanned". The authorization cap (15 s) ends when the gate answers. A clean merge commit runs `pre-merge-commit`, not `pre-commit` (`pgard precommit snippet` shows the line); a merge is compared with HEAD, so the other branch's changes count as added. English and Korean (`--lang`, `PGARD_LANG`); new exit code 1 (`pgard precommit` findings in block mode; a crash of Node also exits 1, and both block).
- Trend view in the dashboard (M8-5, #411), in `pgard dashboard` and `pgard web`: a new **Trend** tab shows this repository's scans saved by the `pgard` command over time (the last 20 at most): stacked bars of active findings by severity, new / no longer reported / unchanged / not comparable between consecutive scans (the scan comparison), and ignored and baselined counts, with a data table that lists every value. A scan that did not cover everything (partial or not tested) is hatched and flagged, and the view says a lower count there can mean less was checked; "no longer reported" is never called fixed. The view says so, instead of drawing an empty chart, when saving scans is off (`--no-store`, `PGARD_NO_STORE=1`), when the project is not verified yet, when there is no store folder, when fewer than two scans are saved, or when stored files are unreadable, from a newer PGARD or dated in the future (left out so they cannot reverse the order), and that dashboard scans are never stored. New read-only `GET /api/trend` behind the same token, Host and Origin checks: the repository id comes only from this session's allowed authorization check (never from the request), only that repository's scans are read, the answer is counts and dates (no paths, finding text or scan ids) for at most 20 scans, and an answer read while the project changed is discarded (`409 project_changed`). A severity chip highlights that severity and sets the shared severity filter of the Findings view; category and the other filters do not apply to the trend, and the view says so. Keyboard (arrow keys between scans), screen-reader labels, English and Korean, light and dark, 390 px. Repeated reads of the same project are shared and cached for 5 seconds. History rules now live in `@pgard/result-store` (`trend-rules`) and are used by both the dashboard and the CLI trend panel: a scan dated after now is future-dated (the strict rule retention already uses; the dashboard leaves such files out and counts them, the CLI panel keeps anchoring on the current scan). **Behaviour change in the CLI trend panel:** it now counts active findings only, so findings ignored by `pgard.config.json` suppressions and findings in the saved baseline are no longer included in its severity counts and totals, matching the dashboard; the panel now labels its chart, table and column as "Active" (English and Korean) so a dropped total after adding a suppression or baseline is explained.
- `pgard web`, the project picker (M8-4, #398, design #356; also fixes #377): starts the dashboard without a project and lets you choose one in the browser by typing a folder name or dropping a folder (macOS and Linux; on Windows it exits with the usage error and points to `pgard dashboard`). The browser sends only a name; the server searches the folders you confirmed in the terminal (default: the common development folders that exist; `pgard web scope list | add | remove`, never changed from the browser), never follows symbolic links, stays on one file system and within fixed limits and time budget, shows each match's real path and `owner/name`, and selects nothing until you confirm and a fresh inspection matches. The walk, the Git calls and the checks run in a child process killed with its process group. Blocked folders (not a Git root, no commits, alternates, no github.com remote, linked worktree or submodule, another owner, writable by group or others along the whole chain, unsafe display text) show the reason and the fix in English and Korean. After the confirm, the existing five authorization checks run as before; every check, owner-approval re-check and scan first repeats the identity and ownership checks, and the gate blocks (new `expectedRepo` on `ScanRequest` and the authorization dependencies) unless the folder still holds the confirmed repository. New `POST /api/auth/cancel` (**Cancel check**), project epoch and `no_project`/`project_changed`/`auth_running` handling, a recent list and settings in `web/` (absolute paths, `0600`, deleted by `pgard history clear --all`, off with `--no-store`), and a page-wide guard so a file dropped outside the drop zone cannot navigate the page. `pgard dashboard` is unchanged and answers every `/api/picker/*` request with `409 fixed_project`. The authorization policy is not relaxed anywhere.
- Fix (#377): the dashboard's authorization check can be cancelled while Git is blocked (a hostile repository, for example a FIFO object). The check gets an AbortSignal that reaches every Git process; `POST /api/auth/cancel`, a client that disconnects during an owner-approval re-check and server shutdown abort it and kill the blocked Git process at once instead of waiting for the 60 s limit.
- Suggested-fix diffs (M9-5, #403, result schema 1.6): `PG-COOKIE-001` (Spring cookie flags set to an explicit off value, Express `res.cookie` on one line) and `PG-CRYPTO-003` (a whole-line `new Random()` with an explicit `java.util.Random` import) can carry `Finding.fix`, a one-line unified diff to review. PGARD never applies it, never writes to your files and has not checked that it compiles or keeps behaviour; a diff never holds a secret (both lines pass redaction unchanged or there is no diff), is bounded to 2,000 characters and deterministic. Shown by `pgard scan --fixes`, in JSON, in SARIF (`fixes`) and read-only with a copy button in the dashboard finding detail. Every other rule keeps guidance only.
- Dependencies in `pgard scan` (M9-3, #386): npm (`package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`) and Go (`go.mod`, `go.sum`) lockfile versions are matched, offline, against the OSV data downloaded with `pgard advisories update`. They are part of the default `code` scope (no new flag). New rule `PG-DEP-001` (OWASP A03:2025, CWE-1395; category `misconfiguration`, status `suspected`, confidence `medium`, `low` for development-only packages and a standalone `go.sum`): "affected version" means the pinned version is in the advisory's affected range, never that the code is reachable or exploitable. Versions are compared with semver (npm) and Go module version rules; a version or range that cannot be compared is reported as not tested. Withdrawn advisories are skipped, records of one issue under several ids (GHSA, GO, CVE) are one finding. Severity is the CVSS v3 base score computed from the advisory's vector, else the database label, else unknown (`medium`). Coverage: one `deps:npm` / `deps:Go` area per ecosystem with a lockfile; no downloaded data is `not_tested` with the `pgard advisories update` hint, stale data (7 or more days, the `pgard doctor` rule) or a lockfile that was not understood is `partial`, and lockfiles of other ecosystems appear in the rule-less `deps:unsupported`. JSON schema 1.5 adds the optional `Finding.dependency`; fingerprints do not depend on the data version. Dependency areas are recomputed on every scan and never block incremental reuse. Behaviour change: a repository with an npm or Go lockfile and no downloaded OSV data now scans as `partial` and exits with code 4 (the `deps:*` area is `not_tested`); run `pgard advisories update` to fix it. Go standard library and toolchain advisories are not checked.
- `pgard sbom` (M9-4, #387): writes a CycloneDX 1.6 JSON SBOM of the packages in the repository's lockfiles (npm, pnpm, yarn, go.mod/go.sum): name, version, package URL (`pkg:npm/%40scope/name@1.0.0`, `pkg:golang/github.com/Azure/x@v1.0.0`; Maven, PyPI and Composer purl rules are ready for the later parsers), a `bom-ref` per component, the lockfiles each came from, and the direct dependencies as the repository's `dependencies` edges (PGARD's parsers do not read the links between other packages or dev/prod scope, so the graph is marked `pgard:dependency-graph = direct-only` and no `scope` is written; a dependency resolved from git, a tarball URL or `file:` is not told apart from a registry package yet). Lockfiles that could not be read, were too large or are not supported yet (and `package.json` projects with no lockfile) are listed as `pgard:unparsed-lockfile` properties, and the SBOM is marked incomplete (`pgard:complete`, a CycloneDX `incomplete` composition). Output is sorted and deterministic apart from the serial number and timestamp. Local only: no network for the SBOM itself and no package manager or build tool; names and paths go through the findings redaction rules. Reading the repository needs the same authorization as `pgard report` (the repository checks run first; exit 3 if they fail). `--output-dir DIR` or a new private temporary directory (0700), a fixed file name `pgard-sbom-<time>-<commit>.cdx.json`, created with `wx` and mode 0600, never overwritten, and a confirmation for a directory inside the repository. English and Korean. Tests validate the output against the official CycloneDX 1.6 JSON schema (vendored under `packages/dependencies/test-fixtures/cyclonedx/` with its Apache-2.0 license; `ajv` is a new dev dependency).
- Interactive `pgard scan` offers detected local dev servers as web scan targets (UX-4, #384, #306): in a terminal, with no scope word, `--port` or `--format json|sarif`, and outside CI, it looks for HTTP services on 127.0.0.1 with the existing port discovery (about 1 second at most; a failure or timeout is ignored) once authorization passes (one `GET /` to each listening port to read its title; skipped when not yet signed in), and asks `Also scan http://127.0.0.1:3000 (title)? ### Changed

- **`pgard precommit` no longer needs a sign-in** (#414, phase 3, D3). By default the hook is a code-only check of the staged changes: no authorization gate, no GitHub sign-in, no network and no keychain, so it works for every contributor and in CI without `pgard login`. One quiet line says `code-only, authorization not verified`; the staged-only scan, suppressions, `mode` and `whenNotScanned` are unchanged. The baseline is not applied in this mode. The 15 s authorization cap (`PGARD_PRECOMMIT_TIMEOUT_MS`) only applies with the new `"precommit": { "requireAuthorization": true }` in the staged `pgard.config.json`, which restores the full gate exactly as before (exit 3 when not authorized). `install` and `snippet` say so.

- `pgard precommit`: a staged file that only looks binary by its content (no known file signature; for example a log full of colour codes with a NUL) is no longer passed over silently as "binary". It is still not read, and every run now names it in a warning ("look binary but have no file format PGARD knows ... This does not block the commit"). It never blocks, whatever `whenNotScanned` says, because many real binary formats have no signature PGARD knows.
- Binary detection knows more file signatures, so these formats are skipped by design rather than called "looks binary": Apple icons (`icns`), `.DS_Store`, binary property lists (and `.loctable`), asset catalogues (`.car`), nib archives, TrueType collections (`.ttc`), TIFF, Photoshop (`.psd`), glTF binary (`.glb`), MP3 (ID3 tag or MPEG frame), FLAC, AIFF/AIFF-C, NumPy (`.npy`), HDF5, RAR, Java keystores (JKS), compiled Python (`.pyc`) and ICC colour profiles. Short signatures that could start a text file are only trusted with a consistent header, so text with a NUL is still read: compiled Python needs its 16-byte header with a flags word of 0 to 3, an MP3 frame a second frame header where the first ends, icns, glTF and ICC a length field equal to the file size (glTF also version 2), `ttcf` version 1.0 or 2.0, `8BPS` version 1 or 2, and `fLaC` a STREAMINFO block. A blob over the size limit is checked against its real size.
- `pgard scan` in a terminal now prints the findings first and the summary last, so the screen ends on the status line, the charts, the coverage count (partial and not-tested areas named) and a "Next" line. Findings are compact by default: critical and high first, at most 10 groups of one or two lines, then `+N more (medium 17, low 2)` pointing to `--all-findings`; test, fixture and vendored code get a title line with counts by severity and keep their critical and high groups (and every secret) listed; the rest is counted. Evidence, fix and standards appear with `--all-findings` (the previous full detail), in the panel view, the dashboard and reports. Long lines are wrapped to the terminal width with a hanging indent, by character and keeping colours per piece; only PGARD's own standards links may run past the width, and other URLs are cut at twice the width. Output that is not a terminal (pipes, files, CI), `--format json` and `--format sarif` are unchanged. Partial and not-tested coverage and the "not a safe result" warnings are shown in the compact form too.
- The panel view now opens by itself for `pgard scan` in a terminal, as the menu already did. `PGARD_PANELS=off` (also `0`, `false`, `no`) turns it off, `--panels` still forces it, and it never opens without a terminal or with `--format json` or `sarif`. The text result is printed before it opens and stays on the main screen. It does not open by itself when `CI` is set (other than empty, `0`, `false`), under `GITHUB_ACTIONS`, `BUILDKITE`, `TF_BUILD` or `JENKINS_URL`, with `TERM=dumb`, or for `pgard baseline set --from-current`; `--panels` or `PGARD_PANELS=on` still open it. Set `PGARD_PANELS=off` when you run `pgard scan` under `script`, `expect`, VS Code tasks or `docker run -it`, where a pseudo-terminal exists but nobody presses a key. Ctrl+D and a closed terminal now leave the view like Esc.
- The result and report text is localized in Korean and English (CLI, reports, dashboard).
- Rule rationale and remediation texts and mappings were rewritten against OWASP 2025 and concrete attack and fix examples.
- Requires Node.js 22.23.4, 24.22.1 or 26.12.1, or a newer patch on the same line; `pgard doctor` fails older releases.
- Analysis is code-based: a scan does not check dependencies against an advisory database. The only OSV use is the user-run `pgard advisories update` download.

### Fixed

- The lockfile collector is bounded against hostile repositories (M9-3 prerequisite, L5, #386): global caps on lockfile bytes (256 MiB), `package.json` bytes (32 MiB, a separate pool), kept packages (500,000) and a 30 s time budget for the walk and reads; an abort signal (`pgard sbom` passes Ctrl+C and a 60 s budget and shows the limits it hit); hard links read once per kind (dev/ino, recorded only after a successful read); reads that never follow symlinks or block on special files; and files that are small in bytes but hostile in shape (more than 500,000 lines, JSON nested more than 512 levels or with more than 1.5 million elements) are not parsed. Anything not read is reported as `not-read`, `partial`, `too-large` or `duplicate` with a note and makes the SBOM incomplete, never clean.
- Without a terminal (stdin or stderr not a TTY) and without a usable saved sign-in, `scan` (all forms and formats), `baseline` and `project verify` no longer start the GitHub device flow and wait up to 15 minutes: they exit 3 at once with a blocked result ("Not signed in ... Run `pgard login` in a terminal first"), valid JSON or SARIF for those formats. `pgard login` without a terminal is a usage error (exit 2). Interactive behaviour is unchanged (#296).
- The keychain sentence "the OS keychain could not be used ..." is now translated in Korean output (#300, part).
- Many false negatives and false positives in secret, auth, cookie and CSRF detection and in Git history checks.
- Port-discovery and dashboard port-gate races, keychain sign-in races, and layout at narrow widths.
- Install guidance for private repositories outside the App installation and for a 404 when the App already covers all repositories.

### Security

- Hostile-repository hardening of the authorization gate (#369): `objects/info/alternates`, `http-alternates`, `info/grafts` and `shallow` are read as small regular files only (no symlinks, FIFOs, devices or oversized files; any problem blocks with a reason instead of passing), the remote identity is read from the raw `remote.<name>.url` and `pushurl` config and blocked when a `url.*.insteadOf` or `pushInsteadOf` rewrite exists, and Git runs with `core.alternateRefsCommand=`, `credential.helper=` and `core.sshCommand=` blanked and `GIT_NO_LAZY_FETCH=1`. Known limit, now documented: the gate confirms the named GitHub repository and that a local commit is known there; it does not prove the working tree matches GitHub.
- Hostile repositories can no longer hold a scan or slip text past it (#368). The Go assignment and name-list patterns and the Java/Kotlin import patterns are linear (a 12 KB Go comment took 68 seconds, 256 KiB of newlines a minute; results are unchanged). JavaScript, TypeScript, Vue and Go files are analyzed in a worker thread with a hard per-file limit of 20 seconds that also honours the time budget and Ctrl+C; a stopped file, a file that reaches the stack limit (deep nesting, previously counted as a syntax error) or the memory limit, and a file the worker failed on (no new worker after 3 failures in a row) are reported as not analyzed and make their area `partial`. The directory walk counts against the time budget and stops after 300,000 entries (`source:walk`, `partial`, and every other `source:*` area partial too). Finding paths mark C0/C1 control, bidi and zero-width characters as visible `\uXXXX` text, `--format json` output and the local result store write U+007F to U+009F, U+061C, U+200B to U+200F, U+2028 to U+202E and U+2066 to U+2069 as `\uXXXX` escapes, and the incremental cache no longer keeps files whose path redaction would change.
- `pgard advisories update` refuses data whose newest record is older than the installed data, or that holds fewer than half as many records, and keeps the installed data (`--force` accepts it); advisory freshness now also considers the age of the newest record, shown in `pgard doctor` (#360). The dashboard server sets header (10 s), request (30 s), keep-alive (5 s) and connection (64) limits, clears its confirmed web target on sign-out and on any new authorization state, and the GitHub API client no longer follows redirects automatically (a renamed repository's redirect to `/repositories/{id}` on `api.github.com` is repeated once by hand).

- Dashboard and web checks are loopback-only; reports and results are redacted, and the dashboard gates port discovery on the full authorization outcome.
- Packaged grammars are checksum-pinned and verified; the package has no install scripts and only exact-pinned direct dependencies.
