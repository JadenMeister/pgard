# 보안 설계: CI(GitHub Actions)에서의 권한 확인

> **참고:** 이 문서는 [`CI_AUTHORIZATION_DESIGN.md`](CI_AUTHORIZATION_DESIGN.md)(영문)의 한국어 번역입니다. 기준 문서는 영문판이며, 내용이 다르면 영문판이 맞습니다. 프로젝트 [README](../README.ko.md)([English](../README.md))와 [문서 목록](README.ko.md)도 참고하세요.

상태: 검토용 설계([#405](https://github.com/JadenMeister/pgard/issues/405), M10-2). 이 문서의 내용은 아직 아무것도 구현되지 않았습니다. 소유자가 승인한 뒤에만 M10-3에서 구현합니다.

"현재"에 대한 설명은 작성 시점의 코드(`packages/policy/src/authorize-project.ts`, `packages/policy/src/checks.ts`, `packages/policy/src/types.ts`, `packages/github-auth`, `packages/git-history`)를 기준으로 합니다. 이 설계가 아직 코드에 없는 것에 기대는 곳에는 **M10-3 요구사항**이라고 표시했습니다. GitHub에 대한 설명은 GitHub 문서에서 가져왔고, 본문에 링크를 달고 [참고 자료](#12-참고-자료)에 모았습니다. 문서가 말하지 않는 부분은 그렇다고 적고, 그 동작에 기대지 않습니다.

## 1. 목표와 비목표

### 목표

1. GitHub Actions 작업(job)에서의 검사도 로컬 검사와 **같은 다섯 가지 확인**(저장소, GitHub 신원, 소유자 승인, 현재 접근, 기여)을 같은 확인 id, 순서, 상태로 증명합니다. 브라우저 로그인은 없습니다.
2. 각 확인은 로컬 증거와 **같거나 더 강한** 증거로 증명합니다. CI가 그런 증거를 만들 수 없으면 그 확인은 이유와 함께 `failed` 또는 `unverifiable`이 되고, 검사는 막힙니다(종료 코드 3).
3. **확인을 건너뛰거나, 완화하거나, 캐시하는 CI 모드는 없습니다.** CI가 바꾸는 것은 `github_identity`의 증거가 어디서 오는지, 그리고 이후 확인을 어느 계정에 대해 평가하는지뿐입니다. `authorizeProject`는 여전히 유일한 게이트이고 `isAuthorizationAllowed`는 바뀌지 않습니다.
4. GitHub Actions 밖에서 "CI인 척" 실행해도 아무것도 허용되지 않습니다. `GITHUB_ACTIONS`, `GITHUB_REPOSITORY`, `GITHUB_ACTOR` 같은 환경 변수는 절대 증거가 아닙니다.
5. 코드, 히스토리, 결과는 러너에 남고, 발견 사항의 세부 내용은 작업 로그에 쓰지 않습니다(T15). 네트워크 통신은 GitHub(`api.github.com`과 Actions 토큰 서비스 `token.actions.githubusercontent.com`)로만 제한됩니다.

### 비목표

- M10-2에서는 구현하지 않고, 로컬 디바이스 플로 경로도 바꾸지 않습니다.
- CI에서 풀 리퀘스트 코드를 검사하지 않습니다([U2](#8-증명할-수-없어-막는-것) 참고). CI는 기본 브랜치로 한정합니다.
- 다른 CI 시스템과 GitHub Enterprise Server는 지원하지 않습니다([9절](#9-범위-밖) 참고).
- 수정된 `pgard` 바이너리는 막지 않습니다. PGARD는 곧 오픈소스가 되며, 누구나 게이트를 뺀 사본을 빌드할 수 있습니다. 이는 지금 노트북에서도 마찬가지입니다. 게이트는 진짜 `pgard`의 사용자와, 그것이 향하는 저장소의 주인을 허가되지 않은 검사로부터 보호합니다. 이 설계는 그 성질을 CI에서도 유지할 뿐, 그 이상을 하려 하지 않습니다.

## 2. 현재의 확인과 로컬 증거

`authorizeProject`는 모든 검사와 `project verify`에서 실행되고, 결과는 절대 캐시되지 않습니다. 다섯 확인이 모두 통과해야만 결정이 `allowed`입니다.

CI에서 중요한 성질 두 가지:

- 확인 3~5의 **주체**는 로그인한 사람입니다. 이 확인들을 의미 있게 만드는 모든 것(소유자, 조직 소유자, 협업자, 기여자)은 그 사람의 GitHub 계정 id에 대한 진술입니다.
- 확인 3~5에는 GitHub API가 필요합니다. 현재 게이트에서 오프라인으로 증명할 수 있는 것은 확인 1뿐입니다.

## 3. CI에서 바뀌는 것

CI 작업에는 터미널 앞의 사람이 없으므로 디바이스 플로가 없습니다. "로그인한 사람"의 자리를 무언가가 대신해야 하고, 확인 3~5는 같은 규칙으로 그 주체에 대해 평가되어야 합니다.

이 설계는 입력을 두 종류로 나눕니다.

- **신원(identity)**: 주체가 누구인가. GitHub가 서명해야 하고, 이 작업과 이 프로세스에 묶여 있어서 복사, 재사용(replay), GitHub 밖에서의 생성이 불가능해야 합니다.
- **사실(facts)**: 저장소, 설치, 멤버십, 풀 리퀘스트, 커밋에 대해 GitHub가 말하는 것. TLS로 `api.github.com`에서 읽은 사실은, 그 토큰이 애초에 읽을 수 있었다면, 어느 토큰으로 읽었든 참입니다. 따라서 읽기 전용 토큰의 출처는 사실을 _읽을 수 있는지_에만 영향을 주고, 사실이 _무엇을 말하는지_에는 영향을 주지 않습니다.

CI에서 신원을 주는 것은 GitHub가 서명한 OIDC 토큰뿐입니다(4절). 사실만 읽는 토큰은 어디서 왔든 상관없지만, 절대 신원이 아닙니다.

**동의는 저장소 단위입니다.** 로컬에서는 `pgard`를 실행하는 사람이 검사를 선택했습니다. CI에서는 저장소 관리자가 환경(environment), 그 시크릿, 호출자 워크플로를 만들어 검사를 선택합니다(7절). `push`의 actor는 그 푸시에 대해 검사를 요청하지 않았습니다. 그 사람은, 터미널 앞의 사람과 똑같이, 확인 3~5가 지위(소유자, 협업자, 기여자)를 평가하는 주체입니다. CI 안내서에 이를 적습니다(**M10-3 요구사항**).

## 4. CI 신원 후보

각 후보마다 각 확인에 어떻게 대응하는지, 어떻게 위조될 수 있는지, 오프라인으로 검증할 수 있는지를 적습니다.

### A. GitHub Actions OIDC 토큰(`id-token: write`)

`permissions: id-token: write`가 있는 작업의 단계(step)는 러너 변수 `ACTIONS_ID_TOKEN_REQUEST_URL`, `ACTIONS_ID_TOKEN_REQUEST_TOKEN`과 원하는 `audience` 쿼리 매개변수로 GitHub OIDC 제공자에게 JWT를 요청할 수 있습니다([OIDC 레퍼런스](https://docs.github.com/en/actions/reference/security/oidc), [워크플로 문법: `permissions`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)). 토큰은 발급자 `https://token.actions.githubusercontent.com`이 RS256으로 서명하며, 키는 [OpenID 설정](https://token.actions.githubusercontent.com/.well-known/openid-configuration)의 `jwks_uri`에 공개됩니다([JWKS](https://token.actions.githubusercontent.com/.well-known/jwks)). 설정에 나열된 클레임: `sub`, `aud`, `exp`, `iat`, `iss`, `jti`, `nbf`, `ref`, `sha`, `repository`, `repository_id`, `repository_owner`, `repository_owner_id`, `enterprise`, `enterprise_id`, `run_id`, `run_number`, `run_attempt`, `actor`, `actor_id`, `workflow`, `workflow_ref`, `workflow_sha`, `head_ref`, `base_ref`, `event_name`, `ref_type`, `ref_protected`, `environment`, `environment_node_id`, `job_workflow_ref`, `job_workflow_sha`, `repository_visibility`, `runner_environment`, `issuer_scope`, `check_run_id`. 이 중 일부(`sha`, `ref_protected`, `enterprise`)는 설정에는 나열되지만 OIDC 레퍼런스에는 설명이 없습니다.

관련된 문서상의 의미:

- `actor` / `actor_id`: 실행을 시작한 계정. 재실행의 경우 GitHub [컨텍스트 레퍼런스](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts)는 `github.actor`가 _최초_ 실행의 사용자로 남고, 재실행은 그 사용자의 권한을 쓰며, 재실행을 시작한 사람은 `github.triggering_actor`라고 말합니다. OIDC 클레임 목록에는 `triggering_actor`가 없습니다.
- `job_workflow_ref` / `job_workflow_sha`: 작업이 재사용 워크플로를 쓸 때 있으며, 호출된 워크플로 파일과 그 커밋을 가리킵니다. 다른 클레임(`repository`, `ref`, `workflow` 등)은 **호출자**를 설명합니다([재사용 워크플로와 OIDC](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-with-reusable-workflows)).
- `environment`: 작업이 쓰는 환경.
- `runner_environment`: `github-hosted` 또는 `self-hosted`.
- `sub`: 형식이 이벤트, 환경, 사용자 지정 템플릿에 따라 달라지고, 2026년 7월 15일 이후에 만들어진(또는 이름이 바뀌거나 이전된) 저장소는 소유자 id와 저장소 id가 들어간 불변 형식을 씁니다([OIDC 레퍼런스](https://docs.github.com/en/actions/reference/security/oidc)). 그래서 이 설계는 **`sub`를 절대 해석하지 않고** 개별 클레임을 확인합니다.
- 수명: 토큰은 "단일 작업 동안만 유효"합니다([OIDC 개념](https://docs.github.com/en/actions/concepts/security/openid-connect)). GitHub는 고정 수명을 문서화하지 않으므로, 설계는 `exp`를 읽고 자체 신선도 한도를 더합니다.

### B. `GITHUB_TOKEN`

"`GITHUB_TOKEN` 시크릿은 GitHub App 설치 액세스 토큰"이며, 작업마다 만들어지고, 워크플로가 들어 있는 저장소로 제한되며, 작업이 끝나거나 GitHub 호스티드 러너에서 최대 6시간(셀프 호스티드는 24시간) 후에 만료됩니다([`GITHUB_TOKEN`](https://docs.github.com/en/actions/concepts/security/github_token)). 권한은 `permissions:`로 정합니다. 포크에서 온 풀 리퀘스트 이벤트(`pull_request_target` 제외)에서는 저장소가 쓰기 토큰 보내기를 켜지 않는 한 쓰기 권한이 읽기 전용으로 바뀌고, `pull_request_target`은 공개 포크에서 와도 읽기/쓰기를 받습니다([워크플로 문법: `permissions`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)).

### C. `pgard`에 건네는 GitHub App 설치 토큰

설치 토큰은 App의 JWT로 `POST /app/installations/{installation_id}/access_tokens`를 호출해 만들고, "1시간 후 만료"되며, App의 행위로 기록되고, 설치가 이미 가진 저장소와 권한 안에서 좁힐 수 있습니다([설치로 인증하기](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation)). `app_id`, `account`, `repository_selection`을 돌려주는 `GET /repos/{owner}/{repo}/installation`은 App의 JWT가 필요하고, 토큰 생성 응답에는 `app_id`나 `account`가 없습니다([Apps REST API](https://docs.github.com/en/rest/apps/apps)).

두 가지 형태:

- **C1. 미리 만들어진 설치 토큰**(예: 작업 앞부분에서 액션이 발급한 것). `pgard`는 어느 App이 발급했는지 알 수 없습니다. 설치 토큰으로 호출할 수 있는 어떤 API도 App id를 돌려주지 않습니다. 소유자 계정(또는 공격자가 통제하는 저장소)에 설치된 아무 App의 토큰이든 똑같아 보입니다. 소유자 승인이 설정된 App에 대한 것임을 보일 수 없습니다. **승인 증거로 거부합니다.**
- **C2. `pgard`에 App 자격 증명(App id와 개인 키)을 줌.** `pgard`가 직접 App JWT를 서명하고, `GET /app`(App의 `owner`)과 `GET /repos/{owner}/{repo}/installation`(`app_id`, 설치 계정)을 읽은 뒤, 이 저장소로 제한한 읽기 전용의 짧은 설치 토큰을 발급해 멤버십과 협업자 권한을 읽는 데만 씁니다. 이는 저장소 소유자가 소유한 **그 App**이 소유자 계정에 설치되어 있음을 증명합니다.

| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- |

### D. 저장된 사용자-서버 토큰(디바이스 플로를 한 번 하고 토큰을 CI 시크릿에 저장)

다섯 확인 모두 지금과 똑같이 실행되겠지만:

- 신원은 이번 실행을 일으킨 사람이 아니라 한때 로그인한 계정입니다. 그 시크릿을 읽는 워크플로를 실행할 수 있는 사람은 누구나 _소유자로서_ 검사하게 되므로, 소유자가 본 적 없는 코드에 소유자 승인과 소유자 예외가 주어집니다.
- 토큰의 수명이 깁니다(App 설정에 따라 8시간 액세스 토큰과 6개월 리프레시 토큰, 또는 만료 없음). 갱신하면 새 시크릿을 다시 써야 합니다.
- 토큰을 환경 변수에 절대 넣지 않는다는 현재 규칙과 충돌합니다.
- 오프라인으로 검증할 수 없고 작업에 묶을 수 없습니다.

**거부.** 개인 액세스 토큰은 같거나 더 나쁘므로(PGARD App에 묶이지도 않음) 같은 이유로 **거부**합니다.

### E. 서명되지 않은 작업 메타데이터(`GITHUB_ACTIONS`, `GITHUB_REPOSITORY`, `GITHUB_ACTOR`, `GITHUB_SHA`, 이벤트 페이로드 파일)

누구나 어떤 기계에서든 설정할 수 있습니다. 확인 결과를 바꾸는 힌트로조차 **절대 증거가 아닙니다**.

## 5. 오프라인 검증과 온라인 검증, 그리고 JWKS

**오프라인으로 검증 가능**(서명 키를 알고 나면 네트워크 없이): JWT 구조, `alg` = `RS256`, `kid`가 가리키는 키로 헤더와 페이로드에 대한 RS256 서명, `iss`, `aud`, `exp`, `nbf`, `iat`, 그리고 로컬 데이터만 필요한 모든 클레임 비교: 검증된 원격과 `repository`, 로컬 `HEAD`와 `sha`, `pgard`에 내장된 값과 `job_workflow_sha` 및 `job_workflow_ref` 접두사, `environment`, `runner_environment`, `event_name`, `ref_type`, `run_attempt`, `actor_id == repository_owner_id`.

**GitHub API가 필요**: 서명 키 자체(JWKS 가져오기), `repository_id`, `repository_owner_id`, 공개 여부, 기본 브랜치가 GitHub가 지금 보고하는 값과 같은지, actor가 `User` 계정인지(`GET /user/{actor_id}`, 로그인 이름은 바뀔 수 있으므로 id로 조회), App 소유자와 설치(C2), 조직 멤버십, 협업자 권한, 모든 기여 사실. 확인 3~5에는 항상 API가 필요하므로 **오프라인 CI 권한 확인은 절대 `allowed`가 될 수 없습니다**. 오프라인 모드는 없습니다.

**JWKS 가져오기와 고정**(**M10-3 요구사항**):

- 발급자 `https://token.actions.githubusercontent.com`과 JWKS URL `https://token.actions.githubusercontent.com/.well-known/jwks`는 `pgard` 안의 상수입니다. 실행 중에 OpenID 설정 문서를 가져오지 **않으므로**, 바뀌거나 위조된 discovery 문서가 키의 출처를 옮길 수 없습니다. GitHub가 `jwks_uri`를 바꾸면 `pgard` 릴리스가 필요합니다.
- JWKS는 권한 확인마다 한 번, HTTPS로, 리디렉션을 따르지 않고, 짧은 타임아웃과 크기 제한을 두고, GitHub 클라이언트와 같은 강화된 fetch로 가져옵니다. `kty: RSA`, `alg: RS256`(또는 `alg` 없음), `use: sig`(또는 `use` 없음)인 키만 받으며, 모듈러스는 최소 2048비트입니다.
- JWKS는 그 한 번의 권한 확인 동안 메모리에만 두고 디스크에 쓰지 않습니다. 권한 확인 결과는 아니지만, 캐시하면 최신으로 유지해야 할 두 번째 신뢰 저장소가 생기고, 어차피 실행은 온라인입니다.
- 키 스냅샷을 신뢰 기준으로 배포하지 않습니다. 스냅샷은 GitHub가 교체해 없앤 키를 계속 받아들이게 됩니다(테스트 전용으로 두는 것은 괜찮습니다).
- 가져온 뒤에도 `kid`를 모르거나, 가져오기에 실패하거나, JWKS가 잘못된 형식이면 `github_identity`는 이유와 함께 `unverifiable`입니다. 다른 키나 디바이스 플로로 넘어가지 않습니다.

## 6. 위협 모델

자산: 권한 결정, App 개인 키(C2), 작업 실행 중의 OIDC 토큰과 설치 토큰, 러너 위의 검사 대상 코드와 발견 사항.

**신뢰의 뿌리.** GitHub의 토큰 서비스, Actions 제어 평면(클레임, 환경 규칙, 어떤 워크플로 파일이 실행될지를 정함), API, 그리고 GitHub 호스티드 러너 이미지를 신뢰합니다. 더 큰 러너(larger runner)는 조직이 통제하는 사용자 지정 이미지를 쓰면서도 `runner_environment: github-hosted`를 보고할 수 있습니다. 그런 이미지는 조직 자신의 신뢰 안에 있으며, 이 설계는 이를 구별할 수 없습니다(U11).

신뢰 경계: 고정된 재사용 워크플로와 그것이 빌드하는 `pgard`(커밋으로 고정되어 신뢰), 호출자 워크플로와 검사 대상 저장소의 나머지 모든 것(신뢰하지 않음: 브랜치에 쓰기 권한이 있으면 누구나 바꿀 수 있으며 `.npmrc`, 로컬 액션, 캐시, 변수, 이벤트 페이로드도 포함), 모든 환경 변수(신뢰하지 않음), 러너 기계(GitHub 호스티드일 때만 신뢰).

## 7. 권장 설계

### 7.1 개요

1. **신원**은 `pgard`가 작업 안에서 새 nonce audience로 직접 요청하고 GitHub JWKS로 검증한 Actions OIDC 토큰에서만 옵니다(후보 A).
2. **작업이 고정**됩니다: 실행 중인 `pgard`를 빌드한 바로 그 커밋의 PGARD 자체 재사용 워크플로를, 그 워크플로의 고정 환경에서, GitHub 호스티드 러너에서, 기본 브랜치에 대한 `push` 또는 `workflow_dispatch`로, 첫 시도에 실행한 작업의 토큰만 받습니다. 검사 대상 저장소가 통제하는 어떤 것도 그 작업에서 코드를 실행할 수 없습니다(7.2).
3. 확인 3~5의 **주체**는 OIDC actor(`actor_id`, `User`)입니다. 기존 확인 함수는 로그인한 사용자 대신 그 주체로 그대로 실행됩니다.
4. **소유자 승인**에는 현재와 같은 강도의 App 증거가 필요합니다: 후보 C2, 저장소 소유자가 소유한 App이며 그 id와 키는 보호된 환경에만 있습니다. 없으면 소유자 승인은 `unverifiable`이고 검사는 막힙니다. 기본 제공 PGARD App은 이 경우입니다(Q1).
5. 저장소와 기여에 대한 **사실**은 `GITHUB_TOKEN`(후보 B, 최소 권한)으로 읽습니다. App 키는 App 소유자, 설치, 조직 멤버십, 협업자 권한에만 씁니다.
6. CI 증거 제공자는 명시적으로 선택합니다(제안: `--identity github-actions`, Q7). 없으면 아무것도 바뀌지 않습니다: 터미널과 저장된 로그인이 없으면 여전히 "Not signed in"으로 막힙니다. 있으면 키체인이나 디바이스 플로로 넘어가지 않습니다.

### 7.2 고정 작업의 불변 조건

검사 대상 저장소가 통제하는 어떤 것도 `pgard`를 실행하는 작업의 코드 실행에 영향을 주어서는 안 됩니다. 그렇지 않으면 그 코드가 `pgard`의 audience로 토큰을 발급받거나(T6, T7) `/proc`에서 키를 읽을 수 있습니다(T16). 각 불변 조건에는 M10-3의 테스트가 있습니다(10절).

1. **I1. 호출자 입력 없음.** `on.workflow_call.inputs`는 비어 있습니다. 호출자가 주는 값은 이름으로 넘기는 시크릿 `PGARD_APP_PRIVATE_KEY`뿐이며, App id는 고정 환경의 환경 변수입니다.
2. **I2. `pgard`는 검사 대상 저장소를 체크아웃하기 전에, 작업 공간(workspace) 밖에서 빌드합니다.** 소스는 `job.workflow_repository`에서 `job.workflow_sha`로([컨텍스트](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts)) `RUNNER_TEMP`에 가져와, 자기 lockfile로 그곳에서 빌드합니다.
3. **I3. `.npmrc`나 다른 저장소 설정이 빌드에 영향을 주지 않습니다.** 빌드는 빈 파일을 가리키는 `NPM_CONFIG_USERCONFIG`와 `NPM_CONFIG_GLOBALCONFIG`, 명시적으로 지정한 공개 레지스트리로 실행하며, 의존성에 꼭 필요하다고 밝혀지지 않는 한 lifecycle 스크립트를 끕니다. 빌드할 때 검사 대상 저장소는 아직 없습니다(I2).
4. **I4. 캐시 없음.** `actions/cache`도, `actions/setup-node`의 `cache:`도, 저장소에서 복원하는 도구 캐시도 없습니다. 그래서 호출자의 `cache-mode`가 복원할 것이 없습니다. M10-3에서 확인합니다.
5. **I5. 신뢰할 수 있는 게시자의 JavaScript 액션만, 전체 커밋 SHA로 고정.** 전이적 액션이 고정되지 않은 composite 액션은 쓰지 않습니다. 바뀔 수 있는 태그를 받는 Docker 액션도 쓰지 않습니다.
6. **I6. 로컬 액션 없음**(`uses: ./...`). 어떤 단계도 검사 대상 저장소의 파일을 실행하지 않습니다.
7. **I7. 이벤트 데이터, `vars`, 그 밖에 저장소가 통제하는 값은 `run:` 스크립트, `uses:`, 액션의 `with:`에 닿는 표현식에 쓰지 않습니다.** 저장소가 통제하는 값(환경의 `PGARD_APP_ID`와 시크릿)은 `env:`를 통해 `pgard` 단계에만 닿고, `pgard`가 검증합니다(숫자, PEM).
8. **I8. 검사 대상 저장소는 데이터로만 체크아웃합니다**(SHA로 고정한 `actions/checkout`, `persist-credentials: false`, `fetch-depth: 30`). 그것을 읽는 프로세스는 `pgard`뿐입니다. 현재와 같이 검사 대상 저장소의 패키지 관리자, 빌드, 테스트는 실행하지 않습니다.

### 7.3 워크플로 모양, 환경, 키 처리

검사 대상 저장소는 PGARD의 재사용 워크플로를 호출합니다. "재사용 워크플로를 호출하는 작업은 `environment` 키워드를 쓸 수 없습니다". 환경 시크릿을 쓰려면 재사용 워크플로가 자기 작업에 `environment`를 설정하고, 호출자는 여전히 시크릿을 이름으로 "넘겨야" 합니다([워크플로 재사용](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows)).

```yaml
# 검사 대상 저장소의 .github/workflows/pgard.yml (호출자)
on:
  push:
    branches: [main]
  workflow_dispatch:
jobs:
  scan:
    uses: JadenMeister/pgard/.github/workflows/ci-scan.yml@<40자리 hex 릴리스 커밋>
    permissions:
      contents: read
      pull-requests: read
      id-token: write
      security-events: write # SARIF 업로드에만 필요
    secrets:
      PGARD_APP_PRIVATE_KEY: ${{ secrets.PGARD_APP_PRIVATE_KEY }} # 환경 시크릿
```

재사용 워크플로(이 저장소에 둠, **M10-3 요구사항**)는 순서대로:

1. 작업 하나, GitHub 호스티드 이미지에서 `runs-on`, `environment: pgard-ci`(고정 이름), 위와 같은 자체 `permissions`;
2. 고정된 `run:` 단계가 `job.workflow_sha`의 PGARD 소스를 `RUNNER_TEMP`에 가져와 빌드하고(I2, I3), 그 SHA를 빌드에 `BUILD_SHA`로 기록;
3. 이미지의 Node.js를 쓰지 않는다면 SHA로 고정한, 캐시 없는 `actions/setup-node`;
4. SHA로 고정한 `actions/checkout`으로 검사 대상 저장소 체크아웃(I8);
5. `env:`에 `PGARD_APP_ID: ${{ vars.PGARD_APP_ID }}`, `PGARD_APP_PRIVATE_KEY: ${{ secrets.PGARD_APP_PRIVATE_KEY }}`, `GITHUB_TOKEN`을 두고 `pgard scan --identity github-actions --format sarif --output-file "$RUNNER_TEMP/pgard.sarif"` 실행;
6. 선택적으로, SHA로 고정한 `github/codeql-action/upload-sarif`(T15).

**환경과 App 설정**(CI 안내서, **M10-3 요구사항**):

- 기본 브랜치만 허용하는 배포 브랜치 정책으로 환경 `pgard-ci`를 만들고, 필수 검토자를 추가하거나 기본 브랜치를 보호합니다(검토 필수, 가능하면 `.github/workflows`에 대한 코드 소유자).
- 키는 `pgard-ci`의 환경 시크릿으로만 저장하고, 저장소나 조직 시크릿으로는 절대 저장하지 않습니다. (같은 이름의 저장소 시크릿보다 환경 시크릿이 우선하지만, 저장소 시크릿은 여전히 브랜치 워크플로가 읽을 수 있습니다.) App id는 환경 변수 `PGARD_APP_ID`로 저장합니다.
- App은 저장소를 소유한 계정 아래에 등록합니다. **Metadata: 읽기**와, 조직이면 **Members: 읽기**만 줍니다. **선택한 저장소**에 설치합니다.
- OIDC `environment` 클레임은 `pgard-ci`와 같아야 하므로(7.5), 환경 밖 작업의 토큰은 거부됩니다.

**릴리스 결합.** 워크플로 파일은 자기 커밋 SHA나 자기로부터 빌드한 패키지의 해시를 담을 수 없습니다. 대신 작업이 `job.workflow_sha`에서 소스로 `pgard`를 빌드하므로(2단계), `job_workflow_sha == BUILD_SHA`를 검증하는 바이너리는 구조상 그 커밋의 코드입니다. 진짜 릴리스 커밋이라면 이것이 진짜 `pgard`입니다. 대안은 npm 릴리스를 설치하고 그 provenance 증명을 `job.workflow_sha`와 대조하는 것입니다(Q10).

### 7.4 키와 토큰 관리

- `pgard`는 다른 어떤 출력보다 먼저 OIDC 토큰, 설치 토큰, 키에 대해 `::add-mask::`를 출력합니다(T16).
- 키는 환경에서 한 번 읽습니다. 프로세스가 사는 동안 `/proc/<pid>/environ`에 남으며(T16), 이는 7.2의 불변 조건 아래에서만 받아들일 수 있습니다. 절대 로그에 남기거나, 인자로 넘기거나, 파일에 쓰지 않습니다.
- 설치 토큰은 이 저장소 id로 제한하고 읽기 전용이며, 끝나면 `DELETE /installation/token`으로 폐기합니다. 현재 `FetchLike`는 `GET`과 `POST`만 허용하므로 M10-3에서 `DELETE`를 더해야 합니다(**M10-3 요구사항**).

### 7.5 OIDC 토큰에 대한 정확한 확인

따로 적지 않으면 모든 비교는 대소문자를 구분하는 정확한 문자열 비교입니다. 클레임이 없거나, JSON 유형이 틀리거나, 중복되면 `github_identity`는 이유에 클레임 이름을 담아 `unverifiable`입니다(값이 민감할 수 있으면 값은 담지 않음). GitHub 토큰에서 숫자 클레임은 10진 문자열이며, 그 외는 거부합니다.

| 클레임 / 필드                                                                                         | 요구 값                                                                                                 | 기대 값의 출처                 |
| ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------ |
| 헤더 `alg`                                                                                            | `RS256`(`none`, `HS*` 등 그 외는 거부)                                                                  | 상수                           |
| 헤더 `kid`                                                                                            | 있어야 하고, 가져온 JWKS의 키 정확히 하나와 일치                                                        | JWKS(5절)                      |
| 서명                                                                                                  | 그 키로 `header.payload`에 대해 유효한 RS256                                                            | JWKS                           |
| `iss`                                                                                                 | `https://token.actions.githubusercontent.com`                                                           | 상수                           |
| `aud`                                                                                                 | `pgard-ci:v1:<nonce>`; 배열이면 원소가 정확히 하나이고 그 값과 같음                                     | 이 프로세스에서 만든 nonce     |
| `iat`                                                                                                 | 로컬 시계 ±60초 이내                                                                                    | 시계                           |
| `nbf`                                                                                                 | ≤ 현재 + 60초                                                                                           | 시계                           |
| `exp`                                                                                                 | > 현재, 그리고 `exp − iat` ≤ 3600초                                                                     | 시계                           |
| `runner_environment`                                                                                  | `github-hosted`                                                                                         | 상수                           |
| `environment`                                                                                         | `pgard-ci`                                                                                              | 상수(고정 작업의 것)           |
| `event_name`                                                                                          | `push` 또는 `workflow_dispatch`                                                                         | 상수 허용 목록                 |
| `ref_type`                                                                                            | `branch`                                                                                                | 상수                           |
| `ref`                                                                                                 | `refs/heads/` + 이번 실행에서 GitHub가 보고한 기본 브랜치                                               | `GET /repos`(온라인)           |
| `run_attempt`                                                                                         | `1`                                                                                                     | 상수(Q2)                       |
| `repository`                                                                                          | 검증된 원격의 `owner/name`, 그리고 GitHub의 `full_name`과 같음                                          | 로컬 원격, `GET /repos`        |
| `repository_id`                                                                                       | GitHub의 저장소 `id`와 같음                                                                             | `GET /repos`                   |
| `repository_owner` / `repository_owner_id`                                                            | GitHub의 `owner.login` / `owner.id`와 같음                                                              | `GET /repos`                   |
| `sha`                                                                                                 | 40자리 hex, 로컬 `HEAD`와 같음(`HEAD`는 그 커밋의 체크아웃이어야 하고 작업 트리는 깨끗해야 함)          | 로컬 Git                       |
| `job_workflow_sha`                                                                                    | `<BUILD_SHA>`                                                                                           | `pgard`에 내장                 |
| `job_workflow_ref`                                                                                    | `JadenMeister/pgard/.github/workflows/ci-scan.yml@`로 시작(저장소와 경로 접두사, 커밋은 위 행에서 확인) | 상수                           |
| `actor_id` / `actor`                                                                                  | 10진 / 비어 있지 않음; `GET /user/{actor_id}`가 `type: User`, 같은 `id`, `login == actor`를 돌려줌      | `GET /user/{actor_id}`(온라인) |
| `sub`, `workflow`, `workflow_ref`, `workflow_sha`, `run_id`, `ref_protected`, `repository_visibility` | 결정에 쓰지 않음. 실행을 추적할 수 있도록 `workflow_ref`와 `run_id`는 `github_identity` 이유에 적음.    | 해당 없음                      |

토큰 요청 자체: `pgard`는 `ACTIONS_ID_TOKEN_REQUEST_URL`과 `ACTIONS_ID_TOKEN_REQUEST_TOKEN`을 읽고, URL이 HTTPS여야 하며, `audience=pgard-ci:v1:<nonce>`를 붙이고, 두 변수와 토큰을 가리고 절대 로그에 남기지 않습니다. 공격자가 통제하는 요청 URL은 기껏해야 토큰을 돌려줄 수 있을 뿐이며, 그 토큰은 위의 모든 확인을 통과해야 합니다.

| `owner_approval`  | C2가 있으면: App JWT; `GET /app` → `owner.id == repository_owner_id`; `GET /repos/{owner}/{repo}/installation` → `app_id` = `PGARD_APP_ID`, `account.id` = `owner.id`, `target_type` = 소유자 유형; 이 저장소로 제한한 읽기 전용 설치 토큰 발급. 조직이면 추가로 `GET /orgs/{org}/memberships/{actor}`가 `state: active`, `role: admin`, `user.id == actor_id`, `organization.id == owner.id`. 같은 `OwnerEvidence`를 만듦(`userId = actor_id`). C2가 없으면: `unverifiable`, "CI cannot prove that the repository owner approved PGARD: set up the pgard-ci environment with the App id and private key of a GitHub App owned by the repository owner (see the CI guide)."                                                                                   |
| `contribution`    | `verifyContribution`을 그대로, `user = 주체`, 로컬 후보(`fetch-depth: 30`으로 최대 30개), 사실용 `GITHUB_TOKEN`, 이번 실행의 소유자 승인에서만 나온 `ownerEvidence`로 실행.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

게이트 코드는 신원 단계에서만 바뀝니다(**M10-3 요구사항**): `getGitHubSession`이 두 제공자(디바이스 플로 또는 GitHub Actions OIDC) 중 하나가 되어 각각 주체와 사실용 클라이언트를 돌려주고, `verifyCurrentAccess`에 CI용 주체 기반 변형이 생깁니다. `AUTHORIZATION_CHECK_ORDER`, `isAuthorizationAllowed`, "절대 캐시하지 않음" 규칙은 바뀌지 않습니다.

## 9. 범위 밖

- **다른 CI 시스템**(GitLab CI, Jenkins, CircleCI, Buildkite, Azure Pipelines 등). PGARD의 소유자 승인은 저장소를 소유한 GitHub 계정에 GitHub App을 설치하는 것이며, 이를 증명할 수 있는 것은 GitHub뿐입니다. GitLab CI OIDC 토큰은 GitHub 저장소나 GitHub 사용자가 아니라 GitLab 프로젝트와 파이프라인을 증명하며, 둘을 잇는 것은 없습니다(미러는 어디든 가리킬 수 있음). Jenkins에는 플랫폼이 서명한 작업 신원이 아예 없습니다. 시스템마다 자체 발급자, 클레임, 위협 모델, GitHub 계정과의 대응이 필요하므로 각각 별도 설계가 필요합니다. 그때까지 `--identity`는 `github-actions`만 받고, 이 시스템들은 지금과 같이 터미널과 저장된 로그인 없이는 막힙니다.
- **GitHub Enterprise Server와 엔터프라이즈 전용 발급자**(Q8): 다른 발급자, 키 집합, API 호스트.
- **CI에서 풀 리퀘스트 검사**(U2): CI는 기본 브랜치로 한정합니다.

## 10. M10-3 요구사항과 테스트 계획

이 문서에 나온 요구사항을 한 목록으로:

- 넘어가기(fallback) 없는 `--identity github-actions` 제공자(이름은 Q7에 따름);
- 프로세스별 nonce audience를 쓰는 OIDC 요청;
- 발급자와 JWKS URL을 고정하고 JWKS는 메모리에만 두는 JWT 검증;
- 7.5절의 정확한 클레임 표;
- 고정 환경 `pgard-ci`, 불변 조건 I1~I8, `job.workflow_sha`에서 소스로 빌드하고 `BUILD_SHA`를 기록하는 재사용 워크플로 `ci-scan.yml`;
- CI의 깨끗한 작업 트리 확인;
- CI용 주체 기반 `current_access`;
- C2 소유자 승인: App JWT, `GET /app` 소유자 확인, 설치 조회, 제한된 읽기 전용 설치 토큰, `FetchLike`의 `DELETE` 지원과 폐기;
- 가림(masking)과 키 관리(7.4);
- CI 로그에 발견 사항 세부 내용 없음(T15);
- README와 CI 안내서: 환경, 배포 브랜치 정책, 검토, 소유자 아래의 App 등록, 최소 권한, 선택한 저장소 설치, T11의 남은 위험, 저장소 단위의 동의, 무엇이 왜 막히는지.

테스트(실제 GitHub 호출 없음, 가짜 JWKS로 제공하는 테스트 키로 서명한 토큰):

- 7.5절의 각 행을 하나씩 바꾸면 기대한 이유와 함께 막힘:
  - 잘못된 `iss`나 `aud`, 만료, 미래의 `iat`;
  - `alg: none`, 공개 키를 비밀로 쓴 `HS256`, 모르는 `kid`;
  - `self-hosted`, 다른 `environment`나 환경 없음;
  - `pull_request`, `pull_request_target`, `workflow_run`, `schedule`, `merge_group`;
  - `run_attempt: "2"`, 다른 브랜치의 `ref`, `sha` ≠ `HEAD`;
  - 다른 커밋의 `job_workflow_sha`, 다른 저장소나 경로의 `job_workflow_ref`;
  - 빠진 클레임, 문자열 대신 숫자;
- 다른 프로세스의 nonce를 가진 토큰(재사용)은 막힘;
- 요청 변수 없이 `GITHUB_ACTIONS=true`이면 막힘. 다른 저장소에 대해 유효하게 서명된 토큰을 돌려주는 서버를 요청 변수가 가리켜도 막힘;
- actor 경우:
  - 봇 actor와 App이 한 푸시는 막힘;
  - 배포 키(deploy key)로 한 푸시와 merge queue 실행: 토큰에 무엇이 담기는지 M10-3에서 확인하며, actor가 확인 3~5를 통과하는 `User`가 아니면 막힘;
  - 개인 소유자, 조직 소유자, 기여가 있거나 없는 협업자는 로컬 테스트와 같이 동작;
  - 공개 저장소에서 협업자가 아닌 사람의 `current_access`는 로컬 결과와 같음;
- C2:
  - 없으면 `owner_approval`은 `unverifiable`이고 다른 확인은 여전히 자기 이유를 보고;
  - 다른 계정이 소유한 App은 실패;
  - 다른 App의 설치는 실패;
  - 설치 토큰은 폐기됨;
- 불변 조건마다 테스트나 워크플로 lint 규칙 하나씩:
  - I1: `workflow_call` 입력 없음;
  - I2: 빌드가 체크아웃 전에 `RUNNER_TEMP` 아래에서 일어남;
  - I3: 검사 대상 저장소의 `.npmrc`는 영향 없음;
  - I4: 캐시 단계 없음, 호출자의 `cache-mode`는 아무것도 복원하지 않음;
  - I5: 모든 `uses:`가 40자리 hex SHA로 고정되고, composite 액션에 고정되지 않은 의존성이 없음;
  - I6: `./` 액션 없음;
  - I7: `run:`, `uses:`, `with:`에 `github.event`, `vars`, `inputs` 없음;
  - I8: 어떤 단계도 검사 대상 저장소의 코드를 실행하지 않음;
- T15: 발견 사항이 있는 검사가 로그에 세부 내용을 남기지 않음;
- T16: 토큰과 키가 가려지고, 디버그 로그가 그것들을 출력하지 않음;
- JWKS 가져오기 실패, 리디렉션, 너무 큰 본문: `unverifiable`, 넘어가기 없음;
- `isAuthorizationAllowed`와 다섯 확인의 순서는 그대로(기존 테스트가 계속 통과).

## 11. 소유자에게 묻는 열린 질문

1. **Q1. CI의 소유자 승인 증거.** 기본 제공 PGARD App으로는 CI에서 소유자 승인을 증명할 수 없습니다(U1). 선택지: (a) **저장소 소유자가 소유한 App으로 C2**, 단 7.3의 강화(고정 환경, 검토가 있는 기본 브랜치 정책, App 소유자 확인, 최소 권한, 선택한 저장소)와 안내서에 적힌 T11의 남은 위험이 있을 때만; (b) 기본 제공 App의 키를 가진, 관리자가 운영하는 서비스가 OIDC 토큰을 검증하고 설치 여부에 답함. "검사는 GitHub에만 연결한다"를 깨고 운영할 서비스가 생김; (c) 기본 브랜치에 소유자가 서명한 정책 파일 같은 새로운 종류의 증거. 정책 변경이므로 별도 검토가 필요. 권장: 그 강화를 갖춘 (a), 그리고 기본 제공 App은 CI에서 막힌 채로 둠.
2. **Q2. 재실행.** 모든 `run_attempt > 1`을 막을지(권장. 재실행한 사람을 모르므로), 아니면 재실행을 받고 주체가 첫 시도의 actor라고 문서화할지?
3. **Q3. `schedule`.** 권장: 영구히 막음. 문서화된 예약 실행의 actor는 그 실행을 요청한 사람일 필요가 없기 때문입니다(U3). 확인 부탁드립니다.
4. **Q4. `ref_protected`.** 이 클레임은 OpenID 설정에는 나열되지만 OIDC 레퍼런스에는 설명이 없으므로 설계는 여기에 기대지 않습니다. 권장: 요구하지 않고, 대신 안내서에서 브랜치 보호를 권함.
5. **Q5. 풀 리퀘스트 검사.** 권장: CI는 기본 브랜치로 한정하고, 지금은 별도 설계를 계획하지 않음. 확인 부탁드립니다.
6. **Q6. 셀프 호스티드 러너.** 영구히 막을지(권장), 아니면 증명할 수 없음을 알면서 소유자가 선언하는 예외를 설계할지?
7. **Q7. CI 선택 방법.** 플래그(`--identity github-actions`), 환경 변수(`PGARD_IDENTITY=github-actions`), 또는 둘 다? 권장: 플래그만, 자동 감지는 절대 하지 않음.
8. **Q8. GitHub Enterprise.** ghe.com이나 GitHub Enterprise Server가 나중에 범위에 들어오는지? 다른 발급자와 API 호스트가 필요합니다.
9. **Q9. 환경 변수의 App 키.** 권장: `pgard-ci` 환경 시크릿에서 온, 단 하나의 `pgard` 단계에만 주는 환경 변수, 가림 처리, T16의 `/proc` 주의 사항을 문서화. 이는 사용자 토큰이 아니라 App 자격 증명이므로 사용자 토큰에 대한 현재 규칙은 바뀌지 않습니다.
10. **Q10. 릴리스 결합.** 작업 안에서 `job.workflow_sha`의 소스로 `pgard`를 빌드할지(권장), 아니면 npm 릴리스를 설치하고 그 provenance를 그 커밋과 대조할지?
