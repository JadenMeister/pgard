# Security design: choosing a project in `pgard web`

> [한국어](WEB_PROJECT_PICKER_DESIGN.ko.md) translation available. This English file is the reference; the translation follows it.

Status: design for review ([#355](https://github.com/JadenMeister/pgard/issues/355), M8-3). Nothing in this document is implemented. M8-4 implements it after review. Back to the [README](../README.md) and the [documents index](README.md).

Statements about "today" describe the code at the time of writing (`apps/local-web/src/server`, `apps/cli/src/commands/dashboard.ts`, `packages/policy`, `packages/git-history`, `packages/result-store`). Where this design relies on something the code does not have yet, it is marked **Requirement for M8-4**. The README stays the source of truth for current behavior; this design changes some of its sentences (see [README changes](#readme-changes-in-m8-4)).

## 1. Goals and non-goals

### Goals

1. `pgard web` starts without a project. The user picks one by searching or by dropping a folder onto the page.
2. The browser is only a **signal** of which project the user means. It never supplies a path and never sends file contents.
3. The local server finds matching Git repositories inside a **user-defined search scope** and shows the real path and the remote. The user confirms them.
4. After confirmation the same five authorization checks run (repository, GitHub identity, owner approval, current access, contribution). A wrong folder can never lead straight to a scan.
5. If the evidence is unclear, block and say why and how to fix it. Authorization is never loosened.
6. Code, paths and results stay local. Nothing new is sent anywhere.

### Non-goals

- No file or directory contents are read for the picker, in the browser or by the server, beyond directory entry names and Git metadata through the existing allowlisted Git runner.
- No browser-typed absolute path, no native folder dialog, no `showDirectoryPicker`.
- No scanning of remote hosts, network shares or removable volumes by default.
- No change to `pgard dashboard`, which stays fixed to the Git root of the terminal's current directory, confirmed in the terminal.
- No change to the authorization gate, its order, its reasons or its caching rules (it is never cached).
- No persistence of scan results by the dashboard (unchanged).
- Protection against an attacker who already runs code as the same OS user is out of scope (they can read the folders directly); the design only avoids making their job easier. See the residual risks in [section 2](#2-threat-model).

## 2. Threat model

Assets: the user's source code and Git history; the paths and repository names on the machine; the GitHub sign-in (OS keychain, never sent to the browser); the authorization decision.

Trust boundaries: the terminal where `pgard web` was started (trusted, the user confirms there); the browser tab that received the session URL (trusted only with the token); every other browser tab, web page and local process (untrusted); the contents of any repository on disk (untrusted data, including its `.git/config`).

What the current server already does, verified in `apps/local-web/src/server/middleware/security.ts` and `create-server.ts`:

- binds to `127.0.0.1` on a free port; `Host` must equal `127.0.0.1:<port>` exactly (421 otherwise);
- every `/api/` call needs the `x-pgard-token` header (32 random bytes, compared with `timingSafeEqual`); a foreign `Origin` or a `Sec-Fetch-Site` other than `same-origin`/`none` is refused; state-changing calls must carry our exact `Origin`; the API sends no CORS headers;
- every response has `Cache-Control: no-store`, a CSP with `default-src 'none'` and `connect-src 'self'`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy: same-origin`;
- the token travels in the URL fragment, the page removes it from the address bar and keeps it in memory only;
- request bodies are capped at 16 KiB and must be `application/json`;
- the server writes no per-request log (the launcher only writes the startup lines and one stop line);
- the project root is fixed for the server's lifetime (`ApiContext.projectRoot`), and no route accepts a path.

The last point is what this design changes, and the only thing that does: a project is chosen after start.

The browser can only toggle roots the server lists, never add a path. The walk stays inside the root's `dev` (T5) and never descends into `.git`, a found repository (no nested search; submodules are not offered) or a symlink. A recent-list entry that lies outside the current scope is blocked `outside_scope` and not offered, with the fix "add its folder with `pgard web scope add` or remove the entry".                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| T5  | **Huge or slow trees, network mounts, hung syscalls**                                                 | Hard limits per search, all server-side constants: depth 4 below a root (maximum 6), 50,000 directory entries visited, 5,000 entries read from any one directory, 20 candidates returned, 5 s soft deadline (stop and say `partial`), 8 s hard deadline. One search at a time per session; a new one cancels the old; at most one search per second (429). A fixed skip list of heavy or private folders (`node_modules`, `.git`, `.cache`, `.npm`, `.Trash`, `Library` on macOS, `AppData` on Windows, and every other dot-folder except those a root names). The walk does not cross a file system boundary: a directory whose `dev` differs from its root's is not entered (like `find -xdev`), which covers mounted volumes and network shares under a root on macOS, Linux and Windows drives. Therefore **Requirement for M8-4:** the walk runs in a `worker_threads` Worker (or a child process) that the server terminates at the hard deadline, so a hung call cannot freeze the dashboard. Residual: a mount that answers slowly but under the limits is still walked until the deadline; the result then says it is partial.                                                                       |
| T6  | **Leaks of paths or repository names** to logs, history, referrer                                     | The server logs nothing per request today, and the picker adds nothing (see [section 7](#7-what-is-logged)). The folder name travels only in a `POST` body, never in a URL, so it is not in the address bar, the browser history, a `Referer` header or an access log. Poll requests use a random search id, not a name. Error messages never echo a name, path or remote URL (reasons are fixed texts, as `readGitHubRemote` already does, because URLs may embed credentials). The UI does not put the project name into `document.title`, `location`, `history.pushState` or any `localStorage` key or value. The search input has `autocomplete="off"`, `autocapitalize="off"` and `spellcheck="false"` so the browser does not store the name in form history or send it to a spell-check service. Links to GitHub use `rel="noopener noreferrer"` (the page-level `Referrer-Policy: no-referrer` already applies). The display path is shortened with `~` for the home folder and passed through `sanitizeDisplayText`. Paths do appear in the terminal only where the user confirmed them, as in `pgard dashboard` today. Residual: the browser's drag-and-drop machinery and the OS may keep the dropped folder name in their own caches; PGARD cannot control that.                                                                                                                                                |
| T7  | **TOCTOU between confirming a path and scanning it**                                                  | The server never trusts the browser's description of a candidate. A candidate is a server-held record (random 128-bit id) with `realRoot`, `dev`/`ino` of the root and of its `.git`, the repository `owner/name` read from the remote, and a timestamp. `confirm` accepts it only within 10 minutes of the search finishing (`PROBE_CONFIRM_WINDOW_MS` is the existing precedent; a clock that moved back fails closed) and **re-inspects** it: same `realpath`, same `dev`/`ino`, still inside the scope, still a Git root, still the same `owner/name`, and the fingerprint the UI displayed (`shown`) equals the server's. Residual: between the last comparison and the file reads of the analysis, a process running as the same user could still swap the directory; that user can already read the files, so this is not a privilege escalation, and the other-user case is covered by the ownership and permission checks in T1. Analysis skips symlinks to files and directories already (README, "Incremental scans"). |
| T8  | **A repository whose remote is not github.com** (or has none, or several different ones)              | The local repository check (`verifyRepository` in `packages/policy/src/checks.ts`) is the source of truth: every fetch and push URL of every remote must parse as the same github.com repository, otherwise the reason is fixed text. The picker shows such a candidate as **blocked, not selectable**, with that reason and the fix (see [section 5](#5-ui-states)). The remote URL itself is never sent to the browser, only `owner/name` for a github.com remote and a fixed reason otherwise. A GitHub Enterprise host, a look-alike host or a mirror is also a non-github.com remote and is blocked, exactly as in the CLI. **Requirement for M8-4:** `verifyRepository` is not exported from `@pgard/policy`; export a local-only "inspect repository" function (no network, no sign-in) so the picker and the gate use the same code. Git runs through the existing hardened runner (`core.fsmonitor=false`, `core.hooksPath` to the null device, no system or global config, allowlisted subcommands), so a hostile `.git/config` cannot execute programs.                                                                                                                                                                                                                                                                                                                                                          |
| T9  | **The recent-list file is tampered with** (or the settings file)                                      | The list is a _hint_, not authority. Each entry is validated as if it were a new search result on every load: it must be a regular, user-owned file with owner-only mode in a non-symlinked `0700` folder; capped at 64 KiB and 20 entries; parsed with a strict schema (unknown `schemaVersion` major: ignored and never overwritten, as the result store does). A tampered entry can therefore at worst appear as a candidate the user sees and refuses. The settings file can widen the scope, so it gets the same file protections and, in addition, its roots are re-validated at every launch and **shown in the terminal prompt before the server starts**; the browser cannot change it. No signature is used: a same-user attacker can read any key PGARD would keep, and a keychain key would add prompts for no gain.                                                                                                                                                                                                                                                                                                                                                                       |
| T10 | **Paths in the process list**                                                                         | `ps` shows the arguments of every local user's processes. Today `pgard dashboard` passes `--project-root <abs>` to the launcher; that is existing behavior. The picker adds no path to argv: scope roots live in the settings file, and `pgard web` starts the launcher with no path arguments.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

## 3. API sketch

All routes are added to `API_ROUTES` (exact `"METHOD /path"` keys, so there are no path parameters; ids go in the query string or the body). All pass through the existing Host, Origin and token checks before the handler. All bodies are `application/json` of at most 16 KiB (the existing cap; picker bodies are far smaller). Errors use the existing envelope `{ "error": { "code", "message" } }` with fixed, translatable messages.

When no project is selected, every existing route that needs one (`/api/auth/*`, `/api/ports*`, `/api/target*`, `/api/scan*`, `/api/reports/*`) returns `409 no_project`.

```ts
interface Candidate {
  candidateId: string; // random 128 bit, server-held, valid 10 minutes
  name: string; // sanitized, <= 120
  displayPath: string; // real path, "~"-shortened, sanitized, <= 400
  shown: string; // fingerprint of realRoot + dev/ino + owner/name; echoed back on confirm
  remote:
    | { status: "github"; repo: string } // "owner/name"
    | { status: "none" | "not_github" | "ambiguous" | "unreadable" };
  selectable: boolean;
  blocked: null | {
    code: PickerBlockCode;
    reason: string; // fixed text (EN; the UI maps the code to EN/KO)
    fix: string; // fixed text
  };
  source: "scope" | "recent";
}

interface RecentEntry extends Candidate {
  lastUsedAt: string;
} // ISO time
```

`Candidate.remote.status` and `blocked` come from the shared local repository check. Only `owner/name` is returned for a github.com remote; no URL, no remote name.

## 4. Session and token binding

Reuse of the current mechanism, with no new credential:

- One token per server run, printed once in the URL fragment; the page keeps it in memory and sends it in `x-pgard-token`. Nothing in the picker is available without it, including candidate ids, search ids and the recent list.
- Candidate and search ids are random, 128 bit, only meaningful with the token (they are per-session server state, like `SessionState`), never stored on disk, and gone when the server stops (`clearSessionState`).
- The new state lives in `SessionState`: the selected project record, the current search, the candidate map and the `projectEpoch`. It is cleared by `clearSessionState` on shutdown, as the rest is.
- Origin and Host rules are unchanged. The picker adds no cookie, no `localStorage` use for names or paths, and no second token.
- **Requirement for M8-4:** `ApiContext.projectRoot` becomes a value read from the session state (null until confirmed). `startScan`, `startVerify`, `recheckOwnerApproval` and the report routes must read it at call time, compare the project record (T7) and reject with `no_project` when it is null.
- **Requirement for M8-4:** `projectEpoch` increments on every confirm and clear; state-changing project routes (`/api/picker/*`, `/api/auth/verify`, `/api/scan`) carry it so a stale second tab is refused. Today no route has one.
- The account binding is unchanged: the signed-in GitHub account is independent of the project. A project change resets the authorization record, so the next check runs from scratch.

`pgard web` (new command) needs an interactive terminal, like `pgard dashboard`: it prints the search scope roots and asks `Search these folders for projects? [y/N]` before starting the server (exit 2 without a terminal). It passes no path on the command line.

## 6. Storage format

Folder: the existing per-user app-data directory from `resolveStoreDirectory()` (`~/Library/Application Support/pgard`, `$XDG_DATA_HOME/pgard` or `~/.local/share/pgard`, `%LOCALAPPDATA%\pgard`), in a new subfolder `web/` so that deleting `repos/` stays safe and unrelated. Never inside a project. Protection follows the result store: `0700` folder and `0600` files on macOS and Linux, no symlink followed for the folder or the files, write to a temp file in the same folder (exclusive create) then rename, size cap before parsing, an unsupported or newer `schemaVersion` is ignored with a notice and never overwritten. On Windows mode bits do not apply and the profile folder's ACLs are inherited and not checked, as for the result store.

**Requirement for M8-4:** the safe-file helpers in `packages/result-store/src/store.ts` are private to the store class today. Extract them (or add the two files as a module of `@pgard/result-store`) rather than re-implementing them.

`web/settings.json`:

```json
{
  "schemaVersion": "1.0",
  "searchRoots": [{ "path": "/Users/alice/code" }],
  "acceptedDefaultHome": false
}
```

- `searchRoots[].path` is an absolute `realpath` at the time it was added. Re-validated at every launch (exists, directory, owned by the user, depth rule); an invalid root is dropped from the session and reported in the terminal.
- Roots are changed only in the terminal: `pgard web scope list | add <folder> | remove <folder>`. `add` resolves and shows the real path and asks for confirmation.
- Limits are constants, not settings (see open question Q2).

`web/recent-projects.json`:

```json
{
  "schemaVersion": "1.0",
  "entries": [
    {
      "id": "r1",
      "path": "/Users/alice/code/shop",
      "repo": "alice/shop",
      "lastUsedAt": "2026-10-28T09:00:00Z"
    }
  ]
}
```

- At most 20 entries, newest first, one per `realpath`; written only after a successful **confirm** (not after a search, and not when the gate later blocks: only a confirmed project).
- `repo` is a display hint only; the displayed owner/name always comes from a fresh read.
- It holds absolute paths, unlike scan results. It is therefore listed in the README as an exception, is removed by `pgard history clear --all`, and is not written when `--no-store` or `PGARD_NO_STORE=1` is set (the recent list is then empty in that session).

## 7. What is logged

- **Server:** nothing per request, as today. No access log, no debug log. The only terminal output stays the startup and stop lines, plus the scope prompt before start, which the user asked for.
- **Never written anywhere** (terminal, file, error text, crash message, telemetry, API errors): a searched or dropped folder name, a scope root, a candidate path, a remote URL, a candidate or search id, the token.
- **In memory only**, discarded on stop: the search, the candidate map, the selected project record, counters such as `visited`.
- **API errors** carry only fixed codes and fixed messages.
- **On disk:** only the two files in [section 6](#6-storage-format). No result is stored by the dashboard.
- **Not logged by the browser:** names and paths are not put in the URL, the title, `localStorage` or the console. The UI language preference is the only thing the page already stores.

## 8. Test plan for M8-4

Unit and integration (vitest, injected `ServerDeps` as the existing tests; no real GitHub, no real keychain):

1. **Middleware reuse.** Each picker route rejects: no token, wrong token, wrong `Host` (including `localhost` and a rebound name), foreign `Origin`, missing `Origin` on POST, `Sec-Fetch-Site: cross-site`, wrong content type, body over 16 KiB. No CORS header on any response, including errors.
2. **Name validation.** Table of bad names: empty, `.`, `..`, `a/b`, `a\b`, `C:`, NUL, control and bidi characters, trailing dot or space, `CON`, 256 units, lone surrogates. NFC and NFD of the same name match the same directory.
3. **Walk.** Fixture trees in a temp directory: depth limit, entry limits, deadline (injected clock) giving `partial`, skip list, no nested search inside a found repository, symlink to a repository outside the scope not offered, symlink loop, symlinked ancestor of a candidate, directory not owned by the user (POSIX, by stubbing `lstat`), a different `dev` (stubbed) not entered.
4. **Worker kill.** A stubbed walker that never returns is terminated at the hard deadline and the server still answers other routes.
5. **Case-insensitive file systems.** Run on the CI `macos-latest` and `windows-latest` jobs (the existing check matrix has both): name `Shop` finds `shop`; scope prefix check with different case; `dev`/`ino` identity used instead of the path string; a name that differs only by case from two directories on a case-sensitive Linux disk returns both. Windows: junction and reparse-point skipped, `\\?\` and UNC roots refused, 8.3 short name resolves to the same identity or is blocked, `ino === 0` gives `identity_unavailable`.
6. **Candidate checks.** For each block code, a fixture repository: no remote, `https://example.com/o/r.git`, GitHub Enterprise host, two remotes to different repos, a remote URL with embedded credentials (the response must not contain the credential or the URL), no commits, alternates, a hostile `.git/config` with `core.fsmonitor`, hooks and `core.sshCommand` that must never run (assert a marker file is not created).
7. **TOCTOU.** After a search: rename the directory, replace it with a symlink, replace it with a different repository, change its remote, wait past 10 minutes (injected clock, also a clock moved back): each gives `candidate_changed` or `candidate_expired` and selects nothing. Between confirm and `POST /api/scan`, swap the directory: the scan is refused. A gate result with a different `owner/name` is refused.
8. **State reset.** Confirm a second project: authorization, target, probe, scan and report are cleared; the old report download returns `409`; confirm during a scan returns `scan_in_progress`; a stale `epoch` returns `project_changed`; routes return `no_project` before the first confirm.
9. **Gate unchanged.** After confirm, `POST /api/auth/verify` runs the unmodified `authorizeProject` with all five checks; a scan after a stale earlier allowed result still re-runs it. A private repository outside the App installation ends in `current_access` failed with the existing install remedy.
10. **Files.** Settings and recent file: created `0600` in `0700`; refused through a symlink or when group/world-writable; oversized, malformed, unknown major `schemaVersion` ignored and not overwritten; 21 entries truncated; tampered `path` to a non-repository, to a symlink, to another user's folder, to a path outside the scope: shown blocked, never selectable, display text from the fresh read; `--no-store` writes nothing; `history clear --all` removes both.
11. **No leaks.** Capture stdout, stderr, thrown messages and every API response while running the scenarios above with a distinctive name and path: none contains the name, the path, a remote URL or a token, except the response fields that are meant to (`displayPath`, `name`, `repo`). The built client bundle and `index.html` never write the name into `document.title`, `location` or `localStorage` (DOM test). The search input has the three attributes of T6.
12. **Client.** The drop handler reads only `webkitGetAsEntry().name` and `isDirectory` and never calls `getAsFile`, `createReader` or `FileReader` (test with a spy). A dropped file (not a folder) shows "Drop a folder, not a file". The blocked states of section 5 render their reason and fix in English and Korean.

End to end, with the existing fake-GitHub deps and no real account, `pgard web` never run against a real account in tests:

13. Pick a repository by name, confirm, pass the five checks, scan, download a report.
14. **Private repository outside the App installation**: pick it, confirm, reach the blocked `current_access` state, see the install guidance, and nothing is scanned.
15. Pick a repository with a non-github.com remote: blocked in the picker with the reason, never reaches authorization.
16. Pick the wrong one of two same-named folders: the confirmation shows the other path and `owner/name`; the user goes back.

## 9. README changes in M8-4

The current README says "The browser cannot choose or read project files. The project root is fixed when the dashboard starts" and "The browser supplies no path at all". After M8-4 these hold for `pgard dashboard` only. For `pgard web` the README must say instead: the browser sends only a folder name; the server searches the user's scope; the user confirms the real path and remote; the five checks run; no file contents are read for this. It must also add the recent-list file and the settings file to the "Stored results" and "Privacy" sections as local, never-uploaded files that contain absolute paths, and update `pgard history clear --all`.

## 10. Open questions for the owner

- **Q1. Default scope.** Should the first run propose the whole home folder (with the skip list), or nothing until the user adds a folder with `pgard web scope add`? This design proposes: home, shown and confirmed in the terminal on first run (`acceptedDefaultHome`), because an empty scope makes drag-and-drop useless at first contact. A narrower default (for example `~/code`, `~/projects`, `~/dev` when they exist) is the alternative.
- **Q2. Limits.** Are depth 4, 50,000 entries, 20 candidates and 5 s acceptable, and should any be user-settable? This design keeps them as constants.
- **Q3. Adding a root from the browser.** This design allows only the terminal to add or change roots (the browser may only toggle existing ones), so a compromised page cannot widen the scope. Is that acceptable, or should the browser be able to request a root (confirmed in the terminal)?
- **Q4. Command naming.** `pgard web` is a new command next to `pgard dashboard`. Is `pgard dashboard` kept as the fixed-project command, or is it replaced? This design keeps both.
- **Q5. Recent list and `--no-store`.** The design writes no recent list when `--no-store` or `PGARD_NO_STORE=1` is set. Is "store nothing" the right reading for a list of project paths, or should the recent list have its own switch?
- **Q6. Windows.** No ownership check and no reliable network-drive detection from Node core. Is a documented residual risk acceptable for the first M8-4 release, or should the first release be macOS and Linux only for the picker?
- **Q7. Recent entries outside the scope.** Blocked as `outside_scope` here (strict). Allow them because the user confirmed them before?
- **Q8. Same-user attacker and swap between confirm and analysis.** Accepted as out of scope here because that attacker can read the files already. Confirm that is the intended boundary.
- **Q9. Worker thread or child process** for the walk. Both give a hard kill; a child process is safer against a hung syscall in a shared thread pool but costs startup time. Preference?
