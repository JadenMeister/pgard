## 1. Goals and non-goals

### Goals

1. `pgard web` starts without a project. The user picks one by searching or by dropping a folder onto the page.
2. The browser is only a **signal** of which project the user means. It never supplies a path and never sends file contents.
3. The local server finds matching Git repositories inside a **user-defined search scope** and shows the real path and the remote. The user confirms them.
4. After confirmation the same five authorization checks run (repository, GitHub identity, owner approval, current access, contribution). A wrong folder can never lead straight to a scan.
5. If the evidence is unclear, block and say why and how to fix it. Authorization is never loosened.
6. Code, paths and results stay local. Nothing new is sent anywhere.

### Decisions already made by the owner

- **Platforms.** macOS and Linux first. On Windows, `pgard web` exits with the usage error (2), explains that the picker is not available there yet, and points to `pgard dashboard` (**Requirement for M8-4**, with a test that runs on the Windows runner). The Windows-specific problems (junctions, UNC paths, 8.3 names, missing `ino`, no ownership check from Node core) are deliberately not designed here and must be designed before the picker is enabled there.
- **Default scope.** Only these common development folders, and only those that exist: `~/code`, `~/projects`, `~/dev`, `~/src`, `~/workspace`, `~/git`, `~/Developer`. They are printed and confirmed in the terminal on first run. Adding the whole home folder is an explicit opt-in (`pgard web scope add ~`, with a warning). Reason: on macOS, walking the home folder triggers TCC permission prompts and makes iCloud download dataless files.
- **Search roots are added in the terminal only.** The browser may show the `pgard web scope add <folder>` command for the user to copy; it can never add or change a root.
- **Two commands.** `pgard dashboard` stays fixed to one project and hard-disables the picker. `pgard web` is the picker.
- **`--no-store`.** The recent list follows `--no-store` / `PGARD_NO_STORE=1`; `pgard web` gets the `--no-store` option (**Requirement for M8-4**).
- **Strict recent list.** A recent entry outside the current scope is shown as a blocked card with the fix.
- **Same-user attackers are out of scope.** A process that already runs as the same OS user can read the folders directly. Other users are covered by the ownership and permission checks (T1, T13).
- **Isolation.** The directory walk, the inspection of candidates (including every Git call) and the revalidation of the recent list run in a **child process**, killed together with its process group.
- **Limits are constants**, with a per-search budget and a minimum typed length of 2.

### Non-goals

- No file or directory contents are read for the picker, in the browser or by the server, beyond directory entry names, `lstat` data and Git metadata through the existing allowlisted Git runner.
- No browser-typed absolute path, no native folder dialog, no `showDirectoryPicker`.
- No scanning of remote hosts, network shares or removable volumes by default.
- No change to the authorization gate, its order, its reasons or its caching rules (it is never cached), except the one added `expectedRepo` check in M4/T7.
- No persistence of scan results by the dashboard (unchanged).
- No linked worktrees, submodules or other `.git` files in v1 (T13).

## 2. Threat model

Assets: the user's source code and Git history; the paths and repository names on the machine; the GitHub sign-in (OS keychain, never sent to the browser); the authorization decision.

Trust boundaries: the terminal where `pgard web` was started (trusted, the user confirms there); the browser tab that received the session URL (trusted only with the token); every other browser tab, web page and local process (untrusted); the contents of any repository on disk (untrusted data, including its `.git/config`); the inspector child process's output (validated by the server against a strict schema, because the child reads untrusted data).

What the current server already does, verified in `apps/local-web/src/server/middleware/security.ts` and `create-server.ts`:

- binds to `127.0.0.1` on a free port; `Host` must equal `127.0.0.1:<port>` exactly (421 otherwise);
- every `/api/` call needs the `x-pgard-token` header (32 random bytes, compared with `timingSafeEqual`); a foreign `Origin` or a `Sec-Fetch-Site` other than `same-origin`/`none` is refused; state-changing calls must carry our exact `Origin`; the API sends no CORS headers;
- every response has `Cache-Control: no-store`, a CSP with `default-src 'none'` and `connect-src 'self'`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy: same-origin`;
- the token travels in the URL fragment, the page removes it from the address bar and keeps it in memory only;
- request bodies are capped at 16 KiB and must be `application/json`;
- the server writes no per-request log (the launcher only writes the startup lines and one stop line);
- the project root is fixed for the server's lifetime (`ApiContext.projectRoot`), and no route accepts a path;
- there is no WebSocket or Server-Sent Events endpoint, and the picker adds none (progress is polled), so no upgrade path needs its own Host/Origin handling.

The fixed project root is what this design changes, and the only thing that does: a project is chosen after start.

| T5  | **Huge or slow trees, network mounts, hung syscalls**                                                               | Hard limits per search (constants): depth 4 below a root (maximum 6), 50,000 directory entries visited, 5,000 entries read from any one directory, 20 candidates returned. **One budget per search covers everything**: walk, candidate inspection (`realpath`, `lstat`, the Git calls) and revalidation: 5 s soft (stop walking, report `partial`) and 8 s hard (child killed). When the budget runs out the response is `partial` with `stoppedAfterSeconds`; folders the walk found but could not inspect are returned as blocked `not_inspected` cards (never selectable, never dropped silently) and counted in `uninspected`. The 3 s Git timeout and the 8 s budget are constants. Each Git call in the inspector has its own timeout of 3 s (**Requirement for M8-4:** `GitRunOptions` has no timeout option today; the runner's fixed 60 s default would let one slow call outlast the whole budget). One search at a time per session; a new one cancels the old; at most one search per second (429); a typed name needs at least 2 characters. A fixed skip list of heavy or private folders (`node_modules`, `.git`, `.cache`, `.npm`, `.Trash`, `Library` on macOS, and every other dot-folder). The walk does not cross a file system boundary: a directory whose `dev` differs from its root's is not entered (like `find -xdev`), which covers mounted volumes and network shares under a root. **Why a child process and not a `worker_threads` Worker:** a Worker shares the process's libuv threadpool (default 4 threads) with the dashboard's own fs, DNS and crypto work. A `stat` on a dead NFS mount can hold a threadpool thread indefinitely; `worker.terminate()` stops JavaScript but cannot free a thread blocked in a syscall, so four hung calls would freeze the dashboard. A child process has its own threadpool. It is started detached, so it leads its own process group, with an allowlisted environment, no token and no IPC beyond a JSON channel the server validates against a strict schema; on the hard deadline, on cancel, and on server shutdown the server sends `SIGKILL` to the whole group (`process.kill(-pid, "SIGKILL")`), which also ends the Git grandchildren. A process stuck in uninterruptible I/O on a dead mount survives `SIGKILL` until the call returns; the server is unaffected, but to avoid piling up, at most 2 such children may be outstanding and a further search answers `503 inspector_busy`. **Mount-trigger notes:** statting a path can itself trigger an automount (autofs, `/net`, `/home` on some Linux sites) or, on macOS, cross the firmlink between the read-only system volume and the Data volume; the `dev` rule keeps the walk from descending into such a mount, but the first `lstat` of the trigger can still block, which is why it runs in the child. UNC paths do not apply (Windows is not supported yet). |

## 3. API sketch

All routes are added to `API_ROUTES` (exact `"METHOD /path"` keys, so there are no path parameters; ids go in the query string or the body). All pass through the existing Host, Origin and token checks before the handler. All bodies are `application/json` of at most 16 KiB (the existing cap). Errors use the existing envelope `{ "error": { "code", "message" } }` with fixed, translatable messages.

**Fixed mode.** When the dashboard was started by `pgard dashboard` (`--project-root` given), the picker is hard-disabled: **every `/api/picker/*` route answers `409 fixed_project`** before reading the body, whatever the request (test in section 8).

**Routes with and without a project.** Needing a project (they answer `409 no_project` while none is selected): `POST /api/auth/verify`, `POST /api/auth/owner-approval`, `GET /api/ports`, `POST /api/ports/probe`, `POST /api/target/confirm`, `POST /api/scan`, `GET /api/reports/html`, `GET /api/reports/pdf`. Working without a project: `GET /api/session`, `GET /api/auth` (it reports the idle state and the stored sign-in), `POST /api/auth/sign-out`, `POST /api/auth/cancel` (**Requirement for M8-4**: new route, no project needed, no epoch), `GET /api/target`, `POST /api/target/clear`, `GET /api/scan`, `POST /api/scan/cancel`, `GET /api/rule-texts` and the picker routes, so the user can sign out and read texts before choosing.

Existing state-changing project routes gain `epoch` in the body: `POST /api/auth/verify`, `POST /api/auth/owner-approval`, `POST /api/ports/probe`, `POST /api/target/confirm`, `POST /api/scan` (**Requirement for M8-4**; a stale or missing epoch in picker mode answers `project_changed`, and in fixed mode the epoch is always 1 and not required).

```ts
interface Candidate {
  candidateId: string; // 22 chars [A-Za-z0-9_-], 128-bit random, server-held, valid 10 minutes
  name: string; // sanitized, <= 120
  displayPath: string; // real path, "~"-shortened, sanitized, <= 400
  displayPathEscaped: string | null; // set only when blocked as unsafe_display
  collision: { tag: string } | null; // same displayPath as another candidate; tag = 6 hex of the fingerprint
  shown: string; // fingerprint of the identity chain + owner/name; echoed back on confirm
  remote:
    | { status: "github"; repo: string } // "owner/name"
    | { status: "none" | "not_github" | "ambiguous" | "unreadable" };
  selectable: boolean;
  blocked: null | {
    code: PickerBlockCode;
    paths: string[]; // for write-bit / ownership blocks: every failing directory or file, "~"-shortened, sanitized (empty otherwise)
    reason: string; // fixed text (EN; the UI maps the code to EN/KO)
    fix: string; // fixed text
  };
  source: "scope" | "recent";
}

interface RecentEntry extends Candidate {
  entryId: string; // 22 chars [A-Za-z0-9_-], random, stored in the file
  lastUsedAt: string; // ISO time
}
```

`Candidate.remote.status` and `blocked` come from the shared local repository check plus the checks of T13. Only `owner/name` is returned for a github.com remote; no URL, no remote name.

**Ids, epochs and bounds.** `candidateId`, `searchId` and `entryId` have one fixed format (22 characters of `[A-Za-z0-9_-]`, 128-bit random from `crypto.randomBytes`); anything else is `400 bad_id` before any lookup. `projectEpoch` is a positive safe integer starting at 1; a request whose epoch is not a safe integer is `400 bad_request`. The candidate map holds at most 100 candidates (oldest dropped first, expired ones purged at every search) and at most 5 finished searches are kept.

## 4. Session and token binding

Reuse of the current mechanism, with no new credential:

- One token per server run, printed once in the URL fragment; the page keeps it in memory and sends it in `x-pgard-token`. Nothing in the picker is available without it, including candidate ids, search ids and the recent list.
- Candidate and search ids are random, only meaningful with the token (per-session server state, like `SessionState`), never stored on disk, and gone when the server stops (`clearSessionState`). Entry ids are random too but are stored in the recent file.
- The new state lives in `SessionState`: the selected project record (identity chain, `owner/name`, name), the current search, the candidate map and the `projectEpoch`. It is cleared by `clearSessionState` on shutdown, and the inspector child's process group is killed then too.
- Origin and Host rules are unchanged. The picker adds no cookie, no `localStorage` use for names or paths, and no second token.
- **Requirement for M8-4:** `ApiContext.projectRoot` becomes a value read from the session state (null until confirmed), captured per request as described in T12.
- **Requirement for M8-4:** `projectEpoch` increments on every confirm and clear, and the routes listed in section 3 carry it.
- The account binding is unchanged: the signed-in GitHub account is independent of the project. A project change resets the authorization record, so the next check runs from scratch.

`pgard web` (**Requirement for M8-4**, new command) needs an interactive terminal, like `pgard dashboard`: it prints the search scope roots (for the first run, the default folders that exist) and asks `Search these folders for projects? [y/N]` before starting the server (exit 2 without a terminal). It passes no path on the command line. It supports `--no-store` and `--no-browser` and `pgard web scope list | add <folder> | remove <folder>` (**Requirement for M8-4**). On Windows it exits with the usage error and points to `pgard dashboard`.

## 6. Storage format

Folder: the existing per-user app-data directory from `resolveStoreDirectory()` (`~/Library/Application Support/pgard` or `$XDG_DATA_HOME/pgard`, default `~/.local/share/pgard`), in a new subfolder `web/` so that deleting `repos/` stays safe and unrelated. Never inside a project. Protection follows the result store: `0700` folder and `0600` files, no symlink followed for the folder or the files, write to a temp file in the same folder (exclusive create) then rename, size cap before parsing, an unsupported or newer `schemaVersion` is ignored with a notice and never overwritten.

**Requirement for M8-4:** the safe-file code in `packages/result-store/src/store.ts` lives inside the store's factory closures and is not exported. Extract it into shared helpers (or add the two files as a module of `@pgard/result-store`) instead of re-implementing it.

`web/settings.json`:

```json
{
  "schemaVersion": "1.0",
  "searchRoots": [{ "path": "/Users/alice/code" }]
}
```

- `searchRoots[].path` is an absolute `realpath` at the time it was added. Re-validated at every launch (exists, directory, safe ownership and mode of T13, depth rule); an invalid root is dropped from the session and reported in the terminal.
- First run: the default development folders that exist are printed and, after the user confirms, written here. With `--no-store` they are not persisted and the question is asked at the next launch.
- Roots are changed only in the terminal: `pgard web scope list | add <folder> | remove <folder>`. `add` shows the real path and asks for confirmation; adding the home folder shows the warning about macOS permission prompts and iCloud downloads.
- Limits are constants, not settings.

`web/recent-projects.json`:

```json
{
  "schemaVersion": "1.0",
  "entries": [
    {
      "entryId": "Zk3dQ0r1nH5uV9xTt2aYpA",
      "path": "/Users/alice/code/shop",
      "repo": "alice/shop",
      "lastUsedAt": "2026-10-28T09:00:00Z"
    }
  ]
}
```

- At most 20 entries, newest first, one per `realpath`; **an entry expires 90 days after `lastUsedAt`** (same as stored results; expired entries are dropped when the file is read and written); written only after a successful **confirm** (not after a search, and not on later gate results).
- `repo` is a display hint only; the displayed owner/name always comes from a fresh read.
- Unlike scan results, it holds absolute paths. The README must list it as an exception. It is removed by `pgard history clear --all` (**Requirement for M8-4**: today that command clears only the result store's data), and it is not written when `--no-store` or `PGARD_NO_STORE=1` is set (the recent list is then empty in that session).

## 7. What is logged, and what is not

- **Server:** nothing per request, as today. No access log, no debug log. The terminal output stays the startup and stop lines. **The terminal does print paths where the user must confirm them:** the scope roots in the start prompt, and the outcome of `pgard web scope list | add | remove`. That is deliberate, it is the trusted channel, and those lines are not written to any file by PGARD.
- **Never written anywhere** (file, error text, crash message, telemetry, API errors): a searched or dropped folder name, a candidate path, a remote URL or remote name, a candidate or search id, the token. The two files in section 6 are the only places paths are stored, on purpose.
- **File-system and Git errors** are never forwarded as text: Node's `error.message` contains the path, and Git's stderr can contain the path and the remote. They are mapped to our own codes (`ENOENT`, `EACCES`, `ELOOP`, `ENAMETOOLONG`, `ENOTDIR`, timeout, others to `unreadable`) and then to a block code with a fixed message.
- **In memory only**, discarded on stop: the search, the candidate map, the selected project record, counters such as `visited`. The inspector child has no stdout or stderr (they are ignored), so nothing it prints can leak.
- **API errors** carry only fixed codes and fixed messages.
- **Not logged by the browser:** names and paths are not put in the URL, the title, `localStorage` or the console. The UI language preference is the only thing the page already stores.

## 8. Test plan for M8-4

Unit and integration (vitest, injected `ServerDeps` as the existing tests; no real GitHub, no real keychain). Where a test needs to fake `lstat`/`readdir` results (owner, mode bits, `dev`, `ino`), the inspector takes an **injectable fs object** (a small interface: `lstat`, `readdir`, `realpath`), not a global stub.

1. **Middleware reuse.** Each picker route rejects: no token, wrong token, wrong `Host` (including `localhost` and a rebound name), foreign `Origin`, missing `Origin` on POST, `Sec-Fetch-Site: cross-site`, wrong content type, body over 16 KiB. No CORS header on any response, including errors.
2. **Fixed mode (M1).** Started as `pgard dashboard` (a `--project-root`): every `/api/picker/*` route, with every method and with valid, invalid and empty bodies, answers `409 fixed_project`, and nothing was searched or selected.
3. **Name validation.** Table of bad names with the exact `bad_name` message (says why and what to do): empty, one character when typed, `.`, `..`, `a/b`, NUL, control and bidirectional characters, 256 units, lone surrogates. NFC and NFD of the same name match the same directory. Case folding is locale independent: with the process locale set to Turkish, `I` still matches only `i` (as `toLowerCase()` defines), never `ı`.
4. **Walk.** Fixture trees in a temp directory: depth limit, entry limits, deadline (injected clock) giving `partial` with `stoppedAfterSeconds` and `not_inspected` cards for what was found but not inspected (nothing dropped silently), skip list, no nested search inside a found repository, symlink to a repository outside the scope not offered, symlink loop, a different `dev` (injected fs) not entered.
5. **Hung threadpool (M2).** In a child, open a FIFO (`mkfifo`, no writer) with `fs.open` four or more times, so every libuv threadpool thread of the child is blocked. While they are blocked, the dashboard server must still answer real fs work within one second: the test times a genuine `fs.promises.stat` in the main process, or calls a test-only route that does fs work. `GET /api/session` is not used for this: it reads the stored sign-in through an injected credential store and the keychain, so it proves nothing about the threadpool. At the hard deadline the child's whole process group is gone (check the pids; `kill -0` fails), the search answers `partial` or `failed`, and a new search works. Also: with two stuck children simulated, the third search answers `503 inspector_busy`. The same test is run once with the work inside a `worker_threads` Worker as a documented control that shows the server freezing, so the reason for the child process stays proven.
6. **Hung mount during revalidation (M3).** A recent-list entry whose path is on a blocked FIFO or an injected never-returning `lstat`: `GET /api/picker/recent` answers quickly with `validating: true`, the entry becomes `unreadable` after the budget, other entries still validate, a second call within 1 s does not start another revalidation, and a call within 30 s uses the cache. Git calls have the 3 s limit (an injected runner that never returns).
7. **Case-insensitive file systems.** On the `macos-latest` check job: name `Shop` finds `shop` (APFS case-insensitive default); NFC and NFD names. On `ubuntu-latest` (case-sensitive): `Shop` and `shop` as two directories both match and both are offered. **Containment by identity (M5):** a look-alike directory `Code` next to the real scope root `code` on a case-sensitive volume, and a directory reached through a symlinked ancestor, are not accepted, because the recorded `dev`/`ino` chain does not match, whatever the strings say.
8. **Ownership and write bits (M6).** With the injected fs: a candidate whose parent chain contains a directory owned by another uid, a group-writable ancestor, a world-writable ancestor, a group-writable `.git`, a group-writable `.git/config`, several failing paths at once (one message, one `chmod go-w a b c`), and a `.git` that is a file (gitdir pointer, linked worktree, submodule layout): each is blocked with the exact code and fixed message, and the message lists every failing directory and file (including `.git/config`) in one exact `chmod go-w a b c` fix. A `commondir` that points outside the project is blocked `git_dir_unsupported`.
9. **Candidate checks.** For each remote block code, a fixture repository: no remote, `https://example.com/o/r.git`, GitHub Enterprise host, two remotes to different repos, a remote URL with embedded credentials and a remote whose name is hostile (the response must contain neither the credential, the URL nor the remote's name), no commits, alternates, and a hostile `.git/config` with `core.fsmonitor`, hooks and `core.sshCommand` that must never run (a marker file must not appear).
10. **TOCTOU (T7).** After a search: rename the directory, replace it with a symlink, replace it with a different repository, change its remote, wait past 10 minutes (injected clock, also a clock moved back): each gives `candidate_changed` or `candidate_expired` and selects nothing. Between confirm and `POST /api/scan`, swap the directory: the scan is refused. `expectedRepo`: a fake gate that returns another `owner/name` makes `runScan`, `verifyProject` and `recheckOwnerApproval` stop with the blocked status and the fixed reason, and no analysis runs (unit tests in `scan-core` and `policy`).
11. **State reset and in-flight work (M7).** Confirm a second project: authorization, target, probe, scan and report are cleared; the old report download returns `409`; a stale `epoch` returns `project_changed`; routes return `no_project` before the first confirm. Confirm during a running scan returns `scan_running`; confirm during a running verify or owner-approval re-check returns `auth_running`. **Cancel check:** with a verify waiting for the device sign-in (fake provider that never resolves), `POST /api/auth/cancel` aborts the sign-in, resets the authorization to idle, and a following confirm succeeds instead of `auth_running`; calling it with nothing running is a 200 no-op. For each async handler (`startVerify`, `recheckOwnerApproval`, `probePort`, `confirmTarget`, `startScan`, report rendering, search completion): start it with a deferred dependency, change the project (through a direct state change in the test), then release the dependency: the handler answers `project_changed` or discards its result, and nothing from it is visible under the new project.
12. **Idempotency, ids and bounds.** Confirming the already selected candidate twice succeeds twice with the same project; removing an unknown `entryId` is a 200 no-op; cancelling an unknown search is a 200 no-op; malformed ids are `bad_id`; a non-integer or huge epoch is `bad_request`; the candidate map never exceeds 100 entries and kept searches 5. `scope/toggle` works with no `epoch`.
