# Security design: authorization in CI (GitHub Actions)

> [한국어](CI_AUTHORIZATION_DESIGN.ko.md) translation available. This English file is the reference; the translation follows it.

Status: design for review ([#405](https://github.com/JadenMeister/pgard/issues/405), M10-2). Nothing in this document is implemented. M10-3 implements it only after the owner has approved it. Back to the [README](../README.md) and the [documents index](README.md).

Statements about "today" describe the code at the time of writing (`packages/policy/src/authorize-project.ts`, `packages/policy/src/checks.ts`, `packages/policy/src/types.ts`, `packages/github-auth`, `packages/git-history`). Where this design relies on something the code does not have yet, it is marked **Requirement for M10-3**. Statements about GitHub are taken from GitHub's documentation, linked inline and listed in [References](#12-references); where the documentation is silent, the design says so and does not rely on the behaviour.

## 1. Goals and non-goals

### Goals

1. A scan in a GitHub Actions job proves **the same five checks** that a local scan proves (repository, GitHub identity, owner approval, current access, contribution), with the same check ids, order and statuses, without a browser sign-in.
2. Each check is proved with evidence **at least as strong** as the local evidence. Where CI cannot produce such evidence, the check is `failed` or `unverifiable` with a reason, and the scan is blocked (exit code 3).
3. There is **no CI mode that skips, relaxes or caches checks**. CI only changes where the evidence for `github_identity` comes from, and which account the later checks are evaluated for. `authorizeProject` stays the single gate and `isAuthorizationAllowed` stays unchanged.
4. Running "as CI" outside GitHub Actions never authorizes anything. Environment variables such as `GITHUB_ACTIONS`, `GITHUB_REPOSITORY` or `GITHUB_ACTOR` are never evidence.
5. Code, history and results stay on the runner. Network traffic stays limited to GitHub (`api.github.com` and the Actions token service `token.actions.githubusercontent.com`).

### Non-goals

- No implementation in M10-2, and no change to the local device-flow path.
- No scanning of pull request code in CI (see [U2](#8-what-remains-unprovable-and-is-therefore-blocked)). A separate design is needed for that.
- No support for other CI systems or for GitHub Enterprise Server (see [section 9](#9-out-of-scope)).
- No defence against a modified `pgard` binary. PGARD is becoming open source; anyone can build a copy without the gate, exactly as on a laptop today. The gate protects users of the real `pgard`, and the people whose repositories it is pointed at, from scans that are not authorized. This design keeps that property in CI and does not try to do more.

Two properties matter for CI:

- The **subject** of checks 3 to 5 is the signed-in person. Everything that makes the checks meaningful (owner, org owner, collaborator, contributor) is a statement about that person's GitHub account id.
- Checks 3 to 5 need the GitHub API. Nothing in today's gate can be proved offline except check 1.

## 3. What changes in CI

In a CI job there is no person at a terminal, so there is no device flow. Something must take the place of "the signed-in person", and checks 3 to 5 must be evaluated for that subject, with the same rules.

This design separates two kinds of input:

- **Identity**: who the subject is. It must be signed by GitHub and bound to this job and this process, so it cannot be copied, replayed or produced outside GitHub.
- **Facts**: what GitHub says about repositories, installations, memberships, pull requests and commits. A fact read from `api.github.com` over TLS is true no matter which token was used to read it, provided the token could read it at all. So the provenance of a read-only token matters for _whether_ a fact can be read, never for _what_ it says.

Only a GitHub-signed OIDC token gives an identity in CI (section 4). Tokens that only read facts may come from anywhere, but they are never identity.

## 4. CI identity options

For each option: how it maps to each check, how it could be spoofed, and whether it can be verified offline.

### A. GitHub Actions OIDC token (`id-token: write`)

A step in a job with `permissions: id-token: write` can ask GitHub's OIDC provider for a JWT, using the runner variables `ACTIONS_ID_TOKEN_REQUEST_URL` and `ACTIONS_ID_TOKEN_REQUEST_TOKEN` and an `audience` query parameter of its choice ([OIDC reference](https://docs.github.com/en/actions/reference/security/oidc), [workflow syntax: `permissions`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)). The token is signed with RS256 by the issuer `https://token.actions.githubusercontent.com`, whose keys are published at the `jwks_uri` of its [OpenID configuration](https://token.actions.githubusercontent.com/.well-known/openid-configuration) ([JWKS](https://token.actions.githubusercontent.com/.well-known/jwks)). The configuration lists these claims: `sub`, `aud`, `exp`, `iat`, `iss`, `jti`, `nbf`, `ref`, `sha`, `repository`, `repository_id`, `repository_owner`, `repository_owner_id`, `enterprise`, `enterprise_id`, `run_id`, `run_number`, `run_attempt`, `actor`, `actor_id`, `workflow`, `workflow_ref`, `workflow_sha`, `head_ref`, `base_ref`, `event_name`, `ref_type`, `ref_protected`, `environment`, `environment_node_id`, `job_workflow_ref`, `job_workflow_sha`, `repository_visibility`, `runner_environment`, `issuer_scope`, `check_run_id`.

Relevant documented semantics:

- `actor` / `actor_id`: the account that initiated the run. For a re-run, GitHub's [contexts reference](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts) says `github.actor` stays the user of the _initial_ run, the re-run uses that user's privileges, and the person who started the re-run is `github.triggering_actor`. The OIDC claims list has no `triggering_actor`.
- `job_workflow_ref` / `job_workflow_sha`: present when the job uses a reusable workflow; they name the called workflow file and its commit. The other claims (`repository`, `ref`, `workflow`, ...) describe the **caller** ([OIDC with reusable workflows](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-with-reusable-workflows)).
- `runner_environment`: `github-hosted` or `self-hosted`.
- `sub`: its format depends on the event, on environments, on customised templates, and, for repositories created (or renamed or transferred) after 15 July 2026, on an immutable format with owner and repository ids ([OIDC reference](https://docs.github.com/en/actions/reference/security/oidc)). This design therefore **never parses `sub`** and checks individual claims instead.
- Lifetime: the token is "only valid for a single job" ([OIDC concepts](https://docs.github.com/en/actions/concepts/security/openid-connect)); GitHub documents no fixed lifetime, so the design reads `exp` and adds its own freshness limit.

### B. `GITHUB_TOKEN`

"The `GITHUB_TOKEN` secret is a GitHub App installation access token", created per job, limited to the repository that contains the workflow, expiring when the job ends or after at most 6 hours on GitHub-hosted runners (24 hours on self-hosted) ([`GITHUB_TOKEN`](https://docs.github.com/en/actions/concepts/security/github_token)). Its permissions are set with `permissions:`; for pull request events from forks, other than `pull_request_target`, write permissions become read-only unless the repository enables sending write tokens; `pull_request_target` gets read/write even from a public fork ([workflow syntax: `permissions`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)).

| Check             | Mapping                                                                                                                                                            | How it could be spoofed                                                                                                                                                             | Offline?          |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- |
| `repository`      | Can read `GET /repos/{owner}/{repo}` (id, owner id and type, default branch) for this repository: facts, not binding.                                              | It is an opaque string in an environment variable. A personal access token, another repository's `GITHUB_TOKEN`, or any other token can be put in the same variable outside GitHub. | No (opaque token) |
| `github_identity` | None. It represents the GitHub Actions App installation, not a person; it says nothing about who triggered the run.                                                | n/a                                                                                                                                                                                 | No                |
| `owner_approval`  | None. It cannot list another App's installations or read organization memberships (`members` is not a `GITHUB_TOKEN` permission scope).                            | n/a                                                                                                                                                                                 | No                |
| `current_access`  | None for a person: `permissions` in `GET /repos` describe the token, not the actor.                                                                                | n/a                                                                                                                                                                                 | No                |
| `contribution`    | Can read the facts the existing rule needs for this repository (`compare`, PRs for a commit, commit verification) with `contents: read` and `pull-requests: read`. | Facts only (section 3); safe to read with any token that can read them.                                                                                                             | No                |

Conclusion: usable as a **fact reader** for this repository, never as identity or approval.

### C. A GitHub App installation token handed to `pgard`

An installation token is created by `POST /app/installations/{installation_id}/access_tokens` with a JWT of the App, "will expire after 1 hour", is attributed to the App, and can be narrowed to repositories and permissions the installation already has ([authenticating as an installation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation)). The endpoint `GET /repos/{owner}/{repo}/installation`, which returns `app_id`, `account` and `repository_selection`, requires the App's JWT, and the token-creation response contains no `app_id` or `account` ([Apps REST API](https://docs.github.com/en/rest/apps/apps)).

Two variants:

- **C1. A ready-made installation token** (for example from an action that mints it earlier in the job). `pgard` cannot tell which App issued it: no installation-token call it may make returns the App id. A token of any App installed on the owner account (or on a repository the attacker controls) would look the same. Owner approval cannot be shown to be about the configured App. **Rejected as approval evidence**; acceptable as a fact reader.
- **C2. App credentials given to `pgard` (App id and private key).** `pgard` signs the App JWT itself, calls `GET /repos/{owner}/{repo}/installation`, checks `app_id` and the installation account, then mints a short installation token for this repository only, with read-only permissions. This proves the installation **of that App** on the owner account, which is today's owner-approval evidence.

For an organization, plus the subject's membership via the installation token (`GET /orgs/{org}/memberships/{username}`, `state`, `role`) ([members API](https://docs.github.com/en/rest/orgs/members)). | Whoever holds the private key can mint tokens for every installation of that App. A key in repository secrets is readable by every workflow that can read those secrets. | `contribution`    | Facts with the installation token.                                                                                                                                                                                                                                                                                                                            | Facts.                                                                                                                                                                                                                                                                                                                                                                                             | No       |

The built-in PGARD App's private key is held by its maintainer and is never shipped or shared. So C2 is available only for an App whose key the repository owner holds: a self-registered App, which is the same case as today's `PGARD_GITHUB_APP_CLIENT_ID` override. See [open question Q1](#11-open-questions-for-the-owner).

### D. A saved user-to-server token (device flow done once, token stored as a CI secret)

All five checks would run exactly as today, but:

- the identity is the account that once signed in, not whoever caused this run: anyone who can run a workflow that reads the secret scans _as the owner_, so owner approval and the owner exemption would be granted to code the owner never saw;
- the token is long-lived (8-hour access tokens with 6-month refresh tokens, or no expiry at all, depending on the App's settings), and refreshing would have to write a new secret back;
- it contradicts today's rule that the token is never put in environment variables;
- it cannot be verified offline and cannot be bound to the job.

**Rejected.** A personal access token is the same or worse (it is not even tied to the PGARD App) and is **rejected** for the same reasons.

### E. Unsigned job metadata (`GITHUB_ACTIONS`, `GITHUB_REPOSITORY`, `GITHUB_ACTOR`, `GITHUB_SHA`, event payload file)

Anyone can set them, on any machine. **Never evidence**, not even as a hint that changes a check result.

## 5. Offline versus online verification, and JWKS

**Verifiable offline** (no network, once the signing keys are known): the JWT structure; `alg` = `RS256`; the RS256 signature over the header and payload with the key named by `kid`; `iss`; `aud`; `exp`, `nbf`, `iat`; and every claim comparison that needs only local data: `repository` against the verified remote, `sha` against local `HEAD`, `job_workflow_ref` / `job_workflow_sha` against the values built into `pgard`, `runner_environment`, `event_name`, `ref_type`, `run_attempt`, and `actor_id == repository_owner_id`.

**Needs the GitHub API**: the signing keys themselves (JWKS fetch); that `repository_id`, `repository_owner_id` and the default branch match what GitHub reports now; that the actor is a `User` account (`GET /users/{actor}`, id must equal `actor_id`); the App installation (C2); organization membership; collaborator permission; all contribution facts. Since checks 3 to 5 always need the API, **an offline CI authorization can never be `allowed`**. There is no offline mode.

**JWKS fetching and pinning** (**Requirement for M10-3**):

- The issuer `https://token.actions.githubusercontent.com` and the JWKS URL `https://token.actions.githubusercontent.com/.well-known/jwks` are constants in `pgard`. The OpenID configuration document is **not** fetched at run time, so a changed or spoofed discovery document cannot move the key source. A change of `jwks_uri` by GitHub needs a `pgard` release.
- The JWKS is fetched over HTTPS once per authorization, with no redirects followed, a short timeout and a size cap, using the same hardened fetch as the GitHub client. Only keys with `kty: RSA`, `alg: RS256` (or absent `alg`) and `use: sig` (or absent `use`) are accepted; at least 2048-bit moduli.
- The JWKS is kept in memory for that one authorization only and never written to disk. It is not an authorization result, but caching it would add a second trust store to keep fresh, and the run is online anyway.
- No key snapshot is shipped as a trust anchor: a snapshot would keep accepting a key that GitHub has rotated out. (Shipping one only for tests is fine.)
- Unknown `kid` after the fetch, a fetch failure, or a malformed JWKS: `github_identity` is `unverifiable` with the reason. Never a fallback to another key or to the device flow.

## 6. Threat model

Assets: the authorization decision; the App private key (C2); the OIDC token and the installation token while the job runs; the scanned code and results on the runner.

Trust boundaries: GitHub's token service and API (trusted for signatures and facts); the pinned reusable workflow and the `pgard` build it installs (trusted, fixed by commit); the caller workflow in the scanned repository (untrusted: anyone with write access to its branch can change it); the event payload and every environment variable (untrusted); the runner machine (trusted only when GitHub-hosted).

| T10 | **Bot or App actor** (Dependabot, `github-actions[bot]`, another App) triggers the run.                                                                                                                                                                                                                                                                                         | `GET /users/{actor}` must return `type: User` and `id == actor_id`. A stolen key still cannot make checks pass for a subject who is not owner, collaborator or contributor, because checks 3 to 5 are evaluated for the OIDC actor.                                                                                                                                  |
| T12 | **Renamed or transferred repository, or remote case differences**.                                                                                                                                                                                                                                                                                                              | `repository_id` and `repository_owner_id` (numbers) are compared with `GET /repos`; names are compared exactly as today (an org name that differs only in case is `unverifiable`).                                                                                                                                                                                                                                                                                                                                                                                            |
| T13 | **Working tree changed after checkout** (an earlier step edits files).                                                                                                                                                                                                                                                                                                          | The scan job has no earlier caller steps (T5). `pgard` additionally requires a clean working tree in CI (`git status --porcelain` empty, **Requirement for M10-3**), because, as today, the checks do not prove that the working tree matches `HEAD`.                                                                                                                                                                                                                                                                                                                         |
| T14 | **Enterprise-specific issuer or GitHub Enterprise Server**: different `iss`, keys and API host.                                                                                                                                                                                                                                                                                 | `iss` must equal the github.com issuer exactly. Anything else is `unverifiable` ([section 9](#9-out-of-scope), Q8).                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

## 7. Recommended design

### 7.1 Overview

1. **Identity** comes only from an Actions OIDC token that `pgard` requests itself, inside the job, with a fresh nonce audience, and verifies against GitHub's JWKS (option A).
2. The **job is fixed**: the token is accepted only from a job that runs PGARD's own reusable workflow, pinned to the exact commit the running `pgard` was built from, on a GitHub-hosted runner, for a `push` or `workflow_dispatch` on the default branch, on the first attempt.
3. The **subject** of checks 3 to 5 is the OIDC actor (`actor_id`, a `User`). The existing check functions run unchanged with that subject in place of the signed-in user.
4. **Owner approval** needs App evidence of the same strength as today: option C2 (App id and private key of the configured App, held by the repository owner). Without it, owner approval is `unverifiable` and the scan is blocked. For the built-in PGARD App this is the case today (Q1).
5. **Facts** are read with the C2 installation token, or with `GITHUB_TOKEN` (option B) where C2 is absent, so that every check still reports its own reason.
6. The CI evidence provider is chosen explicitly (proposed: `--identity github-actions`, Q7). Without it, nothing changes: no terminal and no saved sign-in still blocks with "Not signed in". With it, there is no fallback to the keychain or the device flow.

### 7.2 Workflow shape

The scanned repository calls PGARD's reusable workflow; it cannot add steps to that job.

```yaml
# .github/workflows/pgard.yml in the scanned repository (caller)
on:
  push:
    branches: [main]
  workflow_dispatch:
permissions:
  contents: read
  id-token: write
jobs:
  scan:
    uses: JadenMeister/pgard/.github/workflows/ci-scan.yml@<40-hex release commit>
    with:
      app-id: "123456" # digits only; the configured App (C2)
    secrets:
      PGARD_APP_PRIVATE_KEY: ${{ secrets.PGARD_APP_PRIVATE_KEY }}
```

The reusable workflow (in this repository, **Requirement for M10-3**): `runs-on` a GitHub-hosted image; `actions/checkout` pinned by SHA with `persist-credentials: false` and `fetch-depth: 30` (enough for the contribution candidates); `actions/setup-node` pinned by SHA; installs exactly the `pgard` version built from this commit, with integrity and provenance checked; runs `pgard scan --identity github-actions --format sarif` (or json). No step prints or exports the token request variables, and no input reaches a shell unvalidated.

### 7.3 Exact checks on the OIDC token

All comparisons are exact, case-sensitive string comparisons unless stated. A claim that is missing, has the wrong JSON type, or is duplicated makes `github_identity` `unverifiable` with the claim name in the reason (never its value when the value could be sensitive). Numeric claims are decimal strings in GitHub's tokens; anything else is refused.

| Claim / field                                                                                                        | Required value                                                                                                                                     | Source of the expected value    |
| -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| header `alg`                                                                                                         | `RS256` (`none`, `HS*` and everything else refused)                                                                                                | constant                        |
| header `kid`                                                                                                         | present, matches exactly one key in the fetched JWKS                                                                                               | JWKS (section 5)                |
| signature                                                                                                            | valid RS256 over `header.payload` with that key                                                                                                    | JWKS                            |
| `iss`                                                                                                                | `https://token.actions.githubusercontent.com`                                                                                                      | constant                        |
| `aud`                                                                                                                | `pgard-ci:v1:<nonce>`; if an array, exactly one element, equal to it                                                                               | nonce generated in this process |
| `iat`                                                                                                                | within ±60 s of the local clock                                                                                                                    | clock                           |
| `nbf`                                                                                                                | ≤ now + 60 s                                                                                                                                       | clock                           |
| `exp`                                                                                                                | > now, and `exp − iat` ≤ 3600 s                                                                                                                    | clock                           |
| `runner_environment`                                                                                                 | `github-hosted`                                                                                                                                    | constant                        |
| `event_name`                                                                                                         | `push` or `workflow_dispatch`                                                                                                                      | constant allowlist              |
| `ref_type`                                                                                                           | `branch`                                                                                                                                           | constant                        |
| `ref`                                                                                                                | `refs/heads/` + the default branch GitHub reports in this run                                                                                      | `GET /repos` (online)           |
| `run_attempt`                                                                                                        | `1`                                                                                                                                                | constant (Q2)                   |
| `repository`                                                                                                         | `owner/name` of the verified remote, and equal to GitHub's `full_name`                                                                             | local remote, `GET /repos`      |
| `repository_id`                                                                                                      | equal to GitHub's repository `id`                                                                                                                  | `GET /repos`                    |
| `repository_owner` / `repository_owner_id`                                                                           | equal to GitHub's `owner.login` / `owner.id`                                                                                                       | `GET /repos`                    |
| `sha`                                                                                                                | 40 hex, equal to local `HEAD` (which must be the checkout of that commit, with a clean working tree)                                               | local Git                       |
| `job_workflow_ref`                                                                                                   | `JadenMeister/pgard/.github/workflows/ci-scan.yml@<BUILD_SHA>`                                                                                     | built into the release          |
| `job_workflow_sha`                                                                                                   | `<BUILD_SHA>`                                                                                                                                      | built into the release          |
| `actor_id` / `actor`                                                                                                 | decimal / non-empty; `GET /users/{actor}` returns `type: User` and `id == actor_id`                                                                | `GET /users/{actor}` (online)   |
| `sub`, `workflow`, `workflow_ref`, `workflow_sha`, `run_id`, `environment`, `ref_protected`, `repository_visibility` | not used for the decision. `workflow_ref` and `run_id` are named in the `github_identity` reason so the run can be traced. `ref_protected` see Q4. | n/a                             |

The token request itself: `pgard` reads `ACTIONS_ID_TOKEN_REQUEST_URL` and `ACTIONS_ID_TOKEN_REQUEST_TOKEN`, requires the URL to be HTTPS, appends `audience=pgard-ci:v1:<nonce>`, and never logs either variable or the token. A request URL controlled by an attacker can at worst return a token, which must then pass every check above.

### 7.4 The five checks in CI

| Check             | In CI                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `repository`      | `verifyRepository` unchanged. In addition (**Requirement for M10-3**): the working tree is clean, and the remote's `owner/name` equals the OIDC `repository`. (`HEAD == sha` is checked with the token in `github_identity`, because the token is only requested after the local check passes, keeping today's order.)                                                                                                                                                                                                                                                                                                                                                                 |
| `github_identity` | Request and verify the OIDC token (7.3). Passed reason, for example: "GitHub Actions run 123 (attempt 1) of `owner/repo` on `refs/heads/main`, triggered by `alice` (OIDC token verified)." The subject is `{ id: actor_id, login: actor }`, confirmed as a `User`.                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `current_access`  | Read the repository (`GET /repos`) with the fact token. 404 or no read: as today. Then, for the subject: personal owner (`actor_id == owner.id`): passed; organization owner (an active `admin` membership of the subject, read once with the C2 installation token and reused by owner approval in the same run): passed; anyone else: `GET /repos/{owner}/{repo}/collaborators/{actor}/permission` must be `read`, `write` or `admin`. If no available token can read that permission, `unverifiable`. The `permissions` object of `GET /repos` is **never** used in CI, because it describes the token, not the subject.                                                            |
| `owner_approval`  | C2 present: JWT of the configured App, `GET /repos/{owner}/{repo}/installation`; `app_id` = configured App id, `account.id` = `owner.id`, `target_type` = owner type; mint an installation token restricted to this repository with read-only permissions; the repository is included. Organization: plus `GET /orgs/{org}/memberships/{actor}` with `state: active`, `role: admin`, `user.id == actor_id`, `organization.id == owner.id`. The same `OwnerEvidence` is produced (with `userId = actor_id`). C2 absent: `unverifiable`, "CI cannot prove that the repository owner approved PGARD: provide the App id and private key of the configured GitHub App (see the CI guide)." |
| `contribution`    | `verifyContribution` unchanged with `user = subject`, the local candidates (up to 30 with `fetch-depth: 30`), the fact token, and `ownerEvidence` from this run's owner approval only.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

The gate code changes only at the identity step (**Requirement for M10-3**): `getGitHubSession` becomes one of two providers, the device flow or GitHub Actions OIDC, each returning a subject and a client for facts; and `verifyCurrentAccess` gets a subject-based variant for CI. `AUTHORIZATION_CHECK_ORDER`, `isAuthorizationAllowed` and the "never cached" rule do not change.

## 8. What remains unprovable and is therefore blocked

| #   | Situation                                                                              | Why it cannot be proved                                                                                                          | Result                                                            |
| --- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| U1  | Owner approval with the built-in PGARD App (no private key available to the job)       | Only the App's JWT reveals which App an installation belongs to; the key is the maintainer's and is never shared.                | `owner_approval` `unverifiable` (Q1)                              |
| U2  | Pull request code (`pull_request`, `pull_request_target`)                              | Untrusted code; the commit is not on the default branch; fork runs get no write permission; the actor did not ask for a scan.    | `github_identity` `failed` (event not allowed)                    |
| U3  | `workflow_run`, `schedule`, `issue_comment`, `repository_dispatch` and any other event | The token does not carry the chain's provenance; for `schedule` the meaning of `actor` is not documented in the token reference. | `github_identity` `failed` (event not allowed; Q3 for `schedule`) |
| U4  | Self-hosted runners                                                                    | The runner's operator controls the token request, the binary and the checkout; nothing on the machine can prove otherwise.       | `github_identity` `failed`                                        |
| U5  | Re-runs (`run_attempt > 1`)                                                            | The person who started the re-run (`triggering_actor`) is not in the token.                                                      | `github_identity` `failed` (Q2)                                   |
| U6  | Bot or App actors                                                                      | No person to evaluate.                                                                                                           | `github_identity` `failed`                                        |
| U7  | A job that is not the pinned reusable workflow (inline steps, other versions)          | Earlier steps could mint and relay tokens or change the code.                                                                    | `github_identity` `failed`                                        |
| U8  | Collaborator's current access when no available token may read collaborator permission | The documentation does not state the required permission.                                                                        | `current_access` `unverifiable`                                   |
| U9  | GitHub Enterprise Server, enterprise-specific issuers, other CI systems                | Different issuer, keys or API; out of scope.                                                                                     | `github_identity` `unverifiable`                                  |
| U10 | That the working tree equals what GitHub has                                           | As today: the checks bind `HEAD`, not every file. CI adds the clean-tree requirement only.                                       | Documented limit, same as local                                   |

Every one of these blocks with exit code 3 and a reason that names the fix where one exists.

## 9. Out of scope

- **Other CI systems** (GitLab CI, Jenkins, CircleCI, Buildkite, Azure Pipelines, ...). Owner approval in PGARD is an installation of a GitHub App on the GitHub account that owns the repository, and only GitHub can attest that. A GitLab CI OIDC token attests a GitLab project and pipeline, not a GitHub repository or a GitHub user, and nothing links the two (a mirror can point anywhere). Jenkins has no platform-signed job identity at all. Each system would need its own issuer, claims, threat model and mapping to a GitHub account, so it needs its own design. Until then `--identity` accepts only `github-actions`, and these systems remain where they are today: blocked without a terminal and a saved sign-in.
- **GitHub Enterprise Server and enterprise-specific issuers** (Q8): another issuer, key set and API host.
- **Scanning pull requests in CI** (U2): needs its own design.
- **Uploading results** (for example SARIF to code scanning): unchanged; a blocked scan still produces a blocked document, as the README already says.

## 10. Requirements for M10-3 and test plan

Requirements named in this document, in one list: the `--identity github-actions` provider (name per Q7) with no fallback; the OIDC request with a per-process nonce audience; JWT verification with pinned issuer and JWKS URL, in-memory JWKS only; the exact claim table of 7.3; the build commit (`BUILD_SHA`) built into each release, and a release pipeline that builds the package from that commit with provenance; the reusable workflow `ci-scan.yml`; the clean-working-tree check in CI; a subject-based `current_access` for CI; C2 owner approval (App JWT, installation lookup, restricted read-only installation token, revocation, key hygiene); README and CLI help for CI, including what is blocked and why.

Tests (no real GitHub calls; tokens signed by a test key served as a fake JWKS):

- each row of 7.3 mutated one at a time (wrong `iss`, `aud`, expired, future `iat`, `alg: none`, `HS256` with the public key as secret, unknown `kid`, `self-hosted`, `pull_request`, `pull_request_target`, `workflow_run`, `run_attempt: "2"`, `ref` on another branch, `sha` ≠ `HEAD`, `job_workflow_sha` of another commit, `job_workflow_ref` from another repository, missing claim, numeric instead of string) blocks with the expected reason;
- a token with another process's nonce (replay) blocks;
- `GITHUB_ACTIONS=true` with no request variables, and request variables pointing to a server that returns a validly signed token for another repository, both block;
- bot actor blocks; personal owner, organization owner, collaborator with and without contribution behave as in the local tests;
- without C2, `owner_approval` is `unverifiable` and the others still report their own reasons;
- JWKS fetch failure, redirect, oversized body: `unverifiable`, no fallback;
- `isAuthorizationAllowed` and the five-check order are unchanged (existing tests keep passing).

## 11. Open questions for the owner

1. **Q1. Owner-approval evidence for CI.** With the built-in PGARD App, owner approval cannot be proved in CI (U1). Options: (a) **C2 with a self-registered App** whose key the repository owner holds, in an environment secret (the recommendation; same trust as today's `PGARD_GITHUB_APP_CLIENT_ID` override: which App is configurable, its installation on the owner account is the evidence); (b) a maintainer-run service that holds the built-in App's key, verifies the OIDC token and answers the installation question; this breaks "scans contact GitHub only" and adds a service to operate; (c) a new kind of evidence, such as an owner-signed policy file on the default branch; this is a policy change, needs its own review, and organization ownership could still not be read with `GITHUB_TOKEN`. Is (a) acceptable, and should the built-in App stay blocked in CI until (b) or (c) is decided?
2. **Q2. Re-runs.** Block every `run_attempt > 1` (recommended, because the re-runner is unknown), or accept re-runs and document that the subject is the first attempt's actor?
3. **Q3. `schedule`.** Allow scheduled scans? The token reference does not document who `actor` is for a scheduled run. Recommended: blocked until it is documented.
4. **Q4. `ref_protected`.** Require `ref_protected == "true"` (branch protection or rulesets on the default branch)? It is stricter than local, where no protection is required. Recommended: not required, but named in the reason.
5. **Q5. Pull request scanning.** Should a separate design for scanning PR code in CI be planned (with fork handling and a different contribution model), or is CI limited to the default branch?
6. **Q6. Self-hosted runners.** Blocked permanently (recommended), or should an owner-declared exception be designed, knowing that it cannot be proved?
7. **Q7. How CI is selected.** A flag (`--identity github-actions`), an environment variable (`PGARD_IDENTITY=github-actions`), or both? Recommended: the flag, never auto-detected.
8. **Q8. GitHub Enterprise.** Is ghe.com or GitHub Enterprise Server in scope later? It needs another issuer and API host.
9. **Q9. App key in an environment variable.** C2 needs the private key in the job, normally as an environment variable from a secret. Is that acceptable next to today's rule that a user token is never put in environment variables (the key is an App credential, not a user token), or should `pgard` read it only from a file path?
10. **Q10. Release coupling.** Accept exactly one `job_workflow_sha` per release (recommended; users must update the pinned SHA together with the version), or a published list of accepted SHAs, which needs its own integrity story?
