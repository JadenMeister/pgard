# Security design: authorization in CI (GitHub Actions)

> [한국어](CI_AUTHORIZATION_DESIGN.ko.md) translation available. This English file is the reference; the translation follows it.

Status: design for review ([#405](https://github.com/JadenMeister/pgard/issues/405), M10-2). Nothing in this document is implemented. M10-3 implements it only after the owner has approved it. Back to the [README](../README.md) and the [documents index](README.md).

Statements about "today" describe the code at the time of writing (`packages/policy/src/authorize-project.ts`, `packages/policy/src/checks.ts`, `packages/policy/src/types.ts`, `packages/github-auth`, `packages/git-history`). Where this design relies on something the code does not have yet, it is marked **Requirement for M10-3**. Statements about GitHub are taken from GitHub's documentation, linked inline and listed in [References](#12-references); where the documentation is silent, the design says so and does not rely on the behaviour.

## 1. Goals and non-goals

### Goals

1. A scan in a GitHub Actions job proves **the same five checks** that a local scan proves (repository, GitHub identity, owner approval, current access, contribution), with the same check ids, order and statuses, without a browser sign-in.
2. Each check is proved with evidence **at least as strong** as the local evidence. Where CI cannot produce such evidence, the check is `failed` or `unverifiable` with a reason, and the scan is blocked (exit code 3).
3. There is **no CI mode that skips, relaxes or caches checks**. CI only changes where the evidence for `github_identity` comes from, and which account the later checks are evaluated for. `authorizeProject` stays the single gate and `isAuthorizationAllowed` stays unchanged.
4. Running "as CI" outside GitHub Actions never authorizes anything. Environment variables such as `GITHUB_ACTIONS`, `GITHUB_REPOSITORY` or `GITHUB_ACTOR` are never evidence.
5. Code, history and results stay on the runner, and finding details are not written to the job log (T15). Network traffic stays limited to GitHub (`api.github.com` and the Actions token service `token.actions.githubusercontent.com`).

### Non-goals

- No implementation in M10-2, and no change to the local device-flow path.
- No scanning of pull request code in CI (see [U2](#8-what-remains-unprovable-and-is-therefore-blocked)). CI is limited to the default branch.
- No support for other CI systems or for GitHub Enterprise Server (see [section 9](#9-out-of-scope)).
- No defence against a modified `pgard` binary. PGARD is becoming open source; anyone can build a copy without the gate, exactly as on a laptop today. The gate protects users of the real `pgard`, and the people whose repositories it is pointed at, from scans that are not authorized. This design keeps that property in CI and does not try to do more.

Two properties matter for CI:

- The **subject** of checks 3 to 5 is the signed-in person. Everything that makes the checks meaningful (owner, org owner, collaborator, contributor) is a statement about that person's GitHub account id.
- Checks 3 to 5 need the GitHub API. Nothing in today's gate can be proved offline except check 1.

## 3. What changes in CI

In a CI job there is no person at a terminal, so there is no device flow. Something must take the place of "the signed-in person", and checks 3 to 5 must be evaluated for that subject, with the same rules.

This design separates two kinds of input:

- **Identity**: who the subject is. It must be signed by GitHub and bound to this job and this process, so it cannot be copied, replayed or produced outside GitHub.
- **Facts**: what GitHub says about repositories, installations, memberships, pull requests and commits. A fact read from `api.github.com` over TLS is true no matter which token was used to read it, provided the token could read it at all. So the provenance of a read-only token matters for _whether_ a fact can be read, never for _what_ it says.

Only a GitHub-signed OIDC token gives an identity in CI (section 4). Tokens that only read facts may come from anywhere, but they are never identity.

**Consent is per repository.** Locally, the person who runs `pgard` chose to scan. In CI, a repository admin chose to scan by creating the environment, its secret and the caller workflow (section 7). The actor of a `push` did not ask for a scan on that push; they are the subject whose standing (owner, collaborator, contributor) checks 3 to 5 evaluate, exactly as a person at a terminal would be. This is stated in the CI guide (**Requirement for M10-3**).

## 4. CI identity options

For each option: how it maps to each check, how it could be spoofed, and whether it can be verified offline.

### A. GitHub Actions OIDC token (`id-token: write`)

A step in a job with `permissions: id-token: write` can ask GitHub's OIDC provider for a JWT, using the runner variables `ACTIONS_ID_TOKEN_REQUEST_URL` and `ACTIONS_ID_TOKEN_REQUEST_TOKEN` and an `audience` query parameter of its choice ([OIDC reference](https://docs.github.com/en/actions/reference/security/oidc), [workflow syntax: `permissions`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)). The token is signed with RS256 by the issuer `https://token.actions.githubusercontent.com`, whose keys are published at the `jwks_uri` of its [OpenID configuration](https://token.actions.githubusercontent.com/.well-known/openid-configuration) ([JWKS](https://token.actions.githubusercontent.com/.well-known/jwks)). The configuration lists these claims: `sub`, `aud`, `exp`, `iat`, `iss`, `jti`, `nbf`, `ref`, `sha`, `repository`, `repository_id`, `repository_owner`, `repository_owner_id`, `enterprise`, `enterprise_id`, `run_id`, `run_number`, `run_attempt`, `actor`, `actor_id`, `workflow`, `workflow_ref`, `workflow_sha`, `head_ref`, `base_ref`, `event_name`, `ref_type`, `ref_protected`, `environment`, `environment_node_id`, `job_workflow_ref`, `job_workflow_sha`, `repository_visibility`, `runner_environment`, `issuer_scope`, `check_run_id`. Some of them (`sha`, `ref_protected`, `enterprise`) are listed there but not described in the OIDC reference.

Relevant documented semantics:

- `actor` / `actor_id`: the account that initiated the run. For a re-run, GitHub's [contexts reference](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts) says `github.actor` stays the user of the _initial_ run, the re-run uses that user's privileges, and the person who started the re-run is `github.triggering_actor`. The OIDC claims list has no `triggering_actor`.
- `job_workflow_ref` / `job_workflow_sha`: present when the job uses a reusable workflow; they name the called workflow file and its commit. The other claims (`repository`, `ref`, `workflow`, ...) describe the **caller** ([OIDC with reusable workflows](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-with-reusable-workflows)).
- `environment`: the environment the job uses.
- `runner_environment`: `github-hosted` or `self-hosted`.
- `sub`: its format depends on the event, on environments, on customised templates, and, for repositories created (or renamed or transferred) after 15 July 2026, on an immutable format with owner and repository ids ([OIDC reference](https://docs.github.com/en/actions/reference/security/oidc)). This design therefore **never parses `sub`** and checks individual claims instead.
- Lifetime: the token is "only valid for a single job" ([OIDC concepts](https://docs.github.com/en/actions/concepts/security/openid-connect)); GitHub documents no fixed lifetime, so the design reads `exp` and adds its own freshness limit.

### B. `GITHUB_TOKEN`

"The `GITHUB_TOKEN` secret is a GitHub App installation access token", created per job, limited to the repository that contains the workflow, expiring when the job ends or after at most 6 hours on GitHub-hosted runners (24 hours on self-hosted) ([`GITHUB_TOKEN`](https://docs.github.com/en/actions/concepts/security/github_token)). Its permissions are set with `permissions:`; for pull request events from forks, other than `pull_request_target`, write permissions become read-only unless the repository enables sending write tokens; `pull_request_target` gets read/write even from a public fork ([workflow syntax: `permissions`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)).

| Check             | Mapping                                                                                                                                                            | How it could be spoofed                                                                                                                                                             | Offline?          |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- |
| `repository`      | Can read `GET /repos/{owner}/{repo}` (id, owner id and type, visibility, default branch) for this repository: facts, not binding.                                  | It is an opaque string in an environment variable. A personal access token, another repository's `GITHUB_TOKEN`, or any other token can be put in the same variable outside GitHub. | No (opaque token) |
| `github_identity` | None. It represents the GitHub Actions App installation, not a person; it says nothing about who triggered the run.                                                | n/a                                                                                                                                                                                 | No                |
| `owner_approval`  | None. It cannot list another App's installations or read organization memberships (`members` is not a `GITHUB_TOKEN` permission scope).                            | n/a                                                                                                                                                                                 | No                |
| `current_access`  | None for a person: `permissions` in `GET /repos` describe the token, not the actor.                                                                                | n/a                                                                                                                                                                                 | No                |
| `contribution`    | Can read the facts the existing rule needs for this repository (`compare`, PRs for a commit, commit verification) with `contents: read` and `pull-requests: read`. | Facts only (section 3); safe to read with any token that can read them.                                                                                                             | No                |

Conclusion: usable as a **fact reader** for this repository, never as identity or approval. The recommended design reads all repository and contribution facts with it (least privilege, section 7).

### C. A GitHub App installation token handed to `pgard`

An installation token is created by `POST /app/installations/{installation_id}/access_tokens` with a JWT of the App, "will expire after 1 hour", is attributed to the App, and can be narrowed to repositories and permissions the installation already has ([authenticating as an installation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation)). The endpoint `GET /repos/{owner}/{repo}/installation`, which returns `app_id`, `account` and `repository_selection`, requires the App's JWT, and the token-creation response contains no `app_id` or `account` ([Apps REST API](https://docs.github.com/en/rest/apps/apps)).

Two variants:

- **C1. A ready-made installation token** (for example from an action that mints it earlier in the job). `pgard` cannot tell which App issued it: no installation-token call it may make returns the App id. A token of any App installed on the owner account (or on a repository the attacker controls) would look the same. Owner approval cannot be shown to be about the configured App. **Rejected as approval evidence.**
- **C2. App credentials given to `pgard` (App id and private key).** `pgard` signs the App JWT itself, reads `GET /app` (the App's `owner`) and `GET /repos/{owner}/{repo}/installation` (`app_id`, installation account), then mints a short installation token restricted to this repository with read-only permissions, used only for the membership and collaborator-permission reads. This proves the installation **of that App**, owned by the repository owner, on the owner account.

So C2 is available only for an App whose key the repository owner holds and that the repository owner owns: a self-registered App. This resembles today's `PGARD_GITHUB_APP_CLIENT_ID` override in that the App is configurable, but it is not the same trust: CI adds the App-owner check, and a stolen key is a new risk that does not exist locally (T11). See [open question Q1](#11-open-questions-for-the-owner).

### D. A saved user-to-server token (device flow done once, token stored as a CI secret)

All five checks would run exactly as today, but:

- the identity is the account that once signed in, not whoever caused this run: anyone who can run a workflow that reads the secret scans _as the owner_, so owner approval and the owner exemption would be granted to code the owner never saw;
- the token is long-lived (8-hour access tokens with 6-month refresh tokens, or no expiry at all, depending on the App's settings), and refreshing would have to write a new secret back;
- it contradicts today's rule that the token is never put in environment variables;
- it cannot be verified offline and cannot be bound to the job.

**Rejected.** A personal access token is the same or worse (it is not even tied to the PGARD App) and is **rejected** for the same reasons.

### E. Unsigned job metadata (`GITHUB_ACTIONS`, `GITHUB_REPOSITORY`, `GITHUB_ACTOR`, `GITHUB_SHA`, event payload file)

Anyone can set them, on any machine. **Never evidence**, not even as a hint that changes a check result.

## 5. Offline versus online verification, and JWKS

**Verifiable offline** (no network, once the signing keys are known): the JWT structure; `alg` = `RS256`; the RS256 signature over the header and payload with the key named by `kid`; `iss`; `aud`; `exp`, `nbf`, `iat`; and every claim comparison that needs only local data: `repository` against the verified remote, `sha` against local `HEAD`, `job_workflow_sha` and the `job_workflow_ref` prefix against the values built into `pgard`, `environment`, `runner_environment`, `event_name`, `ref_type`, `run_attempt`, and `actor_id == repository_owner_id`.

**Needs the GitHub API**: the signing keys themselves (JWKS fetch); that `repository_id`, `repository_owner_id`, visibility and the default branch match what GitHub reports now; that the actor is a `User` account (`GET /user/{actor_id}`, by id because a login can change); the App owner and installation (C2); organization membership; collaborator permission; all contribution facts. Since checks 3 to 5 always need the API, **an offline CI authorization can never be `allowed`**. There is no offline mode.

**JWKS fetching and pinning** (**Requirement for M10-3**):

- The issuer `https://token.actions.githubusercontent.com` and the JWKS URL `https://token.actions.githubusercontent.com/.well-known/jwks` are constants in `pgard`. The OpenID configuration document is **not** fetched at run time, so a changed or spoofed discovery document cannot move the key source. A change of `jwks_uri` by GitHub needs a `pgard` release.
- The JWKS is fetched over HTTPS once per authorization, with no redirects followed, a short timeout and a size cap, using the same hardened fetch as the GitHub client. Only keys with `kty: RSA`, `alg: RS256` (or absent `alg`) and `use: sig` (or absent `use`) are accepted; at least 2048-bit moduli.
- The JWKS is kept in memory for that one authorization only and never written to disk. It is not an authorization result, but caching it would add a second trust store to keep fresh, and the run is online anyway.
- No key snapshot is shipped as a trust anchor: a snapshot would keep accepting a key that GitHub has rotated out. (Shipping one only for tests is fine.)
- Unknown `kid` after the fetch, a fetch failure, or a malformed JWKS: `github_identity` is `unverifiable` with the reason. Never a fallback to another key or to the device flow.

## 6. Threat model

Assets: the authorization decision; the App private key (C2); the OIDC token and the installation token while the job runs; the scanned code and the findings on the runner.

**Trust root.** GitHub's token service, its Actions control plane (which decides the claims, the environment rules and which workflow file runs) and its API are trusted, as are GitHub-hosted runner images. Larger runners can use custom images that the organization controls while still reporting `runner_environment: github-hosted`; such an image is inside the organization's own trust, and this design cannot tell it apart (U11).

Trust boundaries: the pinned reusable workflow and the `pgard` it builds (trusted, fixed by commit); the caller workflow and everything else in the scanned repository (untrusted: anyone with write access to a branch can change it, including `.npmrc`, local actions, caches, variables and the event payload); every environment variable (untrusted); the runner machine (trusted only when GitHub-hosted).

The attacker's server must return a GitHub-signed token with this process's nonce as audience, i.e. mint it live inside a job of the target repository that satisfies every claim in section 7.5: default branch, allowed event, GitHub-hosted, the pinned environment, and the pinned workflow commit. By the invariants of section 7.2 no code the repository controls runs in that job, so it cannot relay. A token from any other job fails at least one claim.                                                                                                                                                                                                                                                                                                                                                                                                             |

| T9  | **Re-run by someone else**: `run_attempt > 1` keeps `actor` from the first attempt, and the re-run uses that actor's privileges.                                                                                                                                                                                                                                                                                                                          | `run_attempt` must be `1`. | T10 | **Bot or App actor** (Dependabot, `github-actions[bot]`, another App) triggers the run.                                                                                                                                                                                                                                                                                                                                                                   | `GET /user/{actor_id}` must return `type: User`, the same id and the login `actor`. ## 7. Recommended design

### 7.1 Overview

1. **Identity** comes only from an Actions OIDC token that `pgard` requests itself, inside the job, with a fresh nonce audience, and verifies against GitHub's JWKS (option A).
2. The **job is fixed**: the token is accepted only from a job that runs PGARD's own reusable workflow at the exact commit the running `pgard` was built from, in that workflow's fixed environment, on a GitHub-hosted runner, for a `push` or `workflow_dispatch` on the default branch, on the first attempt. Nothing the scanned repository controls can run code in that job (7.2).
3. The **subject** of checks 3 to 5 is the OIDC actor (`actor_id`, a `User`). The existing check functions run unchanged with that subject in place of the signed-in user.
4. **Owner approval** needs App evidence of the same strength as today: option C2, with an App owned by the repository owner, whose id and key live only in the protected environment. Without it, owner approval is `unverifiable` and the scan is blocked. For the built-in PGARD App this is the case (Q1).
5. **Facts** about the repository and contributions are read with `GITHUB_TOKEN` (option B, least privilege). The App key is used only for the App owner, the installation, the organization membership and the collaborator permission.
6. The CI evidence provider is chosen explicitly (proposed: `--identity github-actions`, Q7). Without it, nothing changes: no terminal and no saved sign-in still blocks with "Not signed in". With it, there is no fallback to the keychain or the device flow.

### 7.2 Invariants for the pinned job

Nothing the scanned repository controls may influence code execution in the job that runs `pgard`. Otherwise that code could mint a token with `pgard`'s audience (T6, T7) or read the key from `/proc` (T16). Each invariant has a test in M10-3 (section 10).

1. **I1. Zero caller inputs.** `on.workflow_call.inputs` is empty. The only caller-supplied value is the secret `PGARD_APP_PRIVATE_KEY`, passed by name; the App id is an environment variable of the pinned environment.
2. **I2. `pgard` is built before the scanned repository is checked out, and outside the workspace.** Its source is fetched at `job.workflow_sha` from `job.workflow_repository` ([contexts](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts)) into `RUNNER_TEMP`, and built there from its own lockfile.
3. **I3. No `.npmrc` or other repository configuration influences the build.** The build runs with `NPM_CONFIG_USERCONFIG` and `NPM_CONFIG_GLOBALCONFIG` pointing to empty files, the public registry set explicitly, and lifecycle scripts disabled unless a dependency is shown to need one. The scanned repository does not exist yet when the build runs (I2). That ordering is also why a lifecycle script that a dependency does need is acceptable: it runs code from PGARD's own lockfile before any repository content is on the machine, and it runs before the OIDC token is requested. Run after the checkout, the same script could be steered by the repository.
4. **I4. No caches.** No `actions/cache`, no `cache:` in `actions/setup-node`, no tool cache restored from the repository. The caller's `cache-mode` therefore has nothing to restore; M10-3 verifies that.
5. **I5. Only JavaScript actions from trusted publishers, pinned by full commit SHA.** No composite action whose transitive actions are not pinned. No Docker actions that pull mutable tags.
6. **I6. No local actions** (`uses: ./...`), and no step runs a file from the scanned repository.
7. **I7. No event data, `vars` or other repository-controlled values in expressions that reach a `run:` script, `uses:` or an action's `with:`.** Repository-controlled values (the environment's `PGARD_APP_ID` and the secret) reach only the `pgard` step, through `env:`, and `pgard` validates them (digits; PEM).
8. **I8. The scanned repository is checked out only as data** (`actions/checkout` pinned by SHA, `persist-credentials: false`, `fetch-depth: 30`), and `pgard` is the only process that reads it. No package manager, build or test of the scanned repository runs, as today.

### 7.3 Workflow shape, environment and key handling

The scanned repository calls PGARD's reusable workflow. "The job that calls the reusable workflow can't use the `environment` keyword"; to use an environment secret, the reusable workflow sets `environment` on its own job, and the caller "must still pass the secret" by name ([reuse workflows](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows)).

```yaml
# .github/workflows/pgard.yml in the scanned repository (caller)
on:
  push:
    branches: [main]
  workflow_dispatch:
jobs:
  scan:
    uses: JadenMeister/pgard/.github/workflows/ci-scan.yml@<40-hex release commit>
    permissions:
      contents: read
      pull-requests: read
      id-token: write
      security-events: write # only for the SARIF upload
    secrets:
      PGARD_APP_PRIVATE_KEY: ${{ secrets.PGARD_APP_PRIVATE_KEY }} # an environment secret
```

The reusable workflow (in this repository, **Requirement for M10-3**), in order:

1. one job, `runs-on` a GitHub-hosted image, `environment: pgard-ci` (fixed name), its own `permissions` as above;
2. `actions/setup-node` pinned by SHA, without cache (I4), because the build needs Node.js;
3. a fixed `run:` step fetches PGARD's source at `job.workflow_sha` into `RUNNER_TEMP` and builds it (I2, I3), recording that SHA as `BUILD_SHA` in the build;
4. `actions/checkout` of the scanned repository, pinned by SHA (I8);
5. `pgard scan --identity github-actions --format sarif --output-file "$RUNNER_TEMP/pgard.sarif"`, with `env:` `PGARD_APP_ID: ${{ vars.PGARD_APP_ID }}`, `PGARD_APP_PRIVATE_KEY: ${{ secrets.PGARD_APP_PRIVATE_KEY }}` and `GITHUB_TOKEN`;
6. optionally, `github/codeql-action/upload-sarif` pinned by SHA (T15).

**Environment and App setup** (the CI guide, **Requirement for M10-3**):

- Create the environment `pgard-ci` with a deployment-branch policy that allows the default branch only, and add required reviewers or protect the default branch (reviews required, and ideally code owners for `.github/workflows`).
- Store the key only as an environment secret of `pgard-ci`, never as a repository or organization secret. (An environment secret takes precedence over a repository secret with the same name, but a repository secret would still be readable by branch workflows.) Store the App id as an environment variable `PGARD_APP_ID`.
- Register the App under the account that owns the repository. Grant only **Metadata: read** and, for organizations, **Members: read**. Install it on **selected repositories**.
- The OIDC `environment` claim must equal `pgard-ci` (7.5), so a token from a job outside the environment is refused.
- Pin `uses:` to the commit of a PGARD **release** (the guide names it for each version). Building from source binds the binary to the workflow commit, but does not by itself prove that the commit is a release.
- Uploading SARIF to code scanning from a private repository needs GitHub Code Security (GitHub Advanced Security). Without it, keep the result file only.

**Release coupling.** The workflow file cannot contain its own commit SHA or the hash of a package built from it. Instead the job builds `pgard` from source at `job.workflow_sha` (step 2), so the binary that verifies `job_workflow_sha == BUILD_SHA` is, by construction, the code of that commit. For a genuine release commit this is the genuine `pgard`. An alternative is to install the npm release and verify its provenance attestation against `job.workflow_sha` (Q10).

### 7.4 Key and token hygiene

- `pgard` emits `::add-mask::` for the OIDC token, the installation token and the key before any other output (T16).
- The key is read once from the environment; it remains in `/proc/<pid>/environ` for the life of the process (T16), which is acceptable only under the invariants of 7.2. It is never logged, put in arguments or written to a file.
- The installation token is restricted to this repository id, read-only, and revoked with `DELETE /installation/token` at the end. Today's `FetchLike` only allows `GET` and `POST`; M10-3 must add `DELETE` (**Requirement for M10-3**).

### 7.5 Exact checks on the OIDC token

All comparisons are exact, case-sensitive string comparisons unless stated. A claim that is missing, has the wrong JSON type, or is duplicated makes `github_identity` `unverifiable` with the claim name in the reason (never its value when the value could be sensitive). Numeric claims are decimal strings in GitHub's tokens; anything else is refused.

| Claim / field                                                                                         | Required value                                                                                                                         | Source of the expected value    |
| ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| header `alg`                                                                                          | `RS256` (`none`, `HS*` and everything else refused)                                                                                    | constant                        |
| header `kid`                                                                                          | present, matches exactly one key in the fetched JWKS                                                                                   | JWKS (section 5)                |
| signature                                                                                             | valid RS256 over `header.payload` with that key                                                                                        | JWKS                            |
| `iss`                                                                                                 | `https://token.actions.githubusercontent.com`                                                                                          | constant                        |
| `aud`                                                                                                 | `pgard-ci:v1:<nonce>`; if an array, exactly one element, equal to it                                                                   | nonce generated in this process |
| `iat`                                                                                                 | within ±60 s of the local clock                                                                                                        | clock                           |
| `nbf`                                                                                                 | ≤ now + 60 s                                                                                                                           | clock                           |
| `exp`                                                                                                 | > now, and `exp − iat` ≤ 3600 s                                                                                                        | clock                           |
| `runner_environment`                                                                                  | `github-hosted`                                                                                                                        | constant                        |
| `environment`                                                                                         | `pgard-ci`                                                                                                                             | constant (the pinned job's)     |
| `event_name`                                                                                          | `push` or `workflow_dispatch`                                                                                                          | constant allowlist              |
| `ref_type`                                                                                            | `branch`                                                                                                                               | constant                        |
| `ref`                                                                                                 | `refs/heads/` + the default branch GitHub reports in this run                                                                          | `GET /repos` (online)           |
| `run_attempt`                                                                                         | `1`                                                                                                                                    | constant (Q2)                   |
| `repository`                                                                                          | `owner/name` of the verified remote, and equal to GitHub's `full_name`                                                                 | local remote, `GET /repos`      |
| `repository_id`                                                                                       | equal to GitHub's repository `id`                                                                                                      | `GET /repos`                    |
| `repository_owner` / `repository_owner_id`                                                            | equal to GitHub's `owner.login` / `owner.id`                                                                                           | `GET /repos`                    |
| `sha`                                                                                                 | 40 hex, equal to local `HEAD` (which must be the checkout of that commit, with a clean working tree)                                   | local Git                       |
| `job_workflow_sha`                                                                                    | `<BUILD_SHA>`                                                                                                                          | built into `pgard`              |
| `job_workflow_ref`                                                                                    | starts with `JadenMeister/pgard/.github/workflows/ci-scan.yml@` (repository and path prefix; the commit is checked with the row above) | constant                        |
| `actor_id` / `actor`                                                                                  | decimal / non-empty; `GET /user/{actor_id}` returns `type: User`, the same `id` and `login == actor`                                   | `GET /user/{actor_id}` (online) |
| `sub`, `workflow`, `workflow_ref`, `workflow_sha`, `run_id`, `ref_protected`, `repository_visibility` | not used for the decision. `workflow_ref` and `run_id` are named in the `github_identity` reason so the run can be traced.             | n/a                             |

The token request itself: `pgard` reads `ACTIONS_ID_TOKEN_REQUEST_URL` and `ACTIONS_ID_TOKEN_REQUEST_TOKEN`, requires the URL to be HTTPS, appends `audience=pgard-ci:v1:<nonce>`, masks and never logs either variable or the token. A request URL controlled by an attacker can at worst return a token, which must then pass every check above.

### 7.6 The five checks in CI

| Check             | In CI                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `repository`      | `verifyRepository` unchanged. In addition (**Requirement for M10-3**): the working tree is clean, and the remote's `owner/name` equals the OIDC `repository`. (`HEAD == sha` is checked with the token in `github_identity`, because the token is only requested after the local check passes, keeping today's order.)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `github_identity` | Request and verify the OIDC token (7.5). Passed reason, for example: "GitHub Actions run 123 (attempt 1) of `owner/repo` on `refs/heads/main`, triggered by `alice` (OIDC token verified)." The subject is `{ id: actor_id, login: actor }`, confirmed as a `User`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `current_access`  | Read the repository (`GET /repos`) with `GITHUB_TOKEN`. 404 or no read: as today. Then, for the subject: public repository: passed (intended to equal local behaviour, where GitHub reports read access for any account; M10-3 tests it); personal owner (`actor_id == owner.id`): passed; organization owner (an active `admin` membership of the subject, read once with the C2 installation token and reused by owner approval in the same run): passed; anyone else: `GET /repos/{owner}/{repo}/collaborators/{actor}/permission` must return `user.id == actor_id` and `permission` `read`, `write` or `admin`. | `owner_approval`  | C2 present: App JWT; `GET /app` → `owner.type` present and equal to the repository owner's type (`User` or `Organization`), and `owner.id == repository_owner_id` (an Enterprise owner, which carries only an `id` from another id space that could collide, is refused); `GET /repos/{owner}/{repo}/installation` → `app_id` = `PGARD_APP_ID`, `account.id` = `owner.id`, `target_type` = owner type; mint an installation token restricted to this repository with read-only permissions. | `contribution`    | `verifyContribution` unchanged with `user = subject`, the local candidates (up to 30 with `fetch-depth: 30`), `GITHUB_TOKEN` for the facts, and `ownerEvidence` from this run's owner approval only.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |

Every blocked case uses exit code 3 and a reason that names the fix where one exists.

## 9. Out of scope

- **Other CI systems** (GitLab CI, Jenkins, CircleCI, Buildkite, Azure Pipelines, ...). Owner approval in PGARD is an installation of a GitHub App on the GitHub account that owns the repository, and only GitHub can attest that. A GitLab CI OIDC token attests a GitLab project and pipeline, not a GitHub repository or a GitHub user, and nothing links the two (a mirror can point anywhere). Jenkins has no platform-signed job identity at all. Each system would need its own issuer, claims, threat model and mapping to a GitHub account, so it needs its own design. Until then `--identity` accepts only `github-actions`, and these systems remain where they are today: blocked without a terminal and a saved sign-in.
- **GitHub Enterprise Server and enterprise-specific issuers** (Q8): another issuer, key set and API host.
- **Scanning pull requests in CI** (U2): CI is limited to the default branch.

## 10. Requirements for M10-3 and test plan

Requirements named in this document, in one list:

- the `--identity github-actions` provider (name per Q7), with no fallback;
- the OIDC request with a per-process nonce audience;
- JWT verification with a pinned issuer and JWKS URL, and the JWKS in memory only;
- the exact claim table of 7.5;
- the reusable workflow `ci-scan.yml` with the fixed `pgard-ci` environment, the invariants I1–I8, and building from source at `job.workflow_sha` with `BUILD_SHA` recorded;
- the clean-working-tree check in CI;
- a subject-based `current_access` for CI;
- C2 owner approval: App JWT, `GET /app` owner check, installation lookup, a restricted read-only installation token, `DELETE` support in `FetchLike` and revocation;
- masking and key hygiene (7.4);
- no finding details in CI logs (T15);
- README and a CI guide: environment, deployment-branch policy, review, App registration under the owner, least-privilege permissions, selected-repository install, the residual risk of T11, consent per repository, and what is blocked and why.

Tests (no real GitHub calls; tokens signed by a test key served as a fake JWKS):

- each row of 7.5 mutated one at a time blocks with the expected reason:
  - wrong `iss` or `aud`; expired; `iat` in the future;
  - `alg: none`; `HS256` with the public key as the secret; unknown `kid`;
  - `self-hosted`; another `environment` or none;
  - `pull_request`, `pull_request_target`, `workflow_run`, `schedule`, `merge_group`;
  - `run_attempt: "2"`; `ref` on another branch; `sha` ≠ `HEAD`;
  - `job_workflow_sha` of another commit; `job_workflow_ref` from another repository or path;
  - a missing claim; a number instead of a string;
- a token with another process's nonce (replay) blocks;
- `GITHUB_ACTIONS=true` with no request variables blocks. So do request variables pointing to a server that returns a validly signed token for another repository;
- actor cases:
  - a bot actor and a push made by an App block;
  - pushes made with a deploy key and merge-queue runs: M10-3 establishes what the token says, and they block unless the actor is a `User` who passes checks 3 to 5;
  - personal owner, organization owner, and a collaborator with and without a contribution behave as in the local tests;
  - on a public repository, `current_access` matches the local result for a non-collaborator;
- C2:
  - without it, `owner_approval` is `unverifiable` and the other checks still report their own reasons;
  - an App owned by another account fails;
  - an App whose `owner` is the Enterprise shape (only `id`, equal to the repository owner's id), has no `type`, or has a `type` that differs from the repository owner's, fails;
  - an installation of another App fails;
  - the installation token is revoked;
- invariants, one test or workflow lint rule each:
  - I1: no `workflow_call` inputs;
  - I2: the build happens before checkout, under `RUNNER_TEMP`;
  - I3: an `.npmrc` in the scanned repository has no effect;
  - I4: no cache steps, and a caller `cache-mode` restores nothing;
  - I5: every `uses:` is pinned by a 40-hex SHA, and no composite action has unpinned dependencies;
  - I6: no `./` actions;
  - I7: no `github.event`, `vars` or `inputs` in `run:`, `uses:` or `with:`;
  - I8: no step runs scanned-repository code;
- T15: a scan with findings leaves no finding detail in the log;
- T16: tokens and the key are masked; debug logging does not print them;
- JWKS fetch failure, redirect or oversized body: `unverifiable`, with no fallback;
- `isAuthorizationAllowed` and the five-check order are unchanged (the existing tests keep passing).

## 11. Open questions for the owner

1. **Q1. Owner-approval evidence for CI.** With the built-in PGARD App, owner approval cannot be proved in CI (U1). Options: (a) **C2 with an App owned by the repository owner**, only with the hardening of 7.3 (fixed environment, default-branch policy with review, App-owner check, least privilege, selected repositories) and the residual risk of T11 stated in the guide; (b) a maintainer-run service that holds the built-in App's key, verifies the OIDC token and answers the installation question; this breaks "scans contact GitHub only" and adds a service to operate; (c) a new kind of evidence, such as an owner-signed policy file on the default branch; this is a policy change and needs its own review. Recommended: (a) with that hardening, and the built-in App stays blocked in CI.
2. **Q2. Re-runs.** Block every `run_attempt > 1` (recommended, because the re-runner is unknown), or accept re-runs and document that the subject is the first attempt's actor?
3. **Q3. `schedule`.** Recommended: blocked permanently, because the documented actor of a scheduled run need not be anyone who asked for it (U3). Confirm.
4. **Q4. `ref_protected`.** The claim is listed in the OpenID configuration but not described in the OIDC reference, so the design does not rely on it. Recommended: do not require it; recommend branch protection in the guide instead.
5. **Q5. Pull request scanning.** Recommended: CI is limited to the default branch; no separate design is planned now. Confirm.
6. **Q6. Self-hosted runners.** Blocked permanently (recommended), or should an owner-declared exception be designed, knowing that it cannot be proved?
7. **Q7. How CI is selected.** A flag (`--identity github-actions`), an environment variable (`PGARD_IDENTITY=github-actions`), or both? Recommended: the flag, never auto-detected.
8. **Q8. GitHub Enterprise.** Is ghe.com or GitHub Enterprise Server in scope later? It needs another issuer and API host.
9. **Q9. App key in an environment variable.** Recommended: an environment variable for the single `pgard` step only, sourced from the `pgard-ci` environment secret, masked, with the `/proc` caveat of T16 documented. It is an App credential, not a user token, so today's rule for user tokens is unchanged.
10. **Q10. Release coupling.** Build `pgard` from source at `job.workflow_sha` inside the job (recommended), or install the npm release and verify its provenance against that commit?
