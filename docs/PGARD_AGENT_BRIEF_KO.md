**현재 상태:** 제품명과 기본 명령 `pgard`, 로컬 실행, GitHub owner 승인·현재 접근·실제 반영 기여 확인, 코드/Git/로컬 HTTP 검사 범위는 대화에서 정했다. TypeScript/Node.js/React 구현 스택은 추천안이다. 현재 문서 작업 공간에는 Git 저장소와 리뷰 대기 PR이 없으므로 구현·PR 생성·병합은 수행하지 않았다.

## 제품 명세

이 문서는 대화에서 **확정한 제품 요구사항**, **제안만 된 구현 선택**, **미결정 사항**을 구분한다. 향후 구현 담당 에이전트는 제안을 확정 사항으로 바꾸지 않는다.

### 1. 제품 정의

PGARD(Project Guard)는 자신이 기여하고 검사 권한을 받은 프로젝트의 코드·Git 이력과, 사용자가 연결한 로컬 웹 서비스를 점검해 취약점의 근거와 수정 가이드를 제공하는 로컬 우선 오픈소스 보안 도구다. 이름과 CLI 실행 명령은 `pgard`로 확정했다. 독립적인 CLI와 웹 제품을 만들되, 검사 결과 의미는 양쪽에서 일치해야 한다. MIT 라이선스와 한국어·영어 README를 제공한다. 웹 제품의 이용약관/개인정보 고지에는 **일회성 로컬 처리**, GitHub 인증 및 선택적 취약점 데이터 갱신을 위한 외부 통신, **사용자가 직접 내보낸 보고서만 사용자 지정 위치에 남는다는 점**을 명시한다. 유료 도메인 구매는 보류한다.

### 2. 승인과 검사 대상

1. 로컬 프로젝트 디렉터리는 Git 저장소이며 유효한 이력을 갖는다. 원격 GitHub 저장소와의 관계를 확인한다.
2. 사용자는 자신의 GitHub 계정으로 로그인한다. PGARD GitHub App은 대상 저장소에 설치되어 있어야 하고 **저장소 owner의 승인**이 있어야 한다. 개인 저장소는 그 개인 owner, 조직 저장소는 조직 owner의 승인만 인정한다. 관리자 또는 멤버 설치만으로는 충족되지 않는다.
3. 검사하는 사용자에게 대상 저장소의 **현재 접근 권한**이 있어야 한다.
4. 본인의 변경 내용이 저장소의 실제 이력에 반영된 커밋·기여·merge가 있어야 한다. PR 생성·리뷰·댓글만으로는 통과하지 않는다. Git 로그의 작성자 이름·이메일만으로 본인을 인증하지 않는다. 로컬 `git log`에서 커밋 후보를 찾고 GitHub 계정과 저장소의 커밋·병합 이력을 대조한다.
5. 타인의 배포 서비스나 오픈소스 프로젝트를 임의로 스캔하는 기능은 만들지 않는다. 로컬 웹 검사도 승인된 프로젝트와 사용자가 연결한 서비스에 한정한다.

**미결정/주의:** GitHub App 설치만으로 "반드시 owner가 승인"했다는 사실을 항상 증명할 수 있는지는 구현 단계에서 GitHub의 실제 권한 모델로 검증해야 한다. 검증할 수 없다면 우회해서 통과시키지 말고 owner 승인 증빙 절차를 설계해야 한다. 공동 작성 커밋 및 squash merge에서 변경 기여를 계정과 연결하는 세부 규칙도 정해야 한다. OAuth 로그인은 사용자 인증 수단이지, 단독으로 저장소 owner 승인을 의미하지 않는다.

### 3. CLI 경험

- `pgard` 한 단어로 TUI를 시작한다.
- 방향키로 항목을 선택하고 Enter로 확정하며 Esc로 이전 단계로 돌아간다. 텍스트/숫자 입력은 단계적으로 받는다.
- 프로젝트를 검사하고, 원하는 경우 로컬 웹 서비스도 연결한다.
- 로컬 웹 검사를 선택한 경우 열린 로컬 포트 후보를 보여준다. 대상이 목록에 없으면 **Other port**에서 포트 번호를 직접 입력한다.
- 선택한 포트에 HTTP로 접속해 `<title>`과 응답 상태, 추정 기술 등의 식별 정보를 보여준 후 "현재 프로젝트의 서비스가 맞습니까? [y/N]"을 묻는다. `Y`는 사용자의 대상 선택이며 코드와 서비스의 동일성을 암호학적으로 증명하지 않는다.
- CLI 결과에는 심각도별 막대 차트, 취약점/의심 구분, 파일:줄 또는 URL, 근거와 대응 가이드를 제공한다.

포트가 열려 있다는 사실만으로 웹 서비스나 소스 코드에 접근할 수 있는 것은 아니다. **코드는 선택한 프로젝트 디렉터리에서**, HTTP 응답은 **확인한 포트에서** 읽는다. 포트 번호만으로 프로토콜이나 기술을 확정하지 않는다.

### 4. 웹 제품 경험

- 웹 제품 역시 사용자의 컴퓨터에서 실행된다. 호스팅 서버에서 사용자의 `127.0.0.1`로 직접 접속하는 구조를 사용하지 않는다.
- CLI와 별도 사용자 화면을 가지며, 검사 결과는 대시보드에서 막대/도넛 차트 및 URL/파일 위치와 함께 보여준다.
- 웹 검사의 핵심은 코드 분석이다. 실행 중인 HTTP 서비스는 응답 및 보안 헤더를 중심으로 보조 검증한다.
- 로그인하지 않아도 코드 검사와 비로그인 HTTP 검사를 수행한다. 로그인 이후 검사를 선택하면 사용자가 PGARD가 연 브라우저에서 직접 로그인한다. PGARD가 앱 로그인 비밀번호를 대신 수집하지 않는다. 세션은 해당 검사에만 사용하고 종료 시 폐기한다.
- 첫 버전은 폼 제출, 회원 정보 수정, 업로드 등 **알려진 상태 변경 동작을 자동 실행하지 않는다**. 단, 잘못 구현된 서비스에서는 GET 탐색에도 부작용이 있을 수 있으므로 완전한 무변경 보장으로 표현하지 않는다. 비로그인/인증 페이지 중 검사를 수행하지 못한 범위는 결과에 "미검사"로 표기한다.
- HTTP 검사에서 실제 탐색 가능한 URL과 헤더를 검사하되, 모든 취약점을 완전히 탐지한다고 주장하지 않는다.

**미결정:** 크롤링 깊이, URL 수/시간 제한, 인증 세션 보관·폐기 방식, 리다이렉트와 로컬 주소 범위의 정확한 정책.

### 5. 코드·Git·의존성 검사 범위

첫 지원 언어/생태계는 JavaScript, TypeScript, React, Vue, Go다. React·Vue는 각각 JS/TS 안에서 프레임워크별 규칙을 둔다. 이미 논의한 검사 목표는 다음과 같다.

| 범주                 | 우선 확인할 정적 근거                                                                   | 판정상 주의                                                     |
| -------------------- | --------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| SQL Injection        | 사용자 입력이 SQL 문자열 결합·보간 후 실행 함수로 이동하는지, 매개변수 바인딩 사용 여부 | DB에 직접 접속하지 않음                                         |
| XSS                  | 위험한 HTML 출력 경로와 신뢰할 수 없는 입력 흐름                                        | API 사용 자체만으로 취약점 확정 금지                            |
| SSRF                 | 외부 입력으로 만든 URL이 서버 HTTP 요청에 전달되는 경로                                 | 허용 목록 등 방어를 함께 판단                                   |
| 접근 제어·인증 실패  | 보호 대상 라우트의 인증/권한 검사 및 세션 설정                                          | 서비스의 의도가 불명확하면 의심/검토 필요                       |
| 무차별 대입 방어     | 로그인·재설정 기능의 시도 제한과 보호 장치                                              | 실제 비밀번호 대량 대입은 수행하지 않음                         |
| 암호화 실패          | 평문 비밀번호 저장, 위험한 해시/암호화, 하드코딩 키                                     | 값 자체를 결과에 노출하지 않음                                  |
| 설정 오류·CSRF       | 서버 설정, 헤더, 쿠키 인증을 쓰는 변경 요청의 CSRF 방어                                 | 배포 환경 의존성을 표시                                         |
| 파일 업로드·다운로드 | 파일 종류/경로 처리, 권한 검사, 경로 조작 위험                                          | 변경·삭제 요청을 자동 실행하지 않음                             |
| 명령 실행·파일 경로  | 입력값의 셸/파일 경로 전달                                                              | 확인된 흐름과 단순 패턴을 구분                                  |
| 알려진 CVE           | 실제 잠긴 의존성 버전과 취약 버전 비교                                                  | CVE 일치와 실제 악용 가능성을 구분                              |
| Git 비밀정보         | 현재 추적 파일과 과거 커밋의 `.env`, 비밀번호, API 키 등                                | 로컬에만 있고 Git에서 제외된 `.env`는 그 자체로 Git 유출이 아님 |

SQL 관련 첫 어댑터로 **`pg`/`mysql2`, Prisma raw query, Go `database/sql`, GORM**을 추천한다. 이는 아직 사용자 승인 전인 구현 범위 제안이다. 각 라이브러리의 정확한 함수 목록과 탐지 조건은 규칙 명세에서 다듬는다. 지원하지 않는 ORM은 "미지원"으로 표시한다. CVE 데이터는 로컬에서 대조하는 방식이 원칙이며, 갱신/배포 방식은 구현 선택이다. 기술 스택 탐지는 확인된 기술/추정 기술/버전 미확인을 구분하고, 탐지 자체를 취약점으로 취급하지 않는다.

### 6. 결과와 데이터 처리

- 모든 결과는 CLI·웹에서 같은 근거와 판정으로 표시한다: 발견 항목, 심각도, 확정/의심/미검사, 파일:줄 또는 URL, 근거, 대응 가이드.
- 사용자가 HTML/PDF로 결과를 내보낼 수 있다. 내보낸 파일은 사용자가 관리한다.
- 검사 코드·Git 기록·비밀정보·결과를 PGARD의 외부 DB 또는 서버에 저장하거나 전송하지 않는다. 로컬 실행 중의 일시적 정보는 최소화한다. GitHub 인증/권한·이력 확인에는 GitHub와의 통신이 필요하므로 "100% 로컬"은 **코드 분석 및 결과 처리의 로컬성**으로 정확히 기술한다.
- 화면/로그/보고서에 비밀번호·토큰 원문을 표시하지 않는다. 민감값은 가리고 위치와 종류 등 조치에 필요한 정보만 남긴다.
- 심각도 산식, 확정/의심 기준, 임시 파일·로그·세션 폐기와 취약점 데이터 업데이트 방법은 **확정된 제품 범위 안의 구현 명세**로 작성한다.

### 7. MVP 제외 및 추후 검토

MVP에서는 DB 연결 정보 입력과 DB 직접 스캔, Docker 설정 검사, 성능 누수 검사를 제외한다. 웹 포트 확인은 DB 포트 스캔과 다르다. 원격 서비스 임의 스캔 및 상태를 바꾸는 공격성 HTTP 테스트도 첫 버전에 넣지 않는다. 추후 범위 변경 시 owner 권한과 로컬 처리 원칙을 다시 검토한다.

### 8. 다음 단계의 산출물

1. 권한 판정 상세 설계: GitHub App 권한/설치/owner 승인 증빙과 커밋 기여 판정 예외.
2. 각 언어·프레임워크의 규칙 목록: source/sink/sanitizer, 판정 근거, 의심 조건, 비지원 범위.
3. CLI·웹 화면 흐름과 공통 결과 스키마.
4. 로컬 HTTP 탐색과 인증 모드의 경계·자원 제한.
5. 데이터 처리/로그/보고서 마스킹 정책 및 배포 방식.

## 기술·개발 구조

> 제품 명세와 함께 에이전트에게 전달할 **추천 아키텍처**. 검사 대상 JS/TS·React·Vue·Go와 로컬 실행 등의 합의 사항을 구현 경계, 데이터 계약, 검증 조건으로 바꾼다. TypeScript/Node/React 구현 스택, 패키지 구조와 첫 SQL 어댑터는 사용자 확정 전 제안이며 착수 시 승인·호환성 확인이 필요하다.

### 1. 기술 선택과 실행 경계

- **추천 주 언어:** TypeScript / Node.js. CLI TUI, 로컬 웹 백엔드, 공용 검사 엔진, 보고서 생성기를 같은 언어로 작성한다.
- **추천 웹 UI:** TypeScript + React. CLI와 별도 실행 프로그램이지만 검사 규칙·결과 스키마·권한 게이트를 공유한다.
- **검사 대상 언어:** JavaScript, TypeScript, React JSX/TSX, Vue 단일 파일 컴포넌트, Go. Go를 분석하기 위해 PGARD 자체를 Go로 작성할 필요는 없다. Go용 구문 분석 어댑터부터 시작하고, 타입 정보가 꼭 필요한 규칙은 이후 독립 Go 분석기로 분리할 수 있다.
- **실행 위치:** 코드 파싱, Git 이력 열람, 로컬 HTTP 요청, 결과 생성, PDF/HTML 생성은 사용자 기기에서 수행한다. 소스 코드와 전체 결과를 PGARD 서버나 외부 DB로 보내지 않는다.
- **필요한 외부 통신:** PGARD가 직접 시작하는 외부 요청은 GitHub의 사용자 인증·저장소 접근/기여 메타데이터 조회와 사용자가 시작한 취약점 데이터 업데이트로 제한한다. 사용자가 로그인하는 웹 서비스 자체의 외부 인증 흐름은 별도로 발생할 수 있다. 따라서 “완전한 오프라인 제품”이라고 표현하지 않는다. 검사 실행과 검사 데이터 처리는 로컬이라는 뜻이다. 보고서에는 사용한 취약점 DB 버전과 갱신 시각을 남긴다.
- **MVP 제외:** DB 직접 접속, 성능 검사, Docker 설정 검사, 원격 웹 서비스 스캔, 비밀번호 무작위 대입, 파괴적인 동적 검사.

### 2. 추천 저장소/패키지 경계

```text
apps/
  cli/                 # pgard 진입점, 방향키 TUI, 실행 상태/요약 표시
  local-web/           # 별도 로컬 실행 진입점과 React UI
packages/
  scan-core/           # ScanRequest → ScanResult 조정, 검사 범위 기록
  policy/              # 권한 게이트, 검사 대상 제한, 결과 등급 기준
  github-auth/         # GitHub App 사용자 로그인, 설치/접근/승인 확인
  git-history/         # remote/SHA 확인, Git 이력·추적 파일 검사
  source-analysis/     # JS/TS/JSX/Vue/Go 파서와 규칙 어댑터
  http-local/          # 열린 로컬 포트 후보, 제한된 HTTP 검사
  advisory/            # 로컬 취약점 DB, lockfile/모듈 버전 대조
  findings/            # 공통 JSON 스키마, 중복 제거, 가림 처리
  report/              # 공통 결과 → HTML/PDF 출력
```

- `apps/*`는 검사 로직을 복제하지 않고 `scan-core`만 호출한다. 검사는 UI와 무관하게 실행 가능해야 한다.
- `policy`가 검사 시작 전 승인과 허용된 대상 주소를 판단한다. 각 검사기가 독자적으로 권한 판단을 우회하지 않는다.
- 분석 어댑터는 `Finding[]`과 `Coverage[]`를 반환한다. 지원하지 않는 기술이나 권한 부족은 `미검사`로 표현하고 `안전`으로 취급하지 않는다.
- 프로젝트 파일은 읽기 전용으로 연다. 프로젝트 설정·스크립트·의존성 설치·빌드는 실행하지 않는다. Git은 고정 인자 형태로 호출하고 사용자 입력을 셸 문자열로 조립하지 않는다.

### 3. 검사 흐름

1. 사용자가 프로젝트 디렉터리를 선택한다. Git 저장소 여부, `remote`의 GitHub 저장소 식별자, 작업 트리 상태를 확인한다. 다른 호스트나 모호한 remote는 자동으로 허용하지 않는다.
2. GitHub App의 **device flow** 등 로컬 앱에 맞는 사용자 인증으로 계정 ID를 얻는다. 토큰은 실행 중 메모리에 두며 화면·로그·보고서에 쓰지 않는다. 장기 보관이 필요하다면 OS 보안 저장소와 명시적 로그아웃 설계를 별도로 승인받는다. [GitHub CLI와 GitHub App 안내](https://docs.github.com/en/apps/creating-github-apps/writing-code-for-a-github-app/building-a-cli-with-a-github-app)
3. 앱 설치의 대상 저장소인지, 사용자의 현재 저장소 접근 권한이 있는지 확인한다. **저장소 owner의 명시적 승인 증거**까지 충족해야 `policy`가 통과시킨다. 조직 저장소는 조직 owner 승인만 인정한다. 승인 증거를 얻지 못하면 검사하지 않는다.
4. 로컬 `git log`에서 변경이 있는 커밋 후보를 찾고 SHA를 GitHub 저장소의 실제 이력과 대조한다. GitHub 계정과 연결된 커밋, 공동 작성, 실제 반영된 merge/squash 기여를 정책에 따라 확인한다. PR 생성·리뷰·댓글만으로 통과시키지 않고, 작성자 이름/이메일만 일치해도 통과시키지 않는다. 모호한 squash 기여는 보수적으로 `확인 불가` 처리한다.
5. 파일·Git 이력을 검사한다. 현재 코드의 취약점과 하드코딩된 비밀정보, Git에 올라간 `.env`/비밀정보를 찾는다. 로컬에만 있고 Git에서 제외된 `.env`는 Git 유출 발견 항목이 아니다. `.env`의 값 자체는 결과에 싣지 않는다.
6. 사용자가 웹 검사를 선택하면 열린 로컬 포트 후보를 보여준다. 목록에 없으면 `Other port`로 번호를 받는다. HTTP 확인 후 `<title>`, URL, 응답 상태, 추정 기술을 보여주고 “이 프로젝트의 서비스인가?”에 `Y/N`으로 답하게 한다. 사용자의 확인은 대상 선택이지 코드와 포트 사이의 기계적 증명은 아니다.
7. 코드를 주 분석 대상으로, 선택한 로컬 서비스의 응답/보안 헤더와 접근 가능한 비로그인 URL을 보조 대상으로 검사한다. 로그인 뒤 화면은 사용자가 임시 브라우저 세션에서 직접 로그인할 때만 제한적으로 탐색한다. 자동 폼 제출, 업로드, 알려진 상태 변경 동작, 비밀번호 추측은 하지 않는다. 다만 `GET` 요청도 서버 구현에 따라 부작용이 있을 수 있으므로 PGARD는 무변경을 보장하지 않으며, 탐색 범위와 잔여 위험을 사용자에게 표시한다.
8. 결과를 공통 스키마로 정규화·중복 제거·가림 처리하여 CLI 또는 로컬 웹에 표시한다. 사용자가 요청하면 로컬 경로에 HTML/PDF를 저장한다. 저장 경로를 제외한 검사 세션은 종료 시 메모리에서 해제한다.

#### 로컬 HTTP와 로컬 웹 서버의 방어 경계

- HTTP 검사 대상은 숫자형 `127.0.0.1` 및 명시적으로 허용한 IPv6 loopback으로 제한한다. 임의 호스트명·외부 IP·Unix socket·`file:` 등 스킴은 거부한다. 리다이렉트의 매 단계에서도 loopback/허용 포트 조건을 다시 확인하고, 벗어나면 중지한다. 포트가 열렸다는 사실이나 페이지 제목이 프로젝트 소스 접근을 뜻하지 않는다.
- 포트 후보 탐지는 HTTP 전용 여부를 요청/응답으로 확인한다. 표준 포트 번호로 서비스를 단정하지 않는다. 포트 열람이 OS 권한으로 제한되면 목록이 불완전할 수 있으며 `Other port`를 제공한다.
- 별도 웹 제품의 Node 프로세스는 `127.0.0.1`에만 바인딩한다. 세션마다 임의 토큰을 만들고 모든 로컬 API에 요구한다. `Origin`/`Host` 검사, CSRF 방어, 기본 CORS 차단, 임의 경로 읽기 API 금지, 사용자 선택 프로젝트 경로만 허용한다. 결과 응답에 `Cache-Control: no-store`를 적용한다. 로컬 서버 종료 시 토큰과 인증 브라우저 세션을 폐기한다.
- 프로젝트 코드를 브라우저에 통째로 전달하지 않는다. 필요한 발견 위치와 비밀정보가 가려진 근거만 전달한다. 로컬 웹이 임의 프로젝트 경로를 웹 요청만으로 고를 수 없도록 로컬 런처의 명시적 폴더 선택/확인 단계를 둔다.
- 로컬 웹 제품의 이용약관·개인정보 안내에는 검사 데이터의 일회성 로컬 처리, GitHub 인증/권한 조회와 선택적 advisory 업데이트에 필요한 외부 통신, 사용자가 직접 저장하는 HTML/PDF 보고서의 관리 책임을 명시한다. `GET` 탐색도 잘못 구현된 앱에서는 상태를 바꿀 수 있으므로 UI에서 무변경을 보장하지 않는다.

### 4. 첫 검사 규칙의 구현 순서

| 그룹                     | MVP의 구체적 탐지                                                                                                    | 기본 판정 한계                                                                            |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| SQL Injection            | JS/TS `pg`, `mysql2`, Prisma raw; Go `database/sql`, GORM의 SQL 문자열 조합/보간 → 실행 흐름. 매개변수 바인딩은 구분 | 첫 버전은 확인 가능한 함수/인자 흐름부터. 동적 호출·사용자 정의 래퍼는 `미검사/의심` 가능 |
| XSS                      | `innerHTML`, React `dangerouslySetInnerHTML`, Vue `v-html` 등 위험한 출력으로 입력이 흐르는 경우                     | API 사용 사실만으로 확정하지 않음                                                         |
| SSRF·명령 실행·파일 경로 | 입력 유래 URL의 서버 HTTP 요청, 셸 실행 인자, 업로드·다운로드 경로 조작 가능성                                       | 도메인 허용 정책·경로 정규화 증거를 함께 평가                                             |
| 인증·접근 제어           | 보호 라우트의 인증/권한 검사 패턴, 세션 쿠키 속성, 객체 ID 사용과 권한 검사 여부                                     | 서비스 역할·미들웨어 구성에 따라 `검토 필요`가 많음                                       |
| CSRF·무차별 대입 방어    | 쿠키 인증을 쓰는 변경 요청의 CSRF 방어 설정, 로그인/재설정 코드의 시도 제한                                          | 실제 비밀번호 시도는 하지 않음. 외부 프록시 방어는 코드만으로 배제 불가                   |
| 암호화·비밀정보          | 평문 비밀번호 저장 패턴, 취약 해시/하드코딩 키, 현재 추적 파일과 Git 이력의 비밀정보                                 | 값은 원문 출력 금지. 의심 패턴은 오탐 가능성 표시                                         |
| 웹 응답·헤더             | 선택한 로컬 서비스의 TLS/쿠키/보안 헤더 및 읽기 전용 응답 확인                                                       | 헤더 하나의 부재로 전체 취약성을 확정하지 않음                                            |
| 알려진 취약점            | npm 계열 lockfile과 Go 모듈의 실제 해석된 버전을 로컬 advisory DB와 대조                                             | 발견된 취약 버전과 실제 악용 가능성은 구분                                                |

- OWASP Top 10은 결과 분류에 사용하고, 세부 규칙은 ASVS/WSTG, CWE와 연결한다. `지원 언어`와 `모든 언어에서 모든 규칙 지원`을 혼동하지 않도록 결과에 언어별 검사 범위를 표시한다.
- SQL 라이브러리의 **추천 첫 지원 대상**은 위 다섯 계열이다. TypeORM/Sequelize/Drizzle/Knex 등은 감지만 하고 raw query 분석 미지원 사실을 남긴다. 실제 어댑터 목록은 구현 스택 승인과 함께 확정한다.
- CVE/advisory DB는 서명·출처·버전·갱신일을 확인한 로컬 파일로 대조한다. 업데이트는 명시적으로 실행하고, 업데이트 시 소스/lockfile을 외부에 업로드하지 않는다. DB가 없거나 오래되면 `미검사/데이터 오래됨`을 보이고 안전 판정을 하지 않는다. [OSV 오프라인 모드](https://github.com/google/osv-scanner/blob/main/docs/offline-mode.md)

### 5. 공통 결과 계약(JSON v1)

```json
{
  "schemaVersion": "1.0",
  "scanId": "local-session-id",
  "startedAt": "2026-10-23T00:00:00Z",
  "target": { "repo": "owner/name", "revision": "git-sha", "webOrigin": "http://127.0.0.1:3000" },
  "coverage": [
    { "area": "source:typescript", "status": "completed", "ruleIds": ["PG-SQL-001"], "note": null },
    { "area": "web:authenticated", "status": "not_tested", "ruleIds": [], "note": "no session" }
  ],
  "findings": [
    {
      "id": "stable-fingerprint",
      "ruleId": "PG-SQL-001",
      "title": "입력값이 SQL 문자열에 결합됨",
      "category": "injection",
      "severity": "high",
      "status": "suspected",
      "confidence": "medium",
      "location": {
        "kind": "file",
        "path": "src/api/users.ts",
        "line": 42,
        "url": null,
        "commit": null
      },
      "evidence": "요청값 → 문자열 결합 → query 호출 (값 가림)",
      "impact": "쿼리 구조가 변경될 가능성",
      "recommendation": "값을 매개변수로 분리",
      "references": { "cwe": ["CWE-89"], "owasp": ["A05:2025"], "cve": [] }
    }
  ],
  "advisoryDb": { "version": "bundle-id", "updatedAt": "2026-10-01T00:00:00Z" }
}
```

- `severity`: `critical|high|medium|low|info`; `status`: `confirmed|suspected|informational`; 검사 실패·범위 밖은 finding이 아닌 `coverage.status = not_tested|partial`로 기록한다.
- `confidence`는 증거 강도를 뜻한다. `severity`는 악용 시 영향과 조건을 뜻한다. 둘을 하나의 숫자 점수로 섞지 않는다. 차트는 심각도별 발견 건수와 미검사 영역을 별도로 표시한다.
- `location.path`는 저장소 상대 경로다. 비밀정보 값, 토큰, 쿠키, 절대 파일 경로, DB URL 비밀번호, HTTP 응답의 민감한 본문은 `evidence`에 넣지 않는다. 비밀정보 동일성 비교가 필요하면 세션 한정 식별자만 사용하고 원문/복구 가능한 해시를 내보내지 않는다.
- 동일 규칙·같은 코드 위치·같은 원인의 중복 발견은 하나로 묶고, 해당 근거가 코드와 HTTP 양쪽에 있으면 출처를 보존한다. 보고서는 정확히 이 스키마의 가려진 사본에서 렌더링한다.

### 6. 먼저 검증할 통합 스파이크

1. **owner-only 승인 증거:** GitHub App 설치 사실만으로 owner의 직접 승인을 입증할 수 없다. 조직 설정에 따라 저장소 관리자가 설치할 수 있고, owner가 설치한 앱에 관리자가 저장소를 추가할 수 있는지도 고려해야 한다. 조직 owner만 설치하도록 조직 정책을 요구하거나, 최소한의 조직 읽기 권한을 요청해 설치 권한을 제한하는 옵션은 권한·프라이버시 비용을 비교한다. owner 신원과 특정 저장소 승인 범위를 재검증할 수 있는 증거 설계를 공식 API로 확인해야 한다. 증거 방식이 확정되지 않으면 owner-only를 완화하지 말고 해당 경로의 검사를 막는다. [GitHub 설치 권한](https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party)
2. **기여 판정:** 공동 작성과 squash merge에서 GitHub 계정과 실제 반영 diff를 어떤 API 조합으로 연결할지 테스트 저장소로 검증한다. `git log`의 이름·이메일은 후보 탐색뿐이며 소유권 증명이 아니다.
3. **로컬 웹 실행:** 브라우저가 로컬 파일 전체에 접근하지 않도록 별도 Node 런처의 폴더 선택/검사 권한과 localhost API 방어를 시험한다.
4. **오프라인 advisory 배포:** 로컬 번들 크기, 업데이트 서명/무결성, GitHub/OSV 이용 조건, 오래된 데이터 표기를 확인한다.

### 7. 완료 조건

- 개인 owner 저장소, 타인 개인 저장소, 조직 저장소에서 `owner 승인 + 사용자 현재 접근 + 반영된 기여`를 각각 검사하며 한 조건이라도 빠지면 분석을 시작하지 않는다. owner 승인 증거가 불명확한 조직 경로는 `blocked`를 표시한다.
- PR만 연 사용자와 작성자 이메일만 위조한 커밋은 통과하지 않는다. GitHub 원격 이력에 없는 로컬 커밋도 기여 근거로 쓰지 않는다.
- CLI와 로컬 웹이 같은 fixture와 같은 선택 범위에 대해 동일한 결과 JSON을 생성한다. 각 UI는 차트와 `파일:줄`/URL, 근거, 가이드, `미검사` 범위를 일치하게 보여준다.
- JS/TS/React/Vue/Go 샘플에서 지원 규칙의 실제 양성/음성 사례를 구분한다. 매개변수 바인딩과 단순 위험 API 사용을 일괄 취약점으로 처리하지 않는다.
- Git에 추적되지 않는 로컬 `.env`는 Git 유출로 판정하지 않는다. 과거 Git 이력의 비밀정보는 찾되 화면·JSON·HTML·PDF에 원문이 남지 않는다.
- HTTP 검사는 선택한 loopback 포트만 접속하고 외부 주소로 향하는 리다이렉트는 중단한다. 제목 확인 `Y/N`을 거치지 않은 포트는 프로젝트 웹 검사 대상으로 연결하지 않는다.
- 비로그인 검사는 동작한다. 로그인 뒤 검사는 사용자의 직접 로그인으로만 시작하고 세션 종료 후 폐기한다. 자동 POST/PUT/DELETE나 폼 제출을 하지 않되, GET 탐색도 무변경을 보장하지 않는다고 UI에 표시한다.
- 웹 UI 서버는 loopback에만 바인딩하고, 다른 웹 origin의 API 호출과 세션 토큰 없는 요청을 거부한다. 리포트는 사용자가 고른 경로에만 쓴다.
- 검사 코드에 프로젝트 실행, 의존성 설치, DB 접속, Docker 검사, 성능 측정 경로가 없다. PGARD가 직접 시작하는 외부 네트워크 요청은 GitHub 인증/메타데이터와 사용자가 시작한 advisory 업데이트로 제한한다.

### 8. MVP 이후 후보

- TypeORM/Sequelize/Drizzle/Knex 및 더 많은 Go 프레임워크/ORM 어댑터.
- 안전한 범위를 별도 설계한 로그인 후 탐색과 상태 변경 요청 검사.
- 프로젝트 포트 자동 연관 근거 강화(실행 프로세스, 명시적 설정 등). 페이지 제목+사용자 확인은 MVP의 대상 선택 절차로 유지한다.
- DB 직접 접속, Docker 설정, 성능 검사. 별도 정책·권한·데이터 처리 설계를 거쳐서만 추가한다.

## 에이전트 실행 지침과 소유권

### 사용자 필수 지시 원문

> 1. 독립적인 업무를 명확한 결과와 책임 소재를 가진 병렬적인 하위 담당 에이전트 그룹으로 분할합니다. 에이전트들이 담당 에이전트에게 직접 메시지를 보내 구체적인 문제를 해결하도록 합니다. 결과가 계획을 변경하거나 해결할 수 없는 경우 보고하도록 합니다. 최종 결과를 통합하고 확인합니다

> 2. 두 에이전트에게 구체적인 결과물, 공유된 제약 조건, 상호 보완적인 책임, 그리고 초기 작성 업무를 분담합니다. 두 에이전트 모두 실질적인 작업을 수행하고, 하나는 결과물을 취합하도록 지정합니다. 두 에이전트가 직접 협력하고, 중복 편집 없이 승인된 하위 시스템 내에서 분담 권한을 조정하도록 합니다. 결과물, 업무 범위 또는 다른 에이전트의 소유권 변경 사항은 상위 에이전트에게 보고합니다.

> 3. 리뷰 대기 중인 각 PR마다 별도의 채팅을 생성하여 변경 사항을 검토하고, 발견한 문제를 귀하에게 보고하도록 해주세요. 각 채팅에서 문제 해결을 관리하고, 각 PRo main 브랜치에 안전하게 병합되도록 전체 작업을 조율해주세요. 진행을 가로막는 문제가 있으면 저에게 보고해주세요.

세 번째 항목의 `PRo main`은 문맥상 **각 PR을 main 브랜치에** 병합한다는 뜻으로 해석한다. 이 문서 작업 공간에는 현재 Git 저장소와 리뷰 대기 PR이 없으므로 지금은 PR별 채팅을 만들거나 병합하지 않는다. **향후 실제 리뷰 대기 PR이 생기면** PR마다 별도 채팅을 만들고, 각 채팅에 해당 PR의 독립 리뷰와 수정 확인을 맡긴다. 총괄 담당은 발견 사항을 취합하고, 필수 검증과 저장소의 리뷰·보호 규칙을 확인한 뒤 안전하게 main에 병합되도록 조율한다. 수정 불가, 권한 부족, 충돌, CI 실패 등 진행 차단 사유는 사용자에게 보고한다.

### 향후 구현 작업의 권장 분담

이 분담은 구현 착수 시 실제 저장소 구조와 담당자 수에 맞게 확정한다. 모듈 경계 변경은 먼저 총괄에게 보고한다.

| 작업 묶음                | 담당 권한   | 구체적 산출물                                                                                                                                               | 검증 기준                                                                                                                           |
| ------------------------ | ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 권한·공통 계약·코드 분석 | 구현 담당 1 | `policy`/`github-auth`/`git-history`, `scan-core`, 공통 결과 JSON, JS/TS·React·Vue·Go 규칙과 Git 비밀정보 분석                                              | owner 승인·현 접근·기여 게이트, 지원 규칙의 양성/음성 사례, 비밀정보 가림                                                           |
| 로컬 HTTP·두 UI·보고서   | 구현 담당 2 | `http-local`, `project verify`·범위별 `scan`·`dashboard`·`rules list`·`doctor`의 CLI 진입점, 독립 CLI TUI와 로컬 웹 UI, HTML/PDF 내보내기, 공통 JSON 렌더링 | 권한 모듈과 동일한 판정, 범위별 coverage, loopback 밖 접속 차단, Y/N 연결, 익명 검사·선택 로그인, 상태 변경 요청 없음, UI 결과 일치 |

공유 계약(`ScanRequest`, `ScanResult`, `Finding`, `Coverage`)은 담당 1이 먼저 초안으로 제시하고 담당 2가 소비자 관점의 변경을 직접 제안한다. 계약이 합의되기 전 두 담당이 각자 별도의 결과 형식을 구현하지 않는다. 구현 담당 2는 검사 규칙/권한 파일을 편집하지 않고, 담당 1은 UI/보고서 파일을 편집하지 않는다. 경계 밖 변경은 해당 소유자와 직접 협의하고 총괄에게 알린다. 각 담당은 자신의 결과를 테스트하고 PR 단위로 검토 가능하게 제출한다.

### 구현 전 차단 가능성이 있는 검증

- **owner 승인 증빙:** GitHub App 설치 여부만으로 owner의 직접 승인을 증명할 수 없을 수 있다. 공식 API 및 실제 조직/개인 저장소 설정으로 증빙 절차를 먼저 검증한다. 증거가 없으면 검사 게이트에서 차단하며 이 정책을 임의 완화하지 않는다.
- **기여 연결:** squash merge·공동 작성에서 계정과 실제 반영된 변경을 연결하는 자료가 부족하면 통과시키지 않고 판정 불가로 표시한다.
- **로컬 제품 보호:** 로컬 웹 서버 자체의 접근 통제, 리다이렉트의 loopback 제한, 인증 세션 폐기를 시험한다.
- **CVE 데이터:** 오프라인 취약점 DB의 출처·무결성·업데이트와 오래된 데이터 표시를 결정한다.

검증 결과가 제품 약속이나 일정·범위를 바꾸거나 해결되지 않는 경우, 담당자는 다른 담당과 총괄에게 즉시 알린다. 총괄은 사용자에게 영향과 선택지를 보고한다.
