# 보안 설계: `pgard web`에서 프로젝트 고르기

> **참고:** 이 문서는 [`WEB_PROJECT_PICKER_DESIGN.md`](WEB_PROJECT_PICKER_DESIGN.md)(영문)의 한국어 번역입니다. 기준 문서는 영문판이며, 내용이 다르면 영문판이 맞습니다. 프로젝트 [README](../README.ko.md)([English](../README.md))와 [문서 목록](README.ko.md)도 참고하세요.

상태: 검토용 설계([#355](https://github.com/JadenMeister/pgard/issues/355), M8-3). 이 문서의 내용은 아직 아무것도 구현되지 않았습니다. 검토가 끝나면 M8-4에서 구현합니다.

"현재"에 대한 설명은 작성 시점의 코드(`apps/local-web/src/server`, `apps/cli/src/commands/dashboard.ts`, `packages/policy`, `packages/git-history`, `packages/result-store`)를 기준으로 합니다. 이 설계가 아직 코드에 없는 것에 기대는 곳에는 **M8-4 요구사항**이라고 표시했습니다. 현재 동작의 기준은 README이며, 이 설계는 README의 일부 문장을 바꿉니다([M8-4의 README 변경](#9-m8-4의-readme-변경) 참고).

## 1. 목표와 비목표

### 목표

1. `pgard web`은 프로젝트 없이 시작합니다. 사용자는 검색하거나 폴더를 페이지에 끌어다 놓아 프로젝트를 고릅니다.
2. 브라우저는 사용자가 어느 프로젝트를 뜻하는지 알려 주는 **신호**일 뿐입니다. 경로를 보내지 않고 파일 내용도 보내지 않습니다.
3. 로컬 서버가 **사용자가 정한 검색 범위** 안에서 이름이 맞는 Git 저장소를 찾고, 실제 경로와 remote를 보여 줍니다. 사용자가 이를 확인합니다.
4. 확인 뒤에는 같은 5가지 권한 확인(저장소, GitHub 신원, 소유자 승인, 현재 접근, 기여)이 실행됩니다. 잘못된 폴더가 곧바로 검사로 이어지는 일은 없습니다.
5. 증거가 불분명하면 막고, 이유와 해결 방법을 알려 줍니다. 권한 확인은 절대 느슨하게 하지 않습니다.
6. 코드, 경로, 결과는 로컬에 머뭅니다. 새로 어디로 보내는 것은 없습니다.

### 비목표

- 피커를 위해 브라우저나 서버가 파일 또는 디렉터리의 내용을 읽지 않습니다. 읽는 것은 디렉터리 항목 이름과, 기존의 허용 목록 Git 실행기를 통한 Git 메타데이터뿐입니다.
- 브라우저에서 입력하는 절대 경로, 네이티브 폴더 대화상자, `showDirectoryPicker`는 쓰지 않습니다.
- 기본값으로 원격 호스트, 네트워크 공유, 이동식 볼륨은 검사하지 않습니다.
- `pgard dashboard`는 바꾸지 않습니다. 계속 터미널의 현재 디렉터리의 Git 루트에 고정되고, 터미널에서 확인합니다.
- 권한 확인의 순서, 이유, 캐시 규칙(캐시하지 않음)은 바꾸지 않습니다.
- 대시보드는 여전히 검사 결과를 저장하지 않습니다.
- 이미 같은 OS 사용자 권한으로 코드를 실행하는 공격자는 범위 밖입니다(그 공격자는 폴더를 직접 읽을 수 있습니다). 이 설계는 그런 공격자가 더 쉽게 일하게 만들지 않는 데까지만 신경 씁니다. 남는 위험은 [2절](#2-위협-모델)에 적었습니다.

## 2. 위협 모델

보호 대상: 사용자의 소스 코드와 Git 기록, 컴퓨터에 있는 경로와 저장소 이름, GitHub 로그인(OS 키체인에 있으며 브라우저로 보내지 않음), 권한 확인 결정.

신뢰 경계: `pgard web`을 시작한 터미널(신뢰함, 사용자가 거기서 확인), 세션 URL을 받은 브라우저 탭(토큰이 있을 때만 신뢰), 그 밖의 모든 탭, 웹 페이지, 로컬 프로세스(신뢰하지 않음), 디스크에 있는 모든 저장소의 내용(`.git/config` 포함, 신뢰하지 않는 데이터).

현재 서버가 이미 하는 일(`apps/local-web/src/server/middleware/security.ts`, `create-server.ts`에서 확인):

- 빈 포트의 `127.0.0.1`에만 바인딩합니다. `Host`는 정확히 `127.0.0.1:<port>`여야 합니다(아니면 421).
- 모든 `/api/` 호출에 `x-pgard-token` 헤더가 필요합니다(무작위 32바이트, `timingSafeEqual`로 비교). 다른 `Origin`이나 `same-origin`/`none`이 아닌 `Sec-Fetch-Site`는 거부합니다. 상태를 바꾸는 호출은 정확한 `Origin`을 보내야 합니다. API는 CORS 헤더를 보내지 않습니다.
- 모든 응답에 `Cache-Control: no-store`, `default-src 'none'`과 `connect-src 'self'`를 가진 CSP, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy: same-origin`이 붙습니다.
- 토큰은 URL 조각(fragment)으로 전달되고, 페이지는 주소창에서 지운 뒤 메모리에만 둡니다.
- 요청 본문은 16 KiB로 제한되고 `application/json`이어야 합니다.
- 서버는 요청별 로그를 쓰지 않습니다(실행기가 시작 문구와 종료 문구 한 줄만 출력).
- 프로젝트 루트는 서버 수명 동안 고정이고(`ApiContext.projectRoot`), 경로를 받는 라우트는 없습니다.

UI는 프로젝트 이름을 `document.title`, `location`, `history.pushState`, `localStorage`의 키나 값에 넣지 않습니다. 검색 입력란에는 `autocomplete="off"`, `autocapitalize="off"`, `spellcheck="false"`를 붙여 브라우저가 이름을 양식 기록에 저장하거나 맞춤법 검사 서비스로 보내지 않게 합니다. GitHub 링크는 `rel="noopener noreferrer"`를 씁니다(페이지 수준의 `Referrer-Policy: no-referrer`도 이미 적용됨). 표시 경로는 홈 폴더를 `~`로 줄이고 `sanitizeDisplayText`를 거칩니다. 경로는 사용자가 확인한 곳, 즉 지금의 `pgard dashboard`와 같은 터미널에만 나옵니다. 남는 위험: 브라우저의 끌어다 놓기 기능이나 OS가 놓은 폴더 이름을 자체 캐시에 남길 수 있고, PGARD는 이를 통제할 수 없습니다.                                                                                      |
| T7  | **경로를 확인한 시점과 검사 시점 사이의 TOCTOU**                                               | 서버는 브라우저가 설명하는 후보를 믿지 않습니다. 후보는 서버가 쥐고 있는 기록(무작위 128비트 id)이며 `realRoot`, 루트와 `.git`의 `dev`/`ino`, remote에서 읽은 저장소 `owner/name`, 시각을 담습니다. `confirm`은 검색이 끝난 지 10분 안에만 받고(`PROBE_CONFIRM_WINDOW_MS`가 선례이며, 시계가 뒤로 가면 닫히는 쪽으로 처리), 다시 **재검사**합니다. 같은 `realpath`, 같은 `dev`/`ino`, 여전히 범위 안, 여전히 Git 루트, 여전히 같은 `owner/name`, UI가 보여 준 지문(`shown`)과 서버의 지문이 같음. 하나라도 다르면 `candidate_changed`이며 아무것도 선택되지 않습니다. 검사를 시작할 때 서버는 `runScan` 호출 전에 프로젝트 기록을 다시 비교하고, `runScan` 자체의 권한 확인이 같은 경로에서 다시 실행됩니다. 이 확인이 돌려준 `owner/name`이 확인된 것과 다르면 거부합니다. **M8-4 요구사항:** 프로젝트 기록과 검사 전 비교는 현재 없습니다. 남는 위험: 마지막 비교와 분석의 파일 읽기 사이에 같은 사용자로 실행되는 프로세스가 디렉터리를 바꿔치기할 수 있습니다. 그 사용자는 이미 파일을 읽을 수 있으므로 권한 상승이 아니며, 다른 사용자의 경우는 T1의 소유자와 권한 확인이 막습니다. 분석은 이미 파일과 디렉터리로의 심볼릭 링크를 건너뜁니다(README "증분 검사").                                                       |
| T8  | **remote가 github.com이 아닌 저장소**(없거나, 서로 다른 여러 개이거나)                         | 로컬 저장소 확인(`packages/policy/src/checks.ts`의 `verifyRepository`)이 기준입니다. 모든 remote의 모든 fetch/push URL이 같은 github.com 저장소로 해석되어야 하고, 아니면 이유는 고정 문구입니다. 피커는 이런 후보를 **막힌 채, 선택 불가**로 이유와 해결 방법과 함께 보여 줍니다([5절](#5-ui-상태) 참고). remote URL은 브라우저로 보내지 않고, github.com remote일 때의 `owner/name`과 그 밖의 경우의 고정 이유만 보냅니다. GitHub Enterprise 호스트, 비슷하게 생긴 호스트, 미러도 github.com이 아닌 remote이므로 CLI와 똑같이 막힙니다. **M8-4 요구사항:** `verifyRepository`는 `@pgard/policy`에서 내보내지지 않습니다. 네트워크도 로그인도 없는 로컬 전용 "저장소 점검" 함수를 내보내 피커와 권한 확인이 같은 코드를 쓰게 합니다. Git은 기존의 강화된 실행기(`core.fsmonitor=false`, `core.hooksPath`를 null 장치로, 시스템/전역 설정 무시, 허용 목록 하위 명령)로 실행되므로, 악의적인 `.git/config`가 프로그램을 실행시킬 수 없습니다.                                                                                                                                                                                                                                                                                 |
| T9  | **최근 목록 파일 변조**(또는 설정 파일 변조)                                                   | 목록은 *힌트*이지 권한이 아닙니다. 항목은 불러올 때마다 새 검색 결과처럼 검증합니다. 심볼릭 링크가 아닌 `0700` 폴더 안의, 소유자 전용 권한의 사용자 소유 일반 파일이어야 하고, 64 KiB와 20개로 제한하며, 엄격한 스키마로 파싱합니다(알 수 없는 `schemaVersion` 메이저는 결과 저장소처럼 무시하고 덮어쓰지 않음). 이어서 모든 항목이 T3~T8의 후보 검사를 모두 통과해야 하고, 저장된 표시 문구가 아니라 새로 얻은 실제 경로와 remote로 표시되며, 여전히 사용자의 확인과 5가지 권한 확인이 필요합니다. 따라서 변조된 항목은 기껏해야 사용자가 보고 거절하는 후보로 나타날 뿐입니다. 설정 파일은 범위를 넓힐 수 있으므로 같은 파일 보호에 더해, 루트를 실행할 때마다 다시 검증하고 **서버가 시작되기 전에 터미널 프롬프트로 보여 줍니다**. 브라우저는 이를 바꿀 수 없습니다. 서명은 쓰지 않습니다. 같은 사용자의 공격자는 PGARD가 보관할 어떤 키도 읽을 수 있고, 키체인 키는 이득 없이 프롬프트만 늘립니다.                                                                                                                                                                                                                                                                                                                      |
| T10 | **프로세스 목록에 보이는 경로**                                                                | `ps`는 모든 로컬 사용자의 프로세스 인자를 보여 줍니다. 현재 `pgard dashboard`는 실행기에 `--project-root <abs>`를 넘기며, 이는 기존 동작입니다. 피커는 argv에 경로를 더하지 않습니다. 범위 루트는 설정 파일에 있고 `pgard web`은 경로 인자 없이 실행기를 시작합니다.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| T11 | **악의적인 폴더 이름이 UI에 도달**(XSS, 문구 위장)                                             | 이름과 경로는 기존 React 클라이언트가 텍스트로 렌더링하며(`dangerouslySetInnerHTML` 없음), 그 전에 서버에서 `sanitizeDisplayText`를 거칩니다(제어 문자와 양방향 문자는 공백이 됨). CSP는 인라인 스크립트를 금지합니다. 확인 단계에서는 전체 실제 경로를 줄여 쓰지 않고 줄바꿈하는 고정폭 블록으로 보여 줍니다.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| T12 | **프로젝트를 바꿀 때 상태가 섞임**                                                             | 프로젝트를 선택하면 이전 프로젝트에 묶인 모든 것을 초기화합니다. 권한 확인 기록(`setAuth`, 포트 탐색도 중단), 확인된 대상, 마지막 탐색, 검사 상태와 결과(보고서 내려받기가 이전 프로젝트의 보고서를 주지 못하게). 검사 중에는 선택을 거부합니다(`scan_in_progress`). `GET /api/session`과 모든 상태 변경 요청에 `projectEpoch` 카운터를 두어, 오래된 화면의 두 번째 탭이 새 프로젝트에 작용하는 대신 `project_changed`로 실패하게 합니다. **M8-4 요구사항:** 현재는 바꿀 수 있는 프로젝트도 epoch도 없습니다.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |

## 3. API 스케치

모든 라우트는 `API_ROUTES`에 추가합니다(정확한 `"METHOD /path"` 키이므로 경로 매개변수가 없고, id는 쿼리 문자열이나 본문에 둡니다). 모두 핸들러 전에 기존의 Host, Origin, 토큰 확인을 거칩니다. 모든 본문은 최대 16 KiB의 `application/json`입니다(기존 제한이며 피커 본문은 훨씬 작음). 오류는 기존 형식 `{ "error": { "code", "message" } }`에 고정된 번역 가능한 메시지를 씁니다.

프로젝트가 선택되지 않았을 때, 프로젝트가 필요한 기존 라우트(`/api/auth/*`, `/api/ports*`, `/api/target*`, `/api/scan*`, `/api/reports/*`)는 `409 no_project`를 돌려줍니다.

| 라우트                                 | 요청                                         | 응답                                                                                                                                      | 비고                                                                                                                                                                                                            |
| -------------------------------------- | -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/session`(확장)               | 없음                                         | 기존 필드와 `mode: "fixed" \| "picker"`, `project: { name } \| null`, `projectEpoch: number`                                              | `projectName`은 `project`로 대체됩니다. `fixed`는 `pgard dashboard`입니다.                                                                                                                                      |
| `GET /api/picker/scope`                | 없음                                         | `{ roots: [{ id, label, enabled }], limits, partialSupport }`                                                                             | `label`은 `~/code` 같은 형태이며 정리됩니다. `id`는 서버가 만든 불투명 값입니다.                                                                                                                                |
| `POST /api/picker/scope/toggle`        | `{ rootId, enabled, epoch }`                 | `{ roots }`                                                                                                                               | 세션 한정 켜기/끄기. 경로를 추가하거나 바꿀 수 없습니다.                                                                                                                                                        |
| `POST /api/picker/search`              | `{ source: "drop" \| "typed", name, epoch }` | `{ searchId, status: "running" }`                                                                                                         | `name`은 T3의 한 조각, 최대 255단위. `typed`는 항목 이름의 접두사나 부분 문자열을 대소문자 무시로 비교하고, `drop`은 정확한 이름(대소문자 접기, NFC)과 비교합니다. 검색을 하나 시작하고 이전 검색은 취소합니다. |
| `GET /api/picker/search?id=<searchId>` | 없음                                         | `{ status: "running" \| "done" \| "partial" \| "cancelled" \| "failed", visited, candidates: Candidate[], skipped: { reason, count }[] }` | `GET /api/auth`처럼 폴링합니다. `id`는 128비트 무작위입니다. 모르는 id는 404 `unknown_search`.                                                                                                                  |
| `POST /api/picker/search/cancel`       | `{ searchId }`                               | `{ status }`                                                                                                                              |                                                                                                                                                                                                                 |
| `GET /api/picker/recent`               | 없음                                         | `{ entries: RecentEntry[] }`                                                                                                              | 호출할 때마다 다시 검증합니다(T9).                                                                                                                                                                              |
| `POST /api/picker/recent/remove`       | `{ entryId, epoch }`                         | `{ entries }`                                                                                                                             | 파일에서 삭제합니다.                                                                                                                                                                                            |
| `POST /api/picker/confirm`             | `{ candidateId, shown, epoch }`              | `{ project: { name }, projectEpoch }`                                                                                                     | 재검사(T7), 선택, 상태 초기화(T12). 권한 확인은 실행하지 않습니다. 그 뒤 페이지가 기존 `POST /api/auth/verify`를 호출합니다.                                                                                    |
| `POST /api/picker/clear`               | `{ epoch }`                                  | `{ projectEpoch }`                                                                                                                        | 프로젝트 없음으로 돌아가며 같은 초기화를 합니다. 검사 중에는 거부합니다.                                                                                                                                        |

```ts
interface Candidate {
  candidateId: string; // 무작위 128비트, 서버가 보관, 10분간 유효
  name: string; // 정리됨, 120자 이하
  displayPath: string; // 실제 경로, "~"로 줄임, 정리됨, 400자 이하
  shown: string; // realRoot + dev/ino + owner/name의 지문. confirm 때 되돌려 보냄
  remote:
    | { status: "github"; repo: string } // "owner/name"
    | { status: "none" | "not_github" | "ambiguous" | "unreadable" };
  selectable: boolean;
  blocked: null | {
    code: PickerBlockCode;
    reason: string; // 고정 문구(영어, UI가 코드를 영어/한국어로 대응)
    fix: string; // 고정 문구
  };
  source: "scope" | "recent";
}

interface RecentEntry extends Candidate {
  lastUsedAt: string;
} // ISO 시각
```

`Candidate.remote.status`와 `blocked`는 공유하는 로컬 저장소 확인에서 나옵니다. github.com remote일 때는 `owner/name`만 돌려주고 URL이나 remote 이름은 돌려주지 않습니다.

### 제한

| 제한                        | 값                                                    |
| --------------------------- | ----------------------------------------------------- |
| 폴더 이름                   | UTF-16 단위로 1~255, 한 조각                          |
| 범위 루트 아래 깊이         | 4(하드 최대 6)                                        |
| 검색당 방문 디렉터리 항목   | 50,000                                                |
| 디렉터리 하나에서 읽는 항목 | 5,000                                                 |
| 반환 후보                   | 20                                                    |
| 검색 데드라인               | 소프트 5초(`partial`), 하드 8초(Worker 종료)          |
| 검색                        | 세션당 동시 1개, 초당 최대 1회(`429 search_too_soon`) |
| 후보 유효 시간              | 10분                                                  |
| 최근 목록                   | 20개, 파일 64 KiB                                     |
| 요청 본문                   | 16 KiB(기존)                                          |

## 4. 세션과 토큰 결합

새 자격 증명 없이 현재 방식을 재사용합니다.

- 서버 실행마다 토큰 하나를 URL 조각으로 한 번 출력하고, 페이지가 메모리에 두었다가 `x-pgard-token`으로 보냅니다. 후보 id, 검색 id, 최근 목록을 포함해 피커의 어떤 것도 토큰 없이는 쓸 수 없습니다.
- 후보 id와 검색 id는 128비트 무작위이며 토큰이 있을 때만 의미가 있고(`SessionState`처럼 세션별 서버 상태), 디스크에 저장하지 않으며, 서버가 멈추면 사라집니다(`clearSessionState`).
- 새 상태는 `SessionState`에 둡니다. 선택된 프로젝트 기록, 현재 검색, 후보 맵, `projectEpoch`. 종료 시 나머지와 함께 `clearSessionState`로 지웁니다.
- Origin과 Host 규칙은 그대로입니다. 피커는 쿠키, 이름이나 경로를 위한 `localStorage`, 두 번째 토큰을 추가하지 않습니다.
- **M8-4 요구사항:** `ApiContext.projectRoot`를 세션 상태에서 읽는 값(확인 전까지 null)으로 바꿉니다. `startScan`, `startVerify`, `recheckOwnerApproval`, 보고서 라우트는 호출 시점에 값을 읽고, 프로젝트 기록을 비교하고(T7), null이면 `no_project`로 거부해야 합니다.
- **M8-4 요구사항:** `projectEpoch`는 confirm과 clear 때마다 증가하며, 프로젝트와 관련해 상태를 바꾸는 라우트(`/api/picker/*`, `/api/auth/verify`, `/api/scan`)가 이를 함께 보내 오래된 두 번째 탭을 거부합니다. 현재는 어떤 라우트에도 없습니다.
- 계정 결합은 그대로입니다. 로그인한 GitHub 계정은 프로젝트와 독립적입니다. 프로젝트가 바뀌면 권한 확인 기록이 초기화되므로 다음 확인은 처음부터 실행됩니다.

`pgard web`(새 명령)은 `pgard dashboard`처럼 대화형 터미널이 필요합니다. 서버를 시작하기 전에 검색 범위 루트를 출력하고 `Search these folders for projects? [y/N]`를 묻습니다(터미널이 없으면 종료 코드 2). 명령줄에 경로를 넘기지 않습니다.

## 6. 저장 형식

폴더: `resolveStoreDirectory()`가 주는 기존 사용자별 앱 데이터 디렉터리(`~/Library/Application Support/pgard`, `$XDG_DATA_HOME/pgard` 또는 `~/.local/share/pgard`, `%LOCALAPPDATA%\pgard`) 안의 새 하위 폴더 `web/`입니다. `repos/`를 지워도 안전하고 서로 무관하도록 분리합니다. 프로젝트 안에는 절대 두지 않습니다. 보호는 결과 저장소를 따릅니다. macOS와 Linux에서 폴더 `0700`, 파일 `0600`, 폴더와 파일 모두 심볼릭 링크를 따라가지 않음, 같은 폴더의 임시 파일에 (배타적 생성으로) 쓴 뒤 이름 변경, 파싱 전 크기 제한, 지원하지 않거나 더 새로운 `schemaVersion`은 알림과 함께 무시하고 덮어쓰지 않음. Windows에서는 권한 비트가 적용되지 않고 프로필 폴더의 ACL을 상속하며 확인하지 않습니다(결과 저장소와 같음).

**M8-4 요구사항:** `packages/result-store/src/store.ts`의 안전한 파일 도우미는 현재 저장소 클래스의 비공개 멤버입니다. 다시 구현하지 말고 추출하거나(또는 두 파일을 `@pgard/result-store`의 모듈로 추가) 재사용하세요.

`web/settings.json`:

```json
{
  "schemaVersion": "1.0",
  "searchRoots": [{ "path": "/Users/alice/code" }],
  "acceptedDefaultHome": false
}
```

- `searchRoots[].path`는 추가 시점의 절대 `realpath`입니다. 실행할 때마다 다시 검증합니다(존재, 디렉터리, 사용자 소유, 깊이 규칙). 유효하지 않은 루트는 그 세션에서 빼고 터미널에 알립니다.
- 루트는 터미널에서만 바꿉니다: `pgard web scope list | add <folder> | remove <folder>`. `add`는 실제 경로를 보여 주고 확인을 받습니다.
- 제한은 설정이 아니라 상수입니다(질문 Q2 참고).

`web/recent-projects.json`:

```json
{
  "schemaVersion": "1.0",
  "entries": [
    {
      "id": "r1",
      "path": "/Users/alice/code/shop",
      "repo": "alice/shop",
      "lastUsedAt": "2026-10-28T09:00:00Z"
    }
  ]
}
```

- 최대 20개, 최신순, `realpath`당 하나. 성공적인 **confirm** 뒤에만 기록합니다(검색 뒤에는 기록하지 않고, 이후 권한 확인이 막더라도 확인된 프로젝트만 기록).
- `repo`는 표시용 힌트일 뿐이고, 표시되는 owner/name은 항상 새로 읽은 값입니다.
- 검사 결과와 달리 절대 경로를 담습니다. 따라서 README에 예외로 적고, `pgard history clear --all`로 지워지며, `--no-store` 또는 `PGARD_NO_STORE=1`일 때는 기록하지 않습니다(그 세션에서는 최근 목록이 비어 있음).

## 7. 무엇을 기록하는가

- **서버:** 현재처럼 요청별로는 아무것도 기록하지 않습니다. 접근 로그도 디버그 로그도 없습니다. 터미널 출력은 시작과 종료 문구, 그리고 사용자가 요청한 시작 전 범위 프롬프트뿐입니다.
- **어디에도 기록하지 않는 것**(터미널, 파일, 오류 문구, 충돌 메시지, 원격 측정, API 오류): 검색하거나 놓은 폴더 이름, 범위 루트, 후보 경로, remote URL, 후보 id와 검색 id, 토큰.
- **메모리에만 있고 종료 시 폐기:** 검색, 후보 맵, 선택된 프로젝트 기록, `visited` 같은 카운터.
- **API 오류**에는 고정 코드와 고정 메시지만 담습니다.
- **디스크:** [6절](#6-저장-형식)의 두 파일뿐입니다. 대시보드는 결과를 저장하지 않습니다.
- **브라우저는 기록하지 않음:** 이름과 경로를 URL, 제목, `localStorage`, 콘솔에 넣지 않습니다. 페이지가 이미 저장하는 것은 UI 언어 선택뿐입니다.

## 8. M8-4 테스트 계획

단위 및 통합 테스트(vitest, 기존 테스트처럼 `ServerDeps` 주입, 실제 GitHub와 실제 키체인 없음):

1. **미들웨어 재사용.** 각 피커 라우트는 다음을 거부합니다. 토큰 없음, 잘못된 토큰, 잘못된 `Host`(`localhost`와 리바인딩된 이름 포함), 다른 `Origin`, POST의 `Origin` 누락, `Sec-Fetch-Site: cross-site`, 잘못된 content type, 16 KiB 초과 본문. 오류를 포함해 어떤 응답에도 CORS 헤더가 없습니다.
2. **이름 검증.** 잘못된 이름 표: 빈 문자열, `.`, `..`, `a/b`, `a\b`, `C:`, NUL, 제어 문자와 양방향 문자, 끝의 점이나 공백, `CON`, 256단위, 짝 없는 서로게이트. 같은 이름의 NFC와 NFD는 같은 디렉터리와 일치합니다.
3. **걷기.** 임시 디렉터리의 픽스처 트리: 깊이 제한, 항목 제한, (주입한 시계로) 데드라인이 `partial`을 줌, 제외 목록, 찾은 저장소 안에서 중첩 검색 없음, 범위 밖 저장소로의 심볼릭 링크는 제시하지 않음, 심볼릭 링크 순환, 후보의 상위가 심볼릭 링크인 경우, 사용자 소유가 아닌 디렉터리(POSIX, `lstat`을 스텁), 다른 `dev`(스텁)에는 들어가지 않음.
4. **Worker 종료.** 돌아오지 않는 걷기 스텁이 하드 데드라인에 종료되고 서버는 다른 라우트에 계속 응답합니다.
5. **대소문자 구분 없는 파일 시스템.** CI의 `macos-latest`와 `windows-latest` 작업(기존 check 매트릭스에 둘 다 있음)에서 실행합니다. `Shop` 이름이 `shop`을 찾음, 대소문자가 다른 범위 접두사 검사, 경로 문자열 대신 `dev`/`ino` 동일성 사용, 대소문자 구분 Linux 디스크에서 대소문자만 다른 두 디렉터리가 있으면 둘 다 반환. Windows: junction과 재분석 지점은 건너뜀, `\\?\`와 UNC 루트는 거부, 8.3 짧은 이름은 같은 동일성으로 해석되거나 막힘, `ino === 0`이면 `identity_unavailable`.
6. **후보 검사.** 차단 코드마다 픽스처 저장소: remote 없음, `https://example.com/o/r.git`, GitHub Enterprise 호스트, 서로 다른 저장소를 가리키는 remote 두 개, 자격 증명이 들어 있는 remote URL(응답에 자격 증명도 URL도 없어야 함), 커밋 없음, alternates, `core.fsmonitor`, 훅, `core.sshCommand`가 든 악의적인 `.git/config`(절대 실행되면 안 됨, 표식 파일이 생기지 않는지 확인).
7. **TOCTOU.** 검색 뒤에 디렉터리 이름 변경, 심볼릭 링크로 교체, 다른 저장소로 교체, remote 변경, 10분 경과(주입한 시계, 시계가 뒤로 간 경우도): 각각 `candidate_changed` 또는 `candidate_expired`가 나오고 아무것도 선택되지 않습니다. confirm과 `POST /api/scan` 사이에 디렉터리를 바꿔치기하면 검사가 거부됩니다. 권한 확인 결과의 `owner/name`이 다르면 거부됩니다.
8. **상태 초기화.** 두 번째 프로젝트를 confirm하면 권한 확인, 대상, 탐색, 검사, 보고서가 지워지고, 이전 보고서 내려받기는 `409`, 검사 중 confirm은 `scan_in_progress`, 오래된 `epoch`는 `project_changed`, 첫 confirm 전의 라우트는 `no_project`를 돌려줍니다.
9. **권한 확인 불변.** confirm 뒤 `POST /api/auth/verify`는 수정 없는 `authorizeProject`를 5가지 확인 모두와 함께 실행하고, 이전에 허용된 결과가 오래되어도 검사 시 다시 실행됩니다. App 설치 밖의 비공개 저장소는 기존 설치 안내와 함께 `current_access` 실패로 끝납니다.
10. **파일.** 설정과 최근 파일은 `0700` 안에 `0600`으로 만들어지고, 심볼릭 링크를 거치거나 그룹/전체 쓰기 가능이면 거부하며, 너무 크거나 잘못되었거나 알 수 없는 메이저 `schemaVersion`이면 무시하고 덮어쓰지 않고, 21개째 항목은 잘리고, 변조된 `path`(저장소가 아닌 곳, 심볼릭 링크, 다른 사용자의 폴더, 범위 밖 경로)는 막힌 채 표시되고 선택할 수 없으며 표시 문구는 새로 읽은 값입니다. `--no-store`는 아무것도 쓰지 않고, `history clear --all`은 둘 다 지웁니다.
11. **누출 없음.** 눈에 띄는 이름과 경로로 위 시나리오를 실행하면서 stdout, stderr, 던져진 메시지, 모든 API 응답을 캡처합니다. 의도된 응답 필드(`displayPath`, `name`, `repo`)를 제외하면 이름, 경로, remote URL, 토큰이 어디에도 없어야 합니다. 빌드된 클라이언트 번들과 `index.html`은 이름을 `document.title`, `location`, `localStorage`에 쓰지 않습니다(DOM 테스트). 검색 입력란에 T6의 세 속성이 있습니다.
12. **클라이언트.** 놓기 핸들러는 `webkitGetAsEntry().name`과 `isDirectory`만 읽고 `getAsFile`, `createReader`, `FileReader`는 절대 호출하지 않습니다(스파이로 테스트). 폴더가 아닌 파일을 놓으면 "파일이 아니라 폴더를 놓으세요"를 보여 줍니다. 5절의 막힘 상태가 영어와 한국어로 이유와 해결 방법을 보여 줍니다.

기존 가짜 GitHub 주입을 쓰는 종단 간 테스트(실제 계정 없음, 테스트에서 `pgard web`을 실제 계정에 실행하지 않음):

13. 이름으로 저장소를 골라 confirm하고, 5가지 확인을 통과하고, 검사하고, 보고서를 내려받습니다.
14. **App 설치 밖의 비공개 저장소:** 고르고 confirm하면 막힌 `current_access` 상태에 이르고, 설치 안내가 보이며, 아무것도 검사되지 않습니다.
15. github.com이 아닌 remote의 저장소를 고르면: 피커에서 이유와 함께 막히고 권한 확인에 이르지 않습니다.
16. 이름이 같은 두 폴더 중 잘못된 것을 고르면: 확인 화면이 다른 경로와 `owner/name`을 보여 주고 사용자가 뒤로 갑니다.

## 9. M8-4의 README 변경

현재 README는 "브라우저는 프로젝트 파일을 고르거나 읽을 수 없습니다. 프로젝트 루트는 대시보드가 시작될 때 고정됩니다"와 "브라우저는 경로를 전혀 제공하지 않습니다"라고 말합니다. M8-4 이후 이 문장은 `pgard dashboard`에만 해당합니다. `pgard web`에 대해서는 README가 대신 다음을 말해야 합니다. 브라우저는 폴더 이름만 보내고, 서버가 사용자의 범위를 검색하고, 사용자가 실제 경로와 remote를 확인하고, 5가지 확인이 실행되며, 이를 위해 파일 내용은 읽지 않는다. 또한 최근 목록 파일과 설정 파일을 "저장된 결과"와 "개인정보" 절에 절대 경로를 담는, 로컬에만 있고 업로드되지 않는 파일로 추가하고 `pgard history clear --all` 설명을 갱신해야 합니다.

## 10. 소유자에게 묻는 질문

- **Q1. 기본 범위.** 처음 실행할 때 홈 폴더 전체(제외 목록 포함)를 제안할까요, 아니면 사용자가 `pgard web scope add`로 폴더를 추가할 때까지 비워 둘까요? 이 설계는 첫 실행 때 터미널에서 홈을 보여 주고 확인받는 방식(`acceptedDefaultHome`)을 제안합니다. 범위가 비어 있으면 처음 만났을 때 끌어다 놓기가 쓸모없기 때문입니다. 대안은 더 좁은 기본값(예: 있을 때 `~/code`, `~/projects`, `~/dev`)입니다.
- **Q2. 제한.** 깊이 4, 50,000개 항목, 후보 20개, 5초가 적당한가요? 사용자가 바꿀 수 있어야 하는 것이 있나요? 이 설계는 상수로 둡니다.
- **Q3. 브라우저에서 루트 추가.** 이 설계는 루트를 추가하거나 바꾸는 것을 터미널에서만 허용하고(브라우저는 기존 루트를 켜고 끌 수만 있음), 침해된 페이지가 범위를 넓히지 못하게 합니다. 이대로 괜찮을까요, 아니면 브라우저가 루트를 요청하고 터미널에서 확인하는 방식을 허용할까요?
- **Q4. 명령 이름.** `pgard web`은 `pgard dashboard` 옆의 새 명령입니다. `pgard dashboard`를 프로젝트 고정 명령으로 유지할까요, 대체할까요? 이 설계는 둘 다 유지합니다.
- **Q5. 최근 목록과 `--no-store`.** 이 설계는 `--no-store`나 `PGARD_NO_STORE=1`일 때 최근 목록을 쓰지 않습니다. 프로젝트 경로 목록에도 "아무것도 저장하지 않음"이 맞는 해석일까요, 아니면 최근 목록에 별도 스위치를 둘까요?
- **Q6. Windows.** Node 기본 기능으로는 소유자 확인도, 믿을 만한 네트워크 드라이브 감지도 할 수 없습니다. M8-4 첫 릴리스에서 문서화된 남는 위험을 받아들일까요, 아니면 피커의 첫 릴리스를 macOS와 Linux로만 제한할까요?
- **Q7. 범위 밖의 최근 항목.** 여기서는 `outside_scope`로 막습니다(엄격). 사용자가 전에 확인했으므로 허용할까요?
- **Q8. 같은 사용자 공격자와 confirm에서 분석 사이의 바꿔치기.** 그 공격자는 이미 파일을 읽을 수 있으므로 범위 밖으로 받아들였습니다. 이것이 의도한 경계가 맞는지 확인해 주세요.
- **Q9. 걷기를 Worker 스레드로 할지 자식 프로세스로 할지.** 둘 다 강제 종료가 되며, 자식 프로세스는 공유 스레드 풀에서 멈춘 시스템 호출에 더 안전하지만 시작 시간이 듭니다. 선호가 있나요?
