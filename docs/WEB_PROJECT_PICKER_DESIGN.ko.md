# 보안 설계: `pgard web`에서 프로젝트 고르기

> **참고:** 이 문서는 [`WEB_PROJECT_PICKER_DESIGN.md`](WEB_PROJECT_PICKER_DESIGN.md)(영문)의 한국어 번역입니다. 기준 문서는 영문판이며, 내용이 다르면 영문판이 맞습니다. 프로젝트 [README](../README.ko.md)([English](../README.md))와 [문서 목록](README.ko.md)도 참고하세요.

상태: 승인된 설계([#355](https://github.com/JadenMeister/pgard/issues/355), M8-3)이며 M8-4([#398](https://github.com/JadenMeister/pgard/issues/398))에서 구현했습니다. 구현이 설계와 다른 곳은 #398의 풀 리퀘스트에 적었습니다. 아래의 "현재"와 "M8-4 요구사항"에 대한 문장은 M8-4 이전의 코드를 설명합니다.

"현재"에 대한 설명은 작성 시점의 코드(`apps/local-web/src/server`, `apps/cli/src/commands/dashboard.ts`, `packages/policy`, `packages/scan-core`, `packages/git-history`, `packages/result-store`)를 기준으로 합니다. 이 설계가 아직 코드에 없는 것에 기대는 곳에는 **M8-4 요구사항**이라고 표시했습니다. 현재 동작의 기준은 README이며, 이 설계는 README의 일부 문장을 바꿉니다([M8-4의 README 변경](#9-m8-4의-readme-변경) 참고).

## 1. 목표와 비목표

### 목표

1. `pgard web`은 프로젝트 없이 시작합니다. 사용자는 검색하거나 폴더를 페이지에 끌어다 놓아 프로젝트를 고릅니다.
2. 브라우저는 사용자가 어느 프로젝트를 뜻하는지 알려 주는 **신호**일 뿐입니다. 경로를 보내지 않고 파일 내용도 보내지 않습니다.
3. 로컬 서버가 **사용자가 정한 검색 범위** 안에서 이름이 맞는 Git 저장소를 찾고, 실제 경로와 remote를 보여 줍니다. 사용자가 이를 확인합니다.
4. 확인 뒤에는 같은 5가지 권한 확인(저장소, GitHub 신원, 소유자 승인, 현재 접근, 기여)이 실행됩니다. 잘못된 폴더가 곧바로 검사로 이어지는 일은 없습니다.
5. 증거가 불분명하면 막고, 이유와 해결 방법을 알려 줍니다. 권한 확인은 절대 느슨하게 하지 않습니다.
6. 코드, 경로, 결과는 로컬에 머뭅니다. 새로 어디로 보내는 것은 없습니다.

### 소유자가 이미 정한 사항

- **플랫폼.** 처음에는 macOS와 Linux만 지원합니다. Windows에서 `pgard web`은 사용법 오류(2)로 종료하고, 피커가 아직 지원되지 않는 이유를 설명하며 `pgard dashboard`를 안내합니다(**M8-4 요구사항**, Windows 러너에서 도는 테스트 포함). Windows 고유의 문제(junction, UNC 경로, 8.3 이름, `ino` 부재, Node 기본 기능으로 소유자 확인 불가)는 의도적으로 여기서 설계하지 않으며, Windows에서 피커를 켜기 전에 따로 설계해야 합니다.
- **기본 범위.** 흔한 개발 폴더 중 실제로 존재하는 것만 씁니다: `~/code`, `~/projects`, `~/dev`, `~/src`, `~/workspace`, `~/git`, `~/Developer`. 첫 실행 때 터미널에 보여 주고 확인받습니다. 홈 폴더 전체를 추가하는 것은 명시적인 선택입니다(`pgard web scope add ~`, 경고 포함). 이유: macOS에서 홈 폴더를 걸으면 TCC 권한 프롬프트가 뜨고 iCloud가 dataless 파일을 내려받게 됩니다.
- **검색 루트는 터미널에서만 추가합니다.** 브라우저는 사용자가 복사할 수 있도록 `pgard web scope add <folder>` 명령을 보여 줄 수 있지만, 루트를 추가하거나 바꿀 수는 없습니다.
- **명령 두 개.** `pgard dashboard`는 프로젝트 하나에 고정되고 피커를 강제로 끕니다. `pgard web`이 피커입니다.
- **`--no-store`.** 최근 목록은 `--no-store` / `PGARD_NO_STORE=1`을 따릅니다. `pgard web`에 `--no-store` 옵션을 추가합니다(**M8-4 요구사항**).
- **엄격한 최근 목록.** 현재 범위 밖의 최근 항목은 해결 방법과 함께 막힌 카드로 보여 줍니다.
- **같은 사용자의 공격자는 범위 밖입니다.** 이미 같은 OS 사용자로 실행되는 프로세스는 폴더를 직접 읽을 수 있습니다. 다른 사용자는 소유자와 권한 확인(T1, T13)이 막습니다.
- **격리.** 디렉터리 걷기, 후보 점검(모든 Git 호출 포함), 최근 목록 재검증은 **자식 프로세스**에서 실행하고, 프로세스 그룹째 종료합니다.
- **제한은 상수입니다.** 검색별 예산과 입력 검색어 최소 2자를 둡니다.

### 비목표

- 피커를 위해 브라우저나 서버가 파일 또는 디렉터리의 내용을 읽지 않습니다. 읽는 것은 디렉터리 항목 이름, `lstat` 정보, 기존의 허용 목록 Git 실행기를 통한 Git 메타데이터뿐입니다.
- 브라우저에서 입력하는 절대 경로, 네이티브 폴더 대화상자, `showDirectoryPicker`는 쓰지 않습니다.
- 기본값으로 원격 호스트, 네트워크 공유, 이동식 볼륨은 검사하지 않습니다.
- 권한 확인의 순서, 이유, 캐시 규칙(캐시하지 않음)은 바꾸지 않습니다. 다만 M4/T7의 `expectedRepo` 확인 하나를 추가합니다.
- 대시보드는 여전히 검사 결과를 저장하지 않습니다.
- 1차 버전에서는 연결된 worktree, 서브모듈 등 `.git` 파일을 지원하지 않습니다(T13).

## 2. 위협 모델

보호 대상: 사용자의 소스 코드와 Git 기록, 컴퓨터에 있는 경로와 저장소 이름, GitHub 로그인(OS 키체인에 있으며 브라우저로 보내지 않음), 권한 확인 결정.

신뢰 경계: `pgard web`을 시작한 터미널(신뢰함, 사용자가 거기서 확인), 세션 URL을 받은 브라우저 탭(토큰이 있을 때만 신뢰), 그 밖의 모든 탭, 웹 페이지, 로컬 프로세스(신뢰하지 않음), 디스크에 있는 모든 저장소의 내용(`.git/config` 포함, 신뢰하지 않는 데이터), 점검용 자식 프로세스의 출력(자식이 신뢰하지 않는 데이터를 읽으므로 서버가 엄격한 스키마로 검증).

현재 서버가 이미 하는 일(`apps/local-web/src/server/middleware/security.ts`, `create-server.ts`에서 확인):

- 빈 포트의 `127.0.0.1`에만 바인딩합니다. `Host`는 정확히 `127.0.0.1:<port>`여야 합니다(아니면 421).
- 모든 `/api/` 호출에 `x-pgard-token` 헤더가 필요합니다(무작위 32바이트, `timingSafeEqual`로 비교). 다른 `Origin`이나 `same-origin`/`none`이 아닌 `Sec-Fetch-Site`는 거부합니다. 상태를 바꾸는 호출은 정확한 `Origin`을 보내야 합니다. API는 CORS 헤더를 보내지 않습니다.
- 모든 응답에 `Cache-Control: no-store`, `default-src 'none'`과 `connect-src 'self'`를 가진 CSP, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy: same-origin`이 붙습니다.
- 토큰은 URL 조각(fragment)으로 전달되고, 페이지는 주소창에서 지운 뒤 메모리에만 둡니다.
- 요청 본문은 16 KiB로 제한되고 `application/json`이어야 합니다.
- 서버는 요청별 로그를 쓰지 않습니다(실행기가 시작 문구와 종료 문구 한 줄만 출력).
- 프로젝트 루트는 서버 수명 동안 고정이고(`ApiContext.projectRoot`), 경로를 받는 라우트는 없습니다.
- WebSocket이나 Server-Sent Events 엔드포인트가 없고 피커도 추가하지 않습니다(진행 상황은 폴링). 따라서 업그레이드 경로에 별도의 Host/Origin 처리가 필요하지 않습니다.

이 설계가 바꾸는 것은 고정된 프로젝트 루트 하나뿐입니다. 프로젝트를 시작 뒤에 고르게 됩니다.

GitHub 기기 로그인을 기다리는 확인(verify)이 막다른 길이 되지 않도록 **확인 취소** 동작인 `POST /api/auth/cancel`을 둡니다. `github.abortPendingSignIn()`을 호출한 뒤 `setAuth`를 대기 상태로 돌리며, `cancelScan`이 검사에 쓰는 것과 같은 쌍입니다. 실행 중인 것이 없으면 200 무동작입니다. confirm은 실행 중인 확인을 스스로 중단하지 않으며, 사용자가 먼저 취소합니다. **모든 비동기 핸들러는 시작할 때 프로젝트 기록과 `projectEpoch`를 잡아 두고, 각 `await` 뒤에 둘 중 하나라도 바뀌었으면 `project_changed`를 던지고 결과를 버립니다.** `api.ts`의 `requireSameAuthorization`이 권한 확인 기록에 쓰는 것과 같은 패턴입니다. 대상은 `startVerify`, `recheckOwnerApproval`, `probePort`, `confirmTarget`, `startScan`, 보고서 렌더링, 검색 완료입니다. 프로젝트와 관련해 상태를 바꾸는 라우트는 페이지가 에포크를 함께 보내, 오래된 화면의 두 번째 탭이 `project_changed`로 실패하게 합니다. **M8-4 요구사항:** 현재는 바꿀 수 있는 프로젝트도 에포크도 없고, `startVerify` 등은 `context.projectRoot`를 직접 읽습니다.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| T13 | **심어 둔 저장소, 쓰기 가능한 저장소, `.git` 간접 참조**(다른 사용자, 공유 폴더, 연결된 worktree, 심볼릭 링크) | 범위 루트부터 후보까지의 모든 디렉터리, 후보의 `.git`, 그 안의 `.git/config` 파일(remote와 모든 Git 설정을 정하는 파일), 확인된 Git 공통 디렉터리에 대해 점검기는 `.git` **파일**(gitdir 포인터, 연결된 worktree, 서브모듈)은 따라가면 걸어온 체인을 벗어나므로 1차 버전에서 고정 이유와 함께 `gitfile_unsupported`로 막습니다. `git rev-parse --git-common-dir`가 알려 주는 공통 디렉터리는 후보 자신의 `.git`으로 해석되어야 하며, 아니면 정확한 해결 방법을 `chmod go-w a b c` 한 명령에 모두 나열해, 사용자가 한 번에 모두 고칠 수 있게 합니다. 다른 사용자와 `/tmp`, `/Users/Shared` 같은 공유 폴더에 대한 방어입니다. ## 3. API 스케치

모든 라우트는 `API_ROUTES`에 추가합니다(정확한 `"METHOD /path"` 키이므로 경로 매개변수가 없고, id는 쿼리 문자열이나 본문에 둡니다). 모두 핸들러 전에 기존의 Host, Origin, 토큰 확인을 거칩니다. 모든 본문은 최대 16 KiB의 `application/json`입니다(기존 제한). 오류는 기존 형식 `{ "error": { "code", "message" } }`에 고정된 번역 가능한 메시지를 씁니다.

**고정 모드.** 대시보드가 `pgard dashboard`로 시작되었으면(`--project-root` 지정) 피커는 강제로 꺼집니다. **모든 `/api/picker/*` 라우트는 본문을 읽기 전에 `409 fixed_project`로 답합니다.** 요청 내용과 무관합니다(테스트는 8절).

**프로젝트가 필요한 라우트와 아닌 라우트.** 프로젝트가 필요한 라우트는 선택된 프로젝트가 없으면 `409 no_project`로 답합니다: `POST /api/auth/verify`, `POST /api/auth/owner-approval`, `GET /api/ports`, `POST /api/ports/probe`, `POST /api/target/confirm`, `POST /api/scan`, `GET /api/reports/html`, `GET /api/reports/pdf`. 프로젝트 없이 동작하는 라우트: `GET /api/session`, `GET /api/auth`(대기 상태와 저장된 로그인을 보고), `POST /api/auth/sign-out`, `POST /api/auth/cancel`(**M8-4 요구사항**: 새 라우트, 프로젝트 불필요, 에포크 없음), `GET /api/target`, `POST /api/target/clear`, `GET /api/scan`, `POST /api/scan/cancel`, `GET /api/rule-texts`, 피커 라우트. 프로젝트를 고르기 전에도 로그아웃하고 문구를 읽을 수 있습니다.

프로젝트와 관련해 상태를 바꾸는 기존 라우트는 본문에 `epoch`를 추가로 받습니다: `POST /api/auth/verify`, `POST /api/auth/owner-approval`, `POST /api/ports/probe`, `POST /api/target/confirm`, `POST /api/scan`(**M8-4 요구사항**. 피커 모드에서 오래되었거나 없는 에포크는 `project_changed`로 답하고, 고정 모드에서는 에포크가 항상 1이며 필요하지 않음).

```ts
interface Candidate {
  candidateId: string; // [A-Za-z0-9_-] 22자, 128비트 무작위, 서버가 보관, 10분간 유효
  name: string; // 정리됨, 120자 이하
  displayPath: string; // 실제 경로, "~"로 줄임, 정리됨, 400자 이하
  displayPathEscaped: string | null; // unsafe_display로 막힌 경우에만 설정
  collision: { tag: string } | null; // 다른 후보와 displayPath가 같음. tag = 지문의 6자리 16진수
  shown: string; // 동일성 체인 + owner/name의 지문. confirm 때 되돌려 보냄
  remote:
    | { status: "github"; repo: string } // "owner/name"
    | { status: "none" | "not_github" | "ambiguous" | "unreadable" };
  selectable: boolean;
  blocked: null | {
    code: PickerBlockCode;
    paths: string[]; // 쓰기 비트/소유자 차단 시 실패한 모든 디렉터리와 파일. "~"로 줄이고 정리(그 밖에는 빈 배열)
    reason: string; // 고정 문구(영어, UI가 코드를 영어/한국어로 대응)
    fix: string; // 고정 문구
  };
  source: "scope" | "recent";
}

interface RecentEntry extends Candidate {
  entryId: string; // [A-Za-z0-9_-] 22자, 무작위, 파일에 저장
  lastUsedAt: string; // ISO 시각
}
```

`Candidate.remote.status`와 `blocked`는 공유하는 로컬 저장소 확인과 T13의 검사에서 나옵니다. github.com remote일 때는 `owner/name`만 돌려주고 URL이나 remote 이름은 돌려주지 않습니다.

**id, 에포크, 상한.** `candidateId`, `searchId`, `entryId`는 형식이 하나입니다(`[A-Za-z0-9_-]` 22자, `crypto.randomBytes`의 128비트 무작위). 그 밖의 형식은 조회 전에 `400 bad_id`입니다. `projectEpoch`는 1에서 시작하는 양의 안전한 정수이며, 안전한 정수가 아닌 에포크를 담은 요청은 `400 bad_request`입니다. 후보 맵은 최대 100개(오래된 것부터 버리고 검색마다 만료된 것을 정리)이며 끝난 검색은 최대 5개만 보관합니다.

## 4. 세션과 토큰 결합

새 자격 증명 없이 현재 방식을 재사용합니다.

- 서버 실행마다 토큰 하나를 URL 조각으로 한 번 출력하고, 페이지가 메모리에 두었다가 `x-pgard-token`으로 보냅니다. 후보 id, 검색 id, 최근 목록을 포함해 피커의 어떤 것도 토큰 없이는 쓸 수 없습니다.
- 후보 id와 검색 id는 무작위이며 토큰이 있을 때만 의미가 있고(`SessionState`처럼 세션별 서버 상태), 디스크에 저장하지 않으며, 서버가 멈추면 사라집니다(`clearSessionState`). 항목 id도 무작위지만 최근 파일에 저장됩니다.
- 새 상태는 `SessionState`에 둡니다. 선택된 프로젝트 기록(동일성 체인, `owner/name`, 이름), 현재 검색, 후보 맵, `projectEpoch`. 종료 시 `clearSessionState`로 지우고 점검용 자식 프로세스의 프로세스 그룹도 종료합니다.
- Origin과 Host 규칙은 그대로입니다. 피커는 쿠키, 이름이나 경로를 위한 `localStorage`, 두 번째 토큰을 추가하지 않습니다.
- **M8-4 요구사항:** `ApiContext.projectRoot`를 세션 상태에서 읽는 값(확인 전까지 null)으로 바꾸고, T12처럼 요청마다 잡아 둡니다.
- **M8-4 요구사항:** `projectEpoch`는 confirm과 clear 때마다 증가하며, 3절에 나열한 라우트가 이를 함께 보냅니다.
- 계정 결합은 그대로입니다. 로그인한 GitHub 계정은 프로젝트와 독립적입니다. 프로젝트가 바뀌면 권한 확인 기록이 초기화되므로 다음 확인은 처음부터 실행됩니다.

`pgard web`(**M8-4 요구사항**, 새 명령)은 `pgard dashboard`처럼 대화형 터미널이 필요합니다. 서버를 시작하기 전에 검색 범위 루트(첫 실행에는 존재하는 기본 폴더)를 출력하고 `Search these folders for projects? [y/N]`를 묻습니다(터미널이 없으면 종료 코드 2). 명령줄에 경로를 넘기지 않습니다. `--no-store`, `--no-browser`와 `pgard web scope list | add <folder> | remove <folder>`를 지원합니다(**M8-4 요구사항**). Windows에서는 사용법 오류로 종료하고 `pgard dashboard`를 안내합니다.

## 6. 저장 형식

폴더: `resolveStoreDirectory()`가 주는 기존 사용자별 앱 데이터 디렉터리(`~/Library/Application Support/pgard` 또는 `$XDG_DATA_HOME/pgard`, 기본값 `~/.local/share/pgard`) 안의 새 하위 폴더 `web/`입니다. `repos/`를 지워도 안전하고 서로 무관하도록 분리합니다. 프로젝트 안에는 절대 두지 않습니다. 보호는 결과 저장소를 따릅니다. 폴더 `0700`, 파일 `0600`, 폴더와 파일 모두 심볼릭 링크를 따라가지 않음, 같은 폴더의 임시 파일에 (배타적 생성으로) 쓴 뒤 이름 변경, 파싱 전 크기 제한, 지원하지 않거나 더 새로운 `schemaVersion`은 알림과 함께 무시하고 덮어쓰지 않음.

**M8-4 요구사항:** `packages/result-store/src/store.ts`의 안전한 파일 코드는 저장소의 팩토리 클로저 안에 있어 내보내지지 않습니다. 다시 구현하지 말고 공유 도우미로 추출하세요(또는 두 파일을 `@pgard/result-store`의 모듈로 추가).

`web/settings.json`:

```json
{
  "schemaVersion": "1.0",
  "searchRoots": [{ "path": "/Users/alice/code" }]
}
```

- `searchRoots[].path`는 추가 시점의 절대 `realpath`입니다. 실행할 때마다 다시 검증합니다(존재, 디렉터리, T13의 안전한 소유자와 권한, 깊이 규칙). 유효하지 않은 루트는 그 세션에서 빼고 터미널에 알립니다.
- 첫 실행: 존재하는 기본 개발 폴더를 출력하고, 사용자가 확인하면 여기에 기록합니다. `--no-store`일 때는 저장하지 않으므로 다음 실행에서 다시 묻습니다.
- 루트는 터미널에서만 바꿉니다: `pgard web scope list | add <folder> | remove <folder>`. `add`는 실제 경로를 보여 주고 확인을 받으며, 홈 폴더를 추가할 때는 macOS 권한 프롬프트와 iCloud 내려받기에 대한 경고를 보여 줍니다.
- 제한은 설정이 아니라 상수입니다.

`web/recent-projects.json`:

```json
{
  "schemaVersion": "1.0",
  "entries": [
    {
      "entryId": "Zk3dQ0r1nH5uV9xTt2aYpA",
      "path": "/Users/alice/code/shop",
      "repo": "alice/shop",
      "lastUsedAt": "2026-10-28T09:00:00Z"
    }
  ]
}
```

- 최대 20개, 최신순, `realpath`당 하나. **항목은 `lastUsedAt`부터 90일 뒤 만료됩니다**(결과 저장소와 같음. 만료된 항목은 파일을 읽고 쓸 때 버림). 성공적인 **confirm** 뒤에만 기록합니다(검색 뒤에는 기록하지 않고, 이후 권한 확인 결과와도 무관).
- `repo`는 표시용 힌트일 뿐이고, 표시되는 owner/name은 항상 새로 읽은 값입니다.
- 검사 결과와 달리 절대 경로를 담습니다. README에 예외로 적어야 합니다. `pgard history clear --all`로 지워지고(**M8-4 요구사항:** 현재 그 명령은 결과 저장소의 데이터만 지움), `--no-store` 또는 `PGARD_NO_STORE=1`일 때는 기록하지 않습니다(그 세션에서는 최근 목록이 비어 있음).

## 7. 무엇을 기록하고 무엇을 기록하지 않는가

- **서버:** 현재처럼 요청별로는 아무것도 기록하지 않습니다. 접근 로그도 디버그 로그도 없습니다. 터미널 출력은 시작과 종료 문구입니다. **터미널은 사용자가 확인해야 하는 곳에서 경로를 출력합니다.** 시작 프롬프트의 범위 루트와 `pgard web scope list | add | remove`의 결과입니다. 이는 의도된 것이며(신뢰하는 채널), PGARD는 그 줄을 어떤 파일에도 쓰지 않습니다.
- **어디에도 기록하지 않는 것**(파일, 오류 문구, 충돌 메시지, 원격 측정, API 오류): 검색하거나 놓은 폴더 이름, 후보 경로, remote URL이나 remote 이름, 후보 id와 검색 id, 토큰. 6절의 두 파일이 경로를 저장하는 유일한 곳이며, 의도된 것입니다.
- **파일 시스템과 Git 오류**는 문구 그대로 전달하지 않습니다. Node의 `error.message`에는 경로가 들어 있고, Git의 stderr에는 경로와 remote가 들어 있을 수 있습니다. 자체 코드(`ENOENT`, `EACCES`, `ELOOP`, `ENAMETOOLONG`, `ENOTDIR`, 시간 초과, 나머지는 `unreadable`)로 바꾼 뒤 고정 메시지가 있는 차단 코드로 대응합니다.
- **메모리에만 있고 종료 시 폐기:** 검색, 후보 맵, 선택된 프로젝트 기록, `visited` 같은 카운터. 점검용 자식 프로세스는 stdout과 stderr가 없으므로(무시) 자식이 출력하는 어떤 것도 새어 나갈 수 없습니다.
- **API 오류**에는 고정 코드와 고정 메시지만 담습니다.
- **브라우저는 기록하지 않음:** 이름과 경로를 URL, 제목, `localStorage`, 콘솔에 넣지 않습니다. 페이지가 이미 저장하는 것은 UI 언어 선택뿐입니다.

## 8. M8-4 테스트 계획

단위 및 통합 테스트(vitest, 기존 테스트처럼 `ServerDeps` 주입, 실제 GitHub와 실제 키체인 없음). 테스트에서 `lstat`/`readdir` 결과(소유자, 권한 비트, `dev`, `ino`)를 흉내 내야 할 때는, 점검기가 전역 스텁이 아니라 **주입 가능한 fs 객체**(`lstat`, `readdir`, `realpath`로 이루어진 작은 인터페이스)를 받습니다.

1. **미들웨어 재사용.** 각 피커 라우트는 다음을 거부합니다. 토큰 없음, 잘못된 토큰, 잘못된 `Host`(`localhost`와 리바인딩된 이름 포함), 다른 `Origin`, POST의 `Origin` 누락, `Sec-Fetch-Site: cross-site`, 잘못된 content type, 16 KiB 초과 본문. 오류를 포함해 어떤 응답에도 CORS 헤더가 없습니다.
2. **고정 모드(M1).** `pgard dashboard`(`--project-root`)로 시작하면, 모든 `/api/picker/*` 라우트가 모든 메서드와, 올바른/잘못된/빈 본문에 대해 `409 fixed_project`로 답하고 아무것도 검색하거나 선택하지 않습니다.
3. **이름 검증.** 잘못된 이름 표와 정확한 `bad_name` 메시지(이유와 할 일을 알려 줌): 빈 문자열, 입력인데 1자, `.`, `..`, `a/b`, NUL, 제어 문자와 양방향 문자, 256단위, 짝 없는 서로게이트. 같은 이름의 NFC와 NFD는 같은 디렉터리와 일치합니다. 대소문자 접기는 로케일과 무관합니다. 프로세스 로케일을 터키어로 두어도 `I`는 `toLowerCase()`가 정의한 대로만 `i`와 일치합니다.
4. **걷기.** 임시 디렉터리의 픽스처 트리: 깊이 제한, 항목 제한, (주입한 시계로) 데드라인이 `stoppedAfterSeconds`가 있는 `partial`과, 찾았지만 점검하지 못한 것에 대한 `not_inspected` 카드를 줌(조용히 버리는 것 없음), 제외 목록, 찾은 저장소 안에서 중첩 검색 없음, 범위 밖 저장소로의 심볼릭 링크는 제시하지 않음, 심볼릭 링크 순환, 다른 `dev`(주입 fs)에는 들어가지 않음.
5. **멈춘 스레드 풀(M2).** 자식 프로세스에서 FIFO(`mkfifo`, 쓰는 쪽 없음)를 `fs.open`으로 네 번 이상 열어 자식의 libuv 스레드 풀 스레드를 모두 막습니다. 막혀 있는 동안에도 실제 fs 작업을 1초 안에 해내야 합니다. 테스트는 메인 프로세스에서 진짜 `fs.promises.stat`의 시간을 재거나, fs 작업을 하는 테스트 전용 라우트를 호출합니다. `GET /api/session`은 주입된 자격 증명 저장소와 키체인을 거쳐 저장된 로그인을 읽으므로 스레드 풀에 대해 아무것도 증명하지 못하기 때문에 쓰지 않습니다. 하드 데드라인에는 자식의 프로세스 그룹 전체가 사라지고(pid 확인, `kill -0` 실패), 검색은 `partial` 또는 `failed`로 답하며, 새 검색은 동작합니다. 또한 멈춘 자식 두 개를 흉내 내면 세 번째 검색은 `503 inspector_busy`로 답합니다. 같은 일을 `worker_threads` Worker 안에서 한 번 실행하는 대조 테스트를 문서화해 서버가 얼어붙는 것을 보여 주고, 자식 프로세스를 쓰는 이유가 계속 증명되게 합니다.
6. **재검증 중 마운트 멈춤(M3).** 경로가 막힌 FIFO이거나 주입한 영원히 돌아오지 않는 `lstat`인 최근 목록 항목: `GET /api/picker/recent`는 `validating: true`로 빨리 답하고, 예산이 지나면 그 항목이 `unreadable`이 되며, 다른 항목은 계속 검증되고, 1초 안의 두 번째 호출은 재검증을 새로 시작하지 않고, 30초 안의 호출은 캐시를 씁니다. Git 호출에는 3초 제한이 있습니다(돌아오지 않는 주입 실행기).
7. **대소문자 구분 없는 파일 시스템.** `macos-latest` check 작업에서: `Shop` 이름이 `shop`을 찾음(APFS 기본값은 대소문자 구분 없음), NFC와 NFD 이름. `ubuntu-latest`(대소문자 구분)에서: `Shop`과 `shop`이 별개 디렉터리로 있으면 둘 다 일치하고 둘 다 제시됩니다. **동일성에 의한 포함 관계(M5):** 대소문자를 구분하는 볼륨에서 실제 범위 루트 `code` 옆의 비슷한 디렉터리 `Code`, 그리고 심볼릭 링크된 상위를 거쳐 닿은 디렉터리는, 문자열이 어떻든 기록된 `dev`/`ino` 체인이 맞지 않으므로 인정되지 않습니다.
8. **소유자와 쓰기 비트(M6).** 주입 fs로: 다른 uid가 소유한 디렉터리가 상위 체인에 있는 후보, 그룹이 쓸 수 있는 상위, 모두가 쓸 수 있는 상위, 그룹이 쓸 수 있는 `.git`, 그룹이 쓸 수 있는 `.git/config`, 여러 경로가 동시에 실패하는 경우(메시지 하나, `chmod go-w a b c` 하나), 파일인 `.git`(gitdir 포인터, 연결된 worktree, 서브모듈 구조): 각각 정확한 코드와 고정 메시지로 막히고, 메시지는 실패한 모든 디렉터리와 파일(`.git/config` 포함)을 정확한 `chmod go-w a b c` 해결 방법 하나로 나열합니다. 프로젝트 밖을 가리키는 `commondir`은 `git_dir_unsupported`로 막힙니다.
9. **후보 검사.** remote 차단 코드마다 픽스처 저장소: remote 없음, `https://example.com/o/r.git`, GitHub Enterprise 호스트, 서로 다른 저장소를 가리키는 remote 두 개, 자격 증명이 들어 있는 remote URL과 악의적인 이름의 remote(응답에 자격 증명도 URL도 remote 이름도 없어야 함), 커밋 없음, alternates, `core.fsmonitor`, 훅, `core.sshCommand`가 든 악의적인 `.git/config`(절대 실행되면 안 됨, 표식 파일이 생기지 않는지 확인).
10. **TOCTOU(T7).** 검색 뒤에 디렉터리 이름 변경, 심볼릭 링크로 교체, 다른 저장소로 교체, remote 변경, 10분 경과(주입한 시계, 시계가 뒤로 간 경우도): 각각 `candidate_changed` 또는 `candidate_expired`가 나오고 아무것도 선택되지 않습니다. confirm과 `POST /api/scan` 사이에 디렉터리를 바꿔치기하면 검사가 거부됩니다. `expectedRepo`: 다른 `owner/name`을 돌려주는 가짜 권한 확인은 `runScan`, `verifyProject`, `recheckOwnerApproval`이 막힘 상태와 고정 이유로 멈추게 하고 분석은 실행되지 않습니다(`scan-core`와 `policy`의 단위 테스트).
11. **상태 초기화와 진행 중 작업(M7).** 두 번째 프로젝트를 confirm하면 권한 확인, 대상, 탐색, 검사, 보고서가 지워지고, 이전 보고서 내려받기는 `409`, 오래된 `epoch`는 `project_changed`, 첫 confirm 전의 라우트는 `no_project`를 돌려줍니다. 검사 중 confirm은 `scan_running`, 확인(verify)이나 소유자 승인 재확인 중 confirm은 `auth_running`을 돌려줍니다. **확인 취소:** 기기 로그인을 기다리는 확인(verify)(영원히 끝나지 않는 가짜 제공자)에서 `POST /api/auth/cancel`이 로그인을 중단하고 권한 확인을 대기 상태로 되돌리며, 이어지는 confirm은 `auth_running` 대신 성공합니다. 실행 중인 것이 없을 때 호출하면 200 무동작입니다. 비동기 핸들러마다(`startVerify`, `recheckOwnerApproval`, `probePort`, `confirmTarget`, `startScan`, 보고서 렌더링, 검색 완료): 지연된 의존성으로 시작하고, (테스트에서 상태를 직접 바꿔) 프로젝트를 바꾼 뒤 의존성을 풀면, 핸들러는 `project_changed`로 답하거나 결과를 버리고, 그 결과는 새 프로젝트 아래에서 보이지 않습니다.
12. **멱등성, id, 상한.** 이미 선택된 후보를 두 번 confirm하면 같은 프로젝트로 두 번 성공합니다. 모르는 `entryId` 삭제는 200 무동작, 모르는 검색 취소도 200 무동작, 잘못된 id는 `bad_id`, 정수가 아니거나 너무 큰 에포크는 `bad_request`, 후보 맵은 100개를 넘지 않고 보관하는 검색은 5개를 넘지 않습니다. `scope/toggle`은 `epoch` 없이 동작합니다.
13. **프로젝트 없는 라우트.** confirm 전에도 `GET /api/auth`, `POST /api/auth/sign-out`, `GET /api/scan`, `POST /api/scan/cancel`, `GET /api/target`, `GET /api/rule-texts`, `GET /api/session`은 동작하고, 3절에서 프로젝트가 필요한 라우트는 `no_project`로 답합니다. 모르는 라우트는 `not_found`, 잘못된 JSON은 `bad_json`, 정적 자원에 `POST`하면 `method_not_allowed`. WebSocket이나 SSE 업그레이드는 받지 않습니다(`Upgrade` 요청은 전환되지 않음).
14. **표시(T11).** 오른쪽에서 왼쪽으로 쓰는 재정의 문자, 제어 문자가 든 디렉터리 이름과 500자 경로: `unsafe_display`로 막히고 이스케이프한 형태로 보이며 원본 그대로는 절대 보이지 않습니다. 표시 경로가 같은 두 후보는 모두 충돌 태그를 보여 줍니다.
15. **파일.** 설정과 최근 파일은 `0700` 안에 `0600`으로 만들어지고, 심볼릭 링크를 거치거나 그룹/전체 쓰기 가능이면 거부하며, 너무 크거나 잘못되었거나 알 수 없는 메이저 `schemaVersion`이면 무시하고 덮어쓰지 않고, 21개째 항목은 잘리고, 90일이 지난 항목은 버려지고, 변조된 `path`(저장소가 아닌 곳, 심볼릭 링크, 다른 사용자의 폴더, 범위 밖 경로)는 막힌 채 표시되고 선택할 수 없으며 표시 문구는 새로 읽은 값입니다. `--no-store`는 최근 목록도 첫 실행 루트도 쓰지 않습니다. `history clear --all`은 `web/`을 지웁니다.
16. **누출 없음.** 눈에 띄는 이름과 경로(픽스처의 `EACCES` 같은 fs 오류 포함)로 위 시나리오를 실행하면서 stdout, stderr, 던져진 메시지, 모든 API 응답을 캡처합니다. 의도된 응답 필드(`displayPath`, `displayPathEscaped`, `name`, `repo`)를 제외하면 이름, 경로, remote URL, 토큰이 어디에도 없어야 합니다. DOM은 이름을 `document.title`, `location`, `localStorage`에 받지 않습니다. 검색 입력란에 T6의 세 속성이 있습니다.
17. **클라이언트 끌어다 놓기.** jsdom에서 가짜 `DataTransfer` 객체(`kind`가 있는 항목, `{ name, isDirectory }`를 돌려주는 `webkitGetAsEntry()`)를 씁니다. 핸들러는 `name`과 `isDirectory`만 읽고 `getAsFile`, `createReader`, `FileReader`는 절대 호출하지 않습니다(가짜 객체에 스파이). 파일을 놓으면 "파일이 아니라 폴더를 놓으세요"를 보여 줍니다. **영역 밖 드롭(m1):** `window`나 `document.body`에 `dragover`와 `drop`을 보내면 `defaultPrevented === true`이고 이동하지 않습니다. 5절의 막힘 상태가 영어와 한국어로 이유와 해결 방법을 보여 줍니다.
18. **플랫폼.** `windows-latest` 작업에서 `pgard web`은 사용법 오류로 종료하고 `pgard dashboard`를 안내하는 메시지를 내며 서버를 시작하지 않습니다.

기존 가짜 GitHub 주입을 쓰는 종단 간 테스트(실제 계정 없음, 테스트에서 `pgard web`을 실제 계정에 실행하지 않음):

19. 이름으로 저장소를 골라 confirm하고, 5가지 확인을 통과하고, 검사하고, 보고서를 내려받습니다.
20. **App 설치 밖의 비공개 저장소:** 고르고 confirm하면 막힌 `current_access` 상태에 이르고, 설치 안내가 보이며, 아무것도 검사되지 않습니다.
21. github.com이 아닌 remote의 저장소를 고르면: 피커에서 이유와 함께 막히고 권한 확인에 이르지 않습니다.
22. 이름이 같은 두 폴더 중 잘못된 것을 고르면: 확인 화면이 다른 경로와 `owner/name`을 보여 주고 사용자가 뒤로 갑니다.

## 9. M8-4의 README 변경

현재 README는 "브라우저는 프로젝트 파일을 고르거나 읽을 수 없습니다. 프로젝트 루트는 대시보드가 시작될 때 고정됩니다"와 "브라우저는 경로를 전혀 제공하지 않습니다"라고 말합니다. M8-4 이후 이 문장은 `pgard dashboard`에만 해당합니다. `pgard web`에 대해서는 README가 대신 다음을 말해야 합니다. 브라우저는 폴더 이름만 보내고, 서버가 사용자의 범위를 검색하고, 사용자가 실제 경로와 remote를 확인하고, 5가지 확인이 실행되며, 이를 위해 파일 내용은 읽지 않고, 피커는 당분간 macOS와 Linux 전용이다. 또한 최근 목록 파일과 설정 파일을 "저장된 결과"와 "개인정보" 절에 절대 경로를 담는, 로컬에만 있고 업로드되지 않는 파일로 추가하고, `pgard web`, `--no-store`, `pgard web scope`, `web/`까지 지우는 `pgard history clear --all`을 문서화하며, `pgard dashboard`가 모든 피커 라우트를 거부한다는 점을 적어야 합니다.

이 문서가 명시한 M8-4 요구사항을 한 목록으로 모으면: `fixed_project` 거부, `SessionState`의 에포크와 프로젝트 기록 및 요청별 캡처, `ScanRequest`, `runScan`, `verifyProject`, `authorizeProject`, `recheckOwnerApproval`의 `expectedRepo`, 로컬 전용 저장소 점검의 내보내기, Git 호출 시간 제한 옵션, 프로세스 그룹 종료가 있는 점검용 자식 프로세스, 공유 안전 파일 도우미, `pgard web`과 그 `--no-store` 옵션 및 `pgard web scope list | add | remove`, `web/`까지 지우는 `history clear --all`, Windows 종료, 창 수준 드래그 방지.
