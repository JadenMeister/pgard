# Scan result schema and versioning

> [한국어](RESULT_SCHEMA.ko.md) translation available. This English file is the reference; the translation follows it.

The scan result (`ScanResult` in `packages/findings/src/contract.ts`) carries a `schemaVersion` in `major.minor` form. The current version is `1.7`. This document says when that version changes and what a reader must do with a version it did not write.

## Version rules

**Minor** (`1.0` to `1.1`): additive and optional only.

- A new optional field, or a new field that older readers can ignore.
- A new value in an open-ended string field (for example a new rule id).

**Major** (`1.x` to `2.0`): anything else.

- A field removed, renamed or retyped.
- A change in the meaning of an existing field.
- A new value in a closed enum (severity, status, category, scope, and so on), because an old reader cannot interpret it.
- A change in how `Finding.id` is derived (see below).

Fields marked deprecated (such as `advisoryDb`) keep their shape until the next major version.

## Reading rules

Readers ignore fields they do not know. Anything that reads a result back (stored results, CI tools, report and SARIF converters) goes through `readScanResult` from `@pgard/findings`. It validates the shape strictly, never throws, and returns either the typed result or a typed error.

| Input version                 | Behaviour                                                                                                                           |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Same (`1.7`)                  | Accepted.                                                                                                                           |
| Older minor of the same major | Accepted. Fields added later are absent; the shape is still valid.                                                                  |
| Newer minor of the same major | Accepted. Unknown fields are ignored (the reader drops them). `sourceVersion` reports the version the file carried.                 |
| Other major                   | Refused with `version_unsupported_major` and a message naming the version. The reader never tries to convert or guess.              |
| Missing or malformed          | Refused with `version_missing` or `version_malformed`. A valid version is exactly two dot-separated integers without leading zeros. |

The version grammar is `major.minor`, each part a non-negative integer of at most 6 digits and without leading zeros.

A version that is accepted is still checked against the full shape. A wrong enum value, a missing required field, a hole in an array, a duplicate `Finding.id`, a line number below 1 or an oversized array is refused with `invalid_shape` or `too_large`, whatever the version says. The reader reads own data properties only (it never runs getters), and caps array sizes, string lengths and the total number of array entries (`READ_LIMITS`), so a hostile file cannot make it do unbounded work after parsing. Callers must cap the file size before `JSON.parse`; the reader cannot do that for them.

Strings are length-capped but not sanitized. Evidence, titles and notes can contain any characters, and escaping them for HTML, terminals or SARIF is the job of whatever renders them.

**Write-back.** The reader returns the fields it knows and drops the rest. When `sourceVersion` is newer than `SCHEMA_VERSION`, never write the reader's output back over the source file: that would silently delete the newer fields. Save a copy under another name, or refuse.

## Which outputs carry the version

- Any JSON output of a scan, including the planned CLI JSON output (`schemaVersion` at the top level).
- Stored results (the same object, written as is).
- Reports built from a result (HTML and PDF). They print the normalized `schemaVersion` of the reader (the version this PGARD implements), not necessarily the version the source file carried.

## Finding.id is a fingerprint

`Finding.id` is a stable fingerprint of rule, location and cause. Stored results are compared with later scans by this id, so it is part of the contract even though its type is only `string`. Changing how it is derived makes ids from older results stop matching, so such a change is a **major** version change. Its type or the rule that it never contains secret values cannot change within a major version either.

## Version history

**1.7** (additive; a minor bump). One optional top-level field, `scanBasis`: whether the authorization gate ran and passed. Shape: `{ mode: "authorized" | "code_only", authorization: "verified" | "not_verified", reason: string | null }`. `mode: "authorized"` means the gate ran (`authorization` holds its five checks); `mode: "code_only"` means no gate ran: only the current files were analyzed (the `code` scope, plus the `secrets:working-tree` area), with no Git history, no web checks, and the result is never stored. `authorization` is `verified` only when the gate ran and allowed the scan, and a code-only result is always `not_verified`. `reason` is `null` exactly when `authorization` is `verified`; otherwise an open-ended code (`no_approval`, `not_checked`, `no_github_remote`, `not_a_git_repository`, `offline`; a reader shows an unknown one generically). No closed enum gains a value. A code-only result keeps `authorization.decision: "blocked"` (truthful: the gate did not allow it), every check `unverifiable` with the reason "Not checked: this was a code-only scan of the files on this computer. No authorization was proven.", and `requestedScopes: ["code"]`; its `overallStatus` comes from the code coverage alone (`completed`, `partial` or `failed`, never `blocked`). **Cross-field rule:** in 1.7, `decision: "blocked"` together with an `overallStatus` other than `blocked` means a code-only scan, so an older reader that checks `decision === "allowed"` never treats it as authorized. SARIF carries the object in `runs[0].properties.pgard.scanBasis`, adds one warning notification ("Code-only scan: authorization was not verified ..."), and uses `automationDetails.id` `pgard/code-only/`. HTML and PDF reports of a code-only result carry a "Not authorized: code-only scan" banner on every page. The result store refuses a result whose `scanBasis.authorization` is not `verified`. Results of `1.6` and older have no such field, and a reader treats absent as `mode: "authorized"` with the gate's own `authorization.decision` (older PGARD ran the gate before every scan).

**1.6** (additive; a minor bump). One optional field on a finding, `fix`: a suggested fix to review, present only on findings of a rule that is declared `fixable` (`RuleDescriptor.fixable`; today `PG-COOKIE-001` and `PG-CRYPTO-003`). Shape: `{ kind: "diff" | "guidance", diff?, confidence, reason? }`. `kind: "diff"` carries `diff`, a unified diff of one repository file with one hunk, no context lines, one removed and one added line (`@@ -N,1 +N,1 @@`), at most 2,000 characters; apply it with `git apply --unidiff-zero`. `kind: "guidance"` has no `diff`: the rule can offer a diff but the code around this finding is not one of its rewrites, and `reason` says why (an open-ended code: `context_not_supported`, `sensitive_text`, `too_large`, `source_unavailable`, `too_many`). `confidence` (`high`, `medium`, `low`) is how sure PGARD is that the rewrite keeps the meaning of the flagged code, never a safety claim. **A fix is a suggestion, not a verified change:** PGARD never applies it, never writes to the scanned files and has not checked that the result compiles or keeps behaviour, and every front end labels it so. Both lines of a diff pass through secret and path redaction unchanged or there is no diff, and a front end (or redaction) that meets a diff that is not one of PGARD's single-line diffs shows guidance instead. SARIF carries a diff as `results[].fixes` (one `artifactChange` with one `replacement` of the flagged line). The fingerprint does not depend on `fix`. Results of `1.5` and older have no such field, and a reader treats that as "not recorded".

**1.5** (additive; a minor bump). One optional field on a finding, `dependency`, present only on `PG-DEP-001` findings (a pinned dependency version inside a published advisory's affected range, from the local OSV data): `{ ecosystem, name, version, dev?, direct?, advisoryId, aliases, affectedRange, fixedVersions, severitySource, score?, vector? }`. `advisoryId` is the primary id (over all record ids and aliases: the smallest GHSA id, else GO, else another record id, and a CVE only when nothing else exists, because CVE aliases are often added later; compare and baseline also pair dependency findings of one package version in one lockfile whose `{advisoryId} + aliases` sets intersect, so a changed primary id does not read as a fix plus a new finding) and `aliases` the other ids of the same issue (CVE, GHSA, GO). `affectedRange` is the range the version is in (`>=1.0.0 <1.2.3`, `all versions`), `fixedVersions` the fixed versions newer than `version` (empty when none is published). `severitySource` is `cvss` (the finding's severity comes from the CVSS v3 base score `score`, computed from `vector`), `database` (the advisory database's own label) or `unknown` (neither exists; the finding is `medium`); it is a closed enum. `dev: true` only when the lockfile says the package is development-only; `direct` is absent when the lockfile does not say. It records a version-range match, never exploitability or reachability. No existing field changed: the finding's `category` is the existing `misconfiguration`, its `status` is `suspected`, its `location` is the lockfile with `line: null`, and the fingerprint is built from rule, lockfile path and the cause `<ecosystem>:<name>@<version>:<advisoryId>`, so it does not depend on the data version. The scan also reports `deps:<ecosystem>` (and rule-less `deps:unsupported`) coverage areas in the `code` scope. Results of `1.4` and older have no such field, and a reader treats that as "not recorded".

**1.4** (additive; a minor bump). One optional field on a finding's `references`, `cert`: the SEI CERT Oracle Java rule ids (`IDS00-J`) that the finding's rule is directly about. It is present only on findings in `.java` and `.kt` files whose rule has such a mapping, and absent everywhere else (other languages link to CERT only indirectly, through a CWE, in the rule details). It is a cross-reference, not a compliance claim. Results of `1.3` and older have no such field, and a reader treats that as "not recorded".

**1.3** (additive; a minor bump). One optional field on a `coverage` entry, `walkedDirectories`, present only on `source:build-output`: `{ paths, complete }`, the skip-named directories (`build`, `dist`, `out`, ...) that the walk entered because they directly contain source files (redacted repository-relative paths) and whether that list is complete. Scan comparison uses it to treat findings below such a directory as ordinary. Results of `1.2` and older have no such field, and a reader treats that as "not recorded", never as "no directory was walked".

**1.2** (additive; a minor bump). One optional top-level field, `incremental`, present when the launcher offered incremental scans (the CLI does; the dashboard does not). `{ used, reason, basedOn, filesRescanned, filesReused, commitsScanned, commitsReused, code, history }`: `used` is true when an area reused data from an earlier stored scan; `reason` is a stable code (`requested_full`, `no_previous_scan`, `store_unavailable`, `previous_unreadable`, `no_saved_state`, `scopes_changed`, `tool_changed`, `config_changed`, `previous_incomplete`, `head_not_ancestor`, `git_failed`, `rules_unclassified`, `analyzer_changed`, `previous_state_too_large`, `previous_state_rejected`, `history_changed`) for the full scan, else `null`; `basedOn` is `{ scanId, revision }` of the stored scan or `null`; the counts are `null` when the scope did not run; `code` and `history` are `{ mode: "incremental" | "full", reason }` or `null`. In an incremental scan `ruleStats` examined counts include reused files and commits, except the history `blobs` target, which is `null` with a `reason`. Results of `1.0` and `1.1` have no `incremental` field, and a reader treats that as "not recorded".

**1.1** (additive; a minor bump). Four optional top-level fields (`ruleStats`, `standardsCoverage`, `suppressions`, `baseline`) and two optional finding fields (`suppression`, `inBaseline`). A `1.0` result has none of them, and a reader treats a missing field as "not recorded", never as "nothing ran" or "nothing checked".

- `ruleStats` (`RuleStat[]`): one entry per rule and coverage area where the rule ran (`completed` or `partial`). `ruleId`, `area` (a `Coverage.area`), `scope`, `status` (the area's status), `findings` (findings the rule reported in that area, counted before findings of several scopes are merged) and `targets`: a list of `{ unit, examined, reason }`. `unit` is an open string (`files`, `commits`, `blobs`, `pages`, `responses`, `unknown`; a new unit is not a schema change). `examined` is a count the analyzer measured, or `null` when it cannot be measured, and then `reason` says why (`reason` is `null` otherwise). An analyzer that reports nothing gets `{ unit: "unknown", examined: null, reason }`, never a guess. The same finding can count in two entries only for `source:react` and `source:heuristics`, which look at files that a language area also covers.
- `standardsCoverage` (`{ owasp, cweTop25 }`): one `StandardCoverageEntry` per OWASP Top 10 2025 category (A01 to A10, in order) and per CWE Top 25 2025 entry (rank order): `id`, `title`, `rank` (`null` for OWASP), `state`, `breadth`, `ruleIds` (rules that ran and contribute), `mappedRuleIds` (every rule of this PGARD version that maps to the entry) and a short English `reason`. `breadth` is `{ cwesWithRules, cwesInCategory }` for OWASP entries (how many CWEs of the category's "List of Mapped CWEs" have at least one PGARD rule) and `null` for CWE Top 25 entries. `state` is `rules_ran`, `rules_partial`, `not_run` or `no_rules`; it is a closed enum, so a new state would be a major change. None of the states means "safe" or "category covered": they say whether PGARD rules that map to the entry ran. It is derived by `computeStandardsCoverage` from the rule mappings and from the scan's own coverage and `ruleStats`. `rules_ran` needs a mapped rule that ran, every contributing area `completed`, no partial code-scope area at all (even one that lists no rules), every scope that has a mapped rule run, every language present covered by a completed mapped rule (history and web rules are not language-bound), no mapped rule that examined 0 targets, and no ran rule missing from the rule catalog. `rules_partial` is some mapped rule that ran with any of those conditions unmet; `not_run` is rules exist but none ran; `no_rules` is no rule maps to the entry (reason `no rules`). Advisories (OSV) are not rules of a scan and never count.
- `Finding.suppression?: { reason: string; expires?: string; source: "pgard.config.json" }`: set only when an active suppression of `pgard.config.json` matched the finding. The finding stays in the result.
- `Finding.inBaseline?: true`: set only when the repository's baseline (`pgard baseline set`) contains the finding (same identity as the scan comparison). Never `false`; absent means not in the baseline, or no baseline.
- `ScanResult.suppressions?: { source; suppressed; critical; bySeverity; entries: { ruleId; path; reason; expires?; state: "active" | "expired"; matched; wildcard; farExpiry }[]; incomplete }`: present when the config has at least one suppression. `suppressed` counts the findings carrying `suppression`, `critical` how many of them are critical, `bySeverity` the count per severity (adds up to `suppressed`), `farExpiry` whether `expires` is more than 366 days ahead, `matched` the findings an entry matches (0 when expired), `wildcard` whether the entry's path matches every file, and `incomplete` whether the matching work budget ran out (later findings are then not suppressed).
- `ScanResult.baseline?: { setAt; scanId; revision; total; matched; new; newInUncertainAreas; toolVersionChanged }`: present when a baseline was applied. `matched` is the number of findings flagged `inBaseline` that are not suppressed (the size of the "In baseline" group), `new` the findings that are neither in the baseline nor suppressed (test and vendored findings included), `total` the findings in the baseline scan. Suppressed findings are left out of a stored baseline.

A blocked or failed scan writes `ruleStats: []` and a `standardsCoverage` in which no entry is `rules_ran` (`not_run` or `no_rules`).

The `suppressions` and `baseline` objects are optional and independent of any other new field, and `SuppressionState` and the `source` literal are the only closed values added (a new value there would be a major change). A suppression, or a baseline, never changes `overallStatus`, the status of any coverage area or `authorization`: the status comes from coverage only. The only coverage text that mentions suppressions is the `note` of the `source:config` area, which counts them.

**1.0**: the original shape.

## Changing the version

The version constant `SCHEMA_VERSION` is bumped in the same pull request that changes the shape, together with a note here and tests for the new compatibility case. The reader's accepted major is derived from that constant.
